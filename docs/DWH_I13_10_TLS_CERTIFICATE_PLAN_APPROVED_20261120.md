# I13-10 — Сертификат внутреннего УЦ и DNS-имя сервера DWH

<sub>План утверждён пользователем 20.11.2026 · Т1 = B (PFX от администраторов), Т2 — выполнено сертификатом, Т3 = A (перенаправление), Т4 отпадает (ключ создан администраторами)</sub>

## 1. Требование

Браузер открывает DWH по DNS-имени без предупреждения о сертификате; `nginx -t` PASS (критерий roadmap, I13-10). Сейчас — временный самоподписанный сертификат на `https://10.1.20.20` (отступление от С5, план I16 раздел 15).

## 2. Что есть сейчас (проверено по коду 19.11.2026)

- nginx: `/etc/nginx/sites-available/dwh.conf` из шаблона `deploy/nginx/dwh.conf` — только 443, `server_name` из шаблона, файлы `/etc/dwh/tls/dwh.crt` и `dwh.key`, заголовок HSTS.
- Временный сертификат выпущен `openssl req -x509` (инструкция сервера, раздел 2, п. 6): RSA 3072, `CN=app-dwh-srv`, SAN `IP:10.1.20.20`, `DNS:app-dwh-srv`.
- `tools/server/dwh_check_network.py --name <имя>` уже проверяет сертификат: срок > 30 дней, совпадение с ключом, имя.
- API не привязан к имени или адресу сервера (нет списка разрешённых хостов, CORS) — смена имени код backend не затрагивает. Вход через домен (I20) от имени сервера не зависит.
- Пакет БД не нужен.

## 3. Решения (на утверждение)

| № | Вопрос | Рекомендация | Другой вариант |
|---|---|---|---|
| Т1 | Как получить сертификат | **A** — ключ и запрос на сертификат (CSR) создаются на сервере, ключ сервер не покидает; администраторы подписывают CSR в УЦ и возвращают сертификат с цепочкой | B — администраторы выдают файл PFX с ключом (ключ передаётся по сети и лежит в файлах) |
| Т2 | Имена в сертификате | **A** — DNS-имя (выбирают администраторы, например `dwh.vtbaze.local`) + `IP:10.1.20.20` | B — только DNS-имя (старый адрес будет с предупреждением) |
| Т3 | Старый адрес `https://10.1.20.20` | **A** — перенаправление на DNS-имя (одно имя у всех; сессия входа привязана к имени в браузере) | B — оба адреса работают как сейчас |
| Т4 | Ключ | **A** — RSA 3072 (принимает шаблон «Веб-сервер» любого УЦ Windows) | B — ECDSA P-256 |

## 4. Нужно от администраторов (до шага 3)

1. DNS-имя сервера и запись A → `10.1.20.20` в DNS домена.
2. Шаблон УЦ для подписи CSR (обычно «Веб-сервер»), разрешено ли IP в SAN (Т2).
3. Корневой сертификат УЦ доверен на ПК пользователей (обычно групповой политикой домена) — иначе предупреждение останется.
4. Выдача в формате Base64 (PEM): сертификат сервера и промежуточные сертификаты цепочки.

## 5. Шаги до `DONE`

1. Утверждение плана (Т1–Т4) и сведения от администраторов (раздел 4).
2. Песочница: инструмент `tools/server/dwh_tls.py`:
   - `csr --name <DNS> [--ip 10.1.20.20]` — ключ `/etc/dwh/tls/pending/dwh.key` (права 600) и CSR в `/srv/dwh/incoming/dwh.csr`; CSR не секрет;
   - `install --cert <файл> [--chain <файл>]` — проверка до замены: сертификат подходит к ключу из `pending`, имена из CSR, цепочка (`openssl verify`), срок > 30 дней; копия текущих файлов, замена, `server_name` и перенаправление (Т3) в `dwh.conf`, `nginx -t`, `reload`; при ошибке — возврат прежних файлов;
   - `--rollback` — возврат предыдущего сертификата;
   - шаблон `deploy/nginx/dwh.conf` — блок перенаправления (Т3);
   - тесты с тестовым УЦ, проверка `nginx -t` и подмены на nginx песочницы; инструкция сервера (раздел о сертификате), `DWH_ENGINES.md` (эксплуатация).
3. Выпуск; на сервере `dwh_tls.py csr` → файл `dwh.csr` администраторам. *(При Т1 = B не нужен — PFX выдан, 20.11.2026.)*
4. Установка: `dwh_tls.py install`, `dwh_check_network.py --name <DNS>` PASS; с ПК: DNS-имя без предупреждения, старый адрес перенаправляет, вход (локальный и домен), помощник; реестр.
5. Подтверждение пользователя — I13-10 `DONE`.

## 6. Не входит

- HTTP на порту 80 (сейчас закрыт) — не открывается.
- Автоматическое продление: срок проверяет `dwh_check_network.py` (предупреждение за 30 дней), продление — повтором шагов 3–4.
- Сертификат для `dwh-llm` (только localhost) и для PostgreSQL (только localhost).

## 8. Шаг 2 — инструмент в песочнице (20.11.2026)

`tools/server/dwh_tls.py`:
- `install --pfx … --name dwh.vtbaze.local --ip 10.1.20.20` — пароль PFX вводится без показа и передаётся `openssl` через stdin (не в окружении, не в файлах, не в выводе); старые PFX (RC2/3DES) — повтор с `-legacy`. Проверки до замены: ключ подходит к сертификату, имя и адрес, срок > 30 дней, цепочка до корневого УЦ из PFX (`openssl verify -purpose sslserver`; без корня — `--ca-file`). Без `--apply` — план и разница файла nginx, ничего не меняется;
- `--apply` — копия текущих файлов в `/etc/dwh/tls/backup/<время>/`, запись `dwh.crt` (сертификат + промежуточные, корень не отдаётся), `dwh.key` (600), `ca.crt` (корневой УЦ, для проверок), `/etc/nginx/sites-available/dwh.conf` из шаблона выпуска с именем; `nginx -t`, `systemctl reload nginx`, живая проверка (сертификат по имени доверен и совпадает, `/` отвечает 200, `https://10.1.20.20` → 301 на `https://dwh.vtbaze.local/…`); при ошибке — прежние файлы и `reload`;
- `rollback` — возврат последней копии; `check` — только живая проверка.

Шаблон `deploy/nginx/dwh.conf`: блок `default_server` с перенаправлением на имя (Т3), основной блок — по `server_name`.

Проверки: тесты `backend/tests/test_dwh_tls.py` 10/10 (тестовый УЦ, настоящий `openssl`: план, неверный пароль, чужое имя, короткий срок, нет корня / `--ca-file`, legacy-PFX, установка и откат, отказ живой проверки и `nginx -t` с откатом, промежуточный УЦ); все тесты 612 OK; сквозная на настоящем nginx песочницы `scratchpad/i1310/e2e.sh` — план, отказ неверного пароля, установка, проверка, откат на прежний самоподписанный — `E2E_RESULT: PASS`.

Далее — шаг 3: выпуск с инструментом; шаги 3–4 объединяются (CSR не нужен при Т1 = B): установка на сервере и проверка с ПК.

## 9. Шаг 4, попытка 1 — откат (20.11.2026, выпуск `2026.11.43`)

План (без `--apply`) — все проверки PASS; разница файла nginx — только `server_name` и блок перенаправления. `--apply`: копия `/etc/dwh/tls/backup/20261120_095633`, файлы записаны, `nginx -t` и `reload` прошли, но живая проверка сразу после `reload` получила прежний самоподписанный сертификат (`CERTIFICATE_VERIFY_FAILED: self-signed`) → защита вернула прежние файлы, `reload`, `TLS_RESULT: FAIL (rolled back)`. Сервер работает как до попытки.

Причина: `reload` nginx плавный — несколько секунд соединения обслуживают старые процессы со старым сертификатом; в сквозной проверке песочницы после `reload` стояла пауза 1,5 с, поэтому случай не был пойман. Исправление: живая проверка повторяется раз в секунду до `--wait` секунд (по умолчанию 20), пока сервер не отдаёт новый сертификат; сквозная проверка — без паузы. Тесты 11/11 (новый — ожидание новых процессов), все 613 OK, сквозная PASS. Доставка — выпуск `2026.11.44`, затем повтор `--apply`.

## 10. Шаг 4 — установка PASS (20.11.2026, выпуск `2026.11.44`)

Осталось: удалить PFX с сервера (`/etc/dwh/tls/pending/dwh.pfx`; копия у пользователя), подтверждение — I13-10 `DONE`.
