# DWH — справка пользователя

<sub>Версия **1.3.1** · **17.11.2026** · Описывает приложение DWH на сервере `https://10.1.20.20` (выпуск с конструктором витрин DM, который сам создаёт, меняет и удаляет таблицы витрин).</sub>

Справка — основа ответов ИИ-помощника (I17). Помощник отвечает по разделам, доступным роли пользователя.

## 0. Разметка доступа (для помощника)
<!-- access: all -->

После заголовка каждого раздела стоит строка `<!-- access: … -->`. Подразделы наследуют разметку раздела, если у них нет своей.

- `all` — раздел виден любому пользователю с правом `AI_ASSISTANT_USE`.
- `permissions=A,B` — нужны **все** перечисленные права.
- `level=ADMIN` — нужен уровень учётной записи `ADMIN` или `SUPERADMIN`; `level=SUPERADMIN` — только `SUPERADMIN`.
- `resource=MODULE:CDP` — нужен доступ к ресурсу «модуль CDP» (рабочее пространство DWH).
- Условия в одной строке соединяются через `;` и действуют вместе.

Если пользователь спрашивает о разделе, который ему недоступен, помощник отвечает: «Текущей роли эта информация недоступна». Содержимое такого раздела он не пересказывает.

## 1. Вход и общие элементы
<!-- access: all -->

### 1.1. Вход в приложение

1. Откройте в браузере `https://10.1.20.20`.
2. Пока у сервера временный сертификат, браузер предупредит о небезопасном подключении: выберите «Дополнительно» → «Перейти на сайт». Сертификат внутреннего УЦ ожидается (задача I13-10).
3. Введите имя пользователя и пароль DWH и нажмите «Войти».

Если администратор выдал временный пароль, после входа откроется экран «Изменить пароль». Требования к паролю:
- 12–128 символов;
- минимум 3 из 4 категорий: заглавные буквы, строчные буквы, цифры, символы.

### 1.2. Язык и выход

- Язык интерфейса (русский, английский, азербайджанский) выбирается переключателем «Язык» на боковой панели. Выбор запоминается в браузере.
- «Выйти» на боковой панели завершает сессию.

### 1.3. Меню

Меню из трёх пунктов. Пункт виден, только если у роли есть права хотя бы на одну его часть:
- **«Загрузки»** — работа загрузок: объекты, запуски, ошибки, качество данных, заявки CRM;
- **«Отчётность»** — отчёты по розничным заявкам;
- **«Администрирование»** — настройки: модули, пользователи, роли, доступ, интеграции.

Если в меню нет ни одного пункта, появляется сообщение «Для этой учётной записи не назначено доступное рабочее пространство DWH». Нужные права выдаёт администратор (раздел 4).

### 1.4. Подтверждения и ошибки

- Действия, которые что-то меняют (запуск, публикация, отзыв), сначала показывают окно подтверждения.
- Важность проблем: `ERROR` — «Серьёзное», `WARNING` — «Предупреждение».
- Технические коды (`SOURCE_NO_RESPONSE`, `READY`, `DRIFT` и др.) не переводятся — по ним ищут в справке и журналах.

## 2. Загрузки
<!-- access: resource=MODULE:CDP -->

Раздел «Загрузки» показывает, как работают загрузки данных из источников. Настройки источников и объектов — в «Администрировании» (раздел 5).

Термины:
- **источник** — внешняя система: CRM (`CRM_RETAIL`) или база `OPERATION_COLLECTOR`;
- **объект** — таблица или представление источника;
- **STG** — первая копия данных в DWH, как в источнике;
- **ODS** — очищенные и приведённые данные;
- **диспетчер** — служба на сервере (`dwh-dispatcher`), выполняет заявки по очереди.

### 2.1. Вкладка «Объекты»
<!-- access: resource=MODULE:CDP; permissions=NAV_INTEGRATION_VIEW,INTEGRATION_VIEW -->

Состояние каждого объекта источника. Колонки:
- «Объект»;
- «Настройка» — опубликованные версии маппинга STG и ODS, либо «нет опубликованного маппинга»;
- «Последний запуск STG», «Последний запуск ODS» — статус, время, «прочитано / вставлено / обновлено»;
- «Последняя ошибка» — полный текст по кнопке «Показать сообщение полностью»;
- «Последняя заявка»;
- «Действия».

Объекты CRM помечены «CRM (свой ETL)»: они загружаются отдельным контуром CRM (вкладка «Управление запусками CRM»).

Кнопка «Обновить» перечитывает состояние.

### 2.2. Ручной запуск объекта
<!-- access: resource=MODULE:CDP; permissions=NAV_INTEGRATION_VIEW,INTEGRATION_VIEW; level=ADMIN -->

Кнопки в колонке «Действия» есть у объектов с опубликованным маппингом:
- **«Запустить»** — STG по стратегии версии в силе (FULL или INCREMENTAL), затем ODS;
- **«Заново полностью»** — один раз прочитать объект целиком, без учёта инкремента, затем ODS. Нужна, если данные в STG нужно полностью сверить с источником;
- **«Продолжить (ODS)»** — только шаг ODS из готовой таблицы STG. Доступна, когда последний STG прошёл успешно, а ODS после него упал.

Порядок:
1. Нажмите кнопку и подтвердите «Создать заявку».
2. Появится сообщение «Заявка №N … создана; её выполнит диспетчер», в колонке заявки — «ждёт диспетчер».
3. Через несколько секунд нажмите «Обновить»: статус заявки станет `RUNNING`, затем `SUCCESS` или `FAILED`.

На объект может быть только одна активная заявка. Пока заявка в очереди, её можно отменить кнопкой «Отменить заявку».

### 2.3. Стратегии FULL и INCREMENTAL
<!-- access: resource=MODULE:CDP; permissions=NAV_INTEGRATION_VIEW,INTEGRATION_VIEW -->

- **FULL** — каждый запуск читает объект целиком.
- **INCREMENTAL** — читает строки, у которых «поле изменения» (дата, время или число) не старше последней успешной загрузки минус «перекрытие». Перекрытие задаётся в минутах и страхует от строк, записанных в источник с опозданием. Первый запуск читает всё.
- **Признак удаления** — необязательное поле `BOOLEAN`. Строки с ним помечаются удалёнными в истории.

Стратегия, поле изменения и перекрытие задаются в «Маппинге» объекта (раздел 5.3) и действуют с новой опубликованной версией.

### 2.4. Вкладка «Запуски»
<!-- access: resource=MODULE:CDP; permissions=NAV_ETL_VIEW,ETL_VIEW -->

История пакетов загрузки:
- пакет, режим, попытка, статус, бизнес-дата, время;
- задания пакета: прочитано, добавлено, обновлено, отклонено, ошибки.

Загрузки объектов показываются с конвейером `OBJECT_LOAD`, загрузки CRM — со своими конвейерами.

### 2.5. Вкладка «Ошибки и история»
<!-- access: resource=MODULE:CDP; level=ADMIN; permissions=ADMIN_INTEGRATION_MANAGE -->

Запуски ETL, ошибки ETL, проверки DQ и проблемы DQ на одном экране. Кнопка «Показать ошибки» у пакета фильтрует ошибки по нему, «Сбросить фильтр» снимает фильтр.

У ошибки загрузки видны:
- «Этап»;
- «Столбец»;
- «Некорректное значение» (поле `bad_value`);
- «Технические сведения».

Для ошибок данных указано поле и правило, число неверных строк, до 5 примеров значений с количеством и до 10 ключей строк. Например: «4 of 65 rows invalid; values: 'birthD' x4; keys: id=1, …».

### 2.6. Частые ошибки загрузки
<!-- access: resource=MODULE:CDP; permissions=NAV_INTEGRATION_VIEW,INTEGRATION_VIEW -->

| Код | Что значит | Что делать |
|---|---|---|
| `SOURCE_NO_RESPONSE` | Источник не ответил 300 с (запрос отменён, через 30 с соединение разорвано) | Проверить доступность источника и сеть; повторить «Запустить». Если повторяется — к владельцу источника |
| `LOCK_TIMEOUT` | Таблица источника заблокирована дольше 60 с | Повторить позже, когда в источнике закончится обработка |
| `TIMEOUT` | Запуск шёл дольше часа и остановлен | Проверить объём; при необходимости — INCREMENTAL |
| `DISPATCHER_LOST` | Диспетчер перезапустился во время заявки; заявка закрыта | Создать заявку снова |
| `TYPE_CONVERSION` | Значение не подходит к целевому типу (например, дата `birthD`) | Посмотреть примеры значений в ошибке; исправить данные в источнике или правило ODS (раздел 5.4) |
| `SOURCE_WRITE_BLOCKED`, `SOURCE_NOT_READ_ONLY` | Защита: DWH обращается к источникам только на чтение | Это защита, а не сбой; сообщить администратору DWH |

### 2.7. Вкладка «Качество данных»
<!-- access: resource=MODULE:CDP; permissions=NAV_DQ_VIEW,DQ_VIEW -->

История проверок DQ. По каждой проверке видны:
- число правил: пройдено, предупреждения, неуспешно;
- результаты правил — щелчок по правилу открывает метрику, ожидаемое значение и строки с ошибками; повторный щелчок закрывает;
- проблемы на уровне строк: источник, заявка, некорректное значение, когда решено.

Список проблем выгружается кнопкой «Выгрузить».

### 2.8. Вкладка «Управление запусками CRM»
<!-- access: resource=MODULE:CDP; level=ADMIN; permissions=ADMIN_INTEGRATION_MANAGE -->

Очередь запросов на запуск заданий CRM ETL.
1. «Создать запрос на выполнение»: выберите задание, успешный пакет источника и режим (`FULL` или `CONTINUE` — продолжить с места остановки).
2. «Поставить в очередь».

Запросы выполняет тот же диспетчер. Запрос в статусе «Ожидает» можно отменить.

### 2.9. Вкладка «Витрины»
<!-- access: resource=MODULE:CDP; permissions=NAV_INTEGRATION_VIEW,INTEGRATION_VIEW -->

Состояние витрин DM — отчётных таблиц схемы `dm`, которые собираются из таблиц ODS. Одна строка — одна витрина:
- **«Версия»** — опубликованная версия настройки; если есть черновик, он показан ниже;
- **«Последний запуск»** — итог (`SUCCESS` / `FAILED`), время и число строк;
- **«Ошибка»** — код и причина. `DM_KEY_NOT_UNIQUE` / `DM_LOOKUP_NOT_UNIQUE`: ключ таблицы или значение справочника повторяется — показано, сколько значений повторяется, и примеры. `DM_KEY_NULL`: пустой ключ в основной таблице. `DM_SOURCE_MISSING`: в ODS нет таблицы или колонки. При ошибке витрина сохраняет прежние строки;
- **«Запрос»** — последняя заявка: «вручную» или «после ODS».

Витрина с флагом «обновляется после ODS» встаёт в очередь сама после успешного шага ODS любой своей таблицы. Администратор может нажать «Обновить витрину»: строки витрины полностью перезаписываются из ODS одной операцией, отчёты до конца обновления видят прежние данные. Заявки выполняет диспетчер; заявку в статусе `QUEUED` можно отменить.

## 3. Отчётность
<!-- access: resource=MODULE:CDP; permissions=NAV_REPORTING_VIEW,REPORT_VIEW -->

### 3.1. «Розничные заявки»

Текущий срез заявок из розничной витрины `dm.v_retail_application_current`.
- Показатели: всего заявок, предварительно одобренные условия, условия, выбранные клиентом, окончательные условия оформления.
- Разделы с разбивкой по статусу, этапу, каналу продаж и предварительно одобренному продукту. Раздел открывается и закрывается щелчком.
- «Фильтр отчёта» — поиск строки в отчёте по слову: введите не менее 3 символов, «Найдено: N», кнопка «Перейти» — к следующему совпадению.

### 3.2. Выгрузка

Кнопка «Выгрузить» в разделе отчёта — форматы Excel (`xlsx`), PDF и текст. В PDF кириллица выводится шрифтом DejaVu, установленным на сервере.

### 3.3. Отчёт по описанию (ИИ-помощник)
<!-- access: resource=MODULE:CDP; permissions=AI_REPORT_RUN -->

Кнопка «Помощник» → режим «Отчёт по описанию».
- Опишите отчёт словами, например «дай все кредиты по каналу ИБ» или «количество заявок по каналам продаж».
- Помощник составляет SQL только по витринам белого списка, разрешённым роли, и показывает число строк, таблицу, «Показать SQL» и «Скачать CSV».
- SQL выполняет отдельная роль только на чтение; данные модели не передаются.
- Пока помощник думает, вместо «Отправить» есть кнопка «Стоп» — остановить ответ и задать другой вопрос.

### 3.4. Сохранённые отчёты: «Мои и общие отчёты»
<!-- access: resource=MODULE:CDP; permissions=NAV_REPORTING_VIEW,REPORT_VIEW -->

Отчёт помощника можно сохранить и открывать позже. Сохраняются описание и запрос, не строки: при открытии отчёт выполняется заново, со свежими данными и с правами того, кто открывает.

**Как сохранить** (нужно право «Отчёт по описанию»):
1. В чате помощника под готовым отчётом нажмите «Сохранить в Отчётность».
2. Проверьте «Название».
3. В поле «Папка» выберите свою личную или общую папку либо «+ Новая папка», введите «Название папки» и «Видимость»: «личная» или «общая».
4. Нажмите «Сохранить» — появится «Сохранено в «Отчётность»: <папка>».

**Где смотреть:** «Отчёты» → вкладка «Мои и общие отчёты».
- Слева папки: «личная» видна только владельцу, «общая» — всем, у кого есть «Отчётность». Там же можно создать папку: название, видимость, «Создать папку».
- Справа отчёты выбранной папки: название, владелец, дата. «Открыть» — выполнить отчёт: таблица, «Показать SQL», «Скачать CSV».
- «Удалить» отчёт может его владелец, а в общей папке — также администратор. Пустую папку удаляет её владелец (общую — также администратор).
- Если отчёт построен по витрине, закрытой для вашей роли, рядом написано «Текущей роли эта информация недоступна», и он не открывается.

## 4. Администрирование: пользователи и доступ
<!-- access: level=ADMIN -->

Раздел «Администрирование» виден учётным записям `ADMIN` и `SUPERADMIN`. Вкладка показывается, если у учётной записи есть её право.

### 4.1. «Пользователи»
<!-- access: level=ADMIN; permissions=ADMIN_USER_MANAGE -->

- «Создать пользователя»: имя пользователя (нельзя изменить после создания), отображаемое название, почта, уровень учётной записи, провайдер аутентификации, начальный пароль, «Требовать смену пароля».
- «Сбросить пароль» → «Установить временный пароль». При следующем входе пользователь сменит его.
- «Отключить» / «Включить»; «Назначить USER» / «Назначить ADMIN» меняет уровень.
- Записи «Защищено» (системные) менять нельзя.

### 4.2. «Роли»
<!-- access: level=ADMIN; permissions=ADMIN_ROLE_MANAGE -->

Справочник бизнес-ролей: «Создать роль» (код роли нельзя изменить после создания), название, описание, «Отключить» / «Включить». В таблице видно число пользователей, разрешений и ресурсов роли.

### 4.3. «Доступ»
<!-- access: level=ADMIN; permissions=ADMIN_ACCESS_MANAGE -->

- **«Политики ролей»** — выберите бизнес-роль. В «Разрешениях» нажмите «Предоставить» или «Отозвать» у нужного права. В «Ресурсах» так же — модули и наборы данных.
- **«Назначения пользователей»** — выберите пользователя `USER` и предоставьте ему бизнес-роли. У пользователя может быть несколько ролей.

Как дать пользователю доступ, по порядку:
1. «Роли» → «Создать роль» (или выберите существующую).
2. «Доступ» → «Политики ролей» → выберите роль → «Предоставить» нужные «Разрешения» и «Ресурсы» (например, модуль CDP). Роль без прав ничего не открывает.
3. «Доступ» → «Назначения пользователей» → выберите пользователя `USER` → «Предоставить» ему эту роль.

Пользователям `ADMIN` и `SUPERADMIN` роли не нужны.

`SUPERADMIN` и `ADMIN` получают все активные права автоматически; пользователям `USER` права дают только роли.

Права, которые открывают разделы:

| Что открыть | Нужные права |
|---|---|
| «Загрузки» → «Объекты» | ресурс модуль CDP, `NAV_INTEGRATION_VIEW`, `INTEGRATION_VIEW` |
| «Загрузки» → «Витрины» | ресурс модуль CDP, `NAV_INTEGRATION_VIEW`, `INTEGRATION_VIEW`; кнопки «Обновить витрину» — администратор (`ADMIN_INTEGRATION_MANAGE`) |
| Отчёт помощника по витрине | `AI_REPORT_RUN` и право, указанное у витрины (обычно `REPORT_VIEW`) |
| «Загрузки» → «Запуски» | ресурс модуль CDP, `NAV_ETL_VIEW`, `ETL_VIEW` |
| «Загрузки» → «Качество данных» | ресурс модуль CDP, `NAV_DQ_VIEW`, `DQ_VIEW` |
| «Отчётность» | ресурс модуль CDP, `NAV_REPORTING_VIEW`, `REPORT_VIEW` |
| Чат ИИ-помощника | `AI_ASSISTANT_USE` |
| Отчёт по описанию | `AI_REPORT_RUN` |
| Настройки ИИ-помощника | `AI_ADMIN_MANAGE` |

### 4.4. «Модули»
<!-- access: level=ADMIN; permissions=ADMIN_MODULE_MANAGE -->

Справочник бизнес-модулей: «Создать модуль», «Изменить», «Отключить» / «Включить». Код модуля нельзя изменить после создания.

## 5. Администрирование: интеграции
<!-- access: level=ADMIN; permissions=ADMIN_INTEGRATION_MANAGE -->

Вкладка «Интеграции»: «Исходные системы», «Объекты источника», «Контракты», «Сопоставления», «Правила DQ».

### 5.1. Исходные системы и подключение

1. «Создать исходную систему»: код, название, тип источника, описание.
2. Кнопка «Подключение» у системы открывает панель подключения.
   - **База данных:** хост, порт, база данных, имя пользователя, режим SSL → «Сохранить настройки».
   - **Папка с файлами:** папка и маска файлов.
   - **API:** хранится только название; URL и учётные данные задаются у каждого объекта.
3. Учётные данные: введите пароль или токен в поле «Пароль или токен» → «Сохранить учётные данные». Пароль не отображается и никогда не показывается снова. Заменить — «Заменить учётные данные», отключить — «Отозвать учётные данные».
4. «Проверить подключение». При успехе — «Подключение работает: статус READY»; при ошибке — понятный код (таблица ниже).
5. После `READY` доступны «Показать объекты источника» (до 5000, с фильтром) и «Снять снимок структуры» — он нужен для маппинга.

Снимок структуры `CRM_RETAIL` из интерфейса не снимают: CRM пользуется своим контуром.

| Код проверки | Что значит |
|---|---|
| `AUTH_FAILED` | неверный пользователь или пароль |
| `HOST_NOT_FOUND` | имя хоста не найдено |
| `CONNECTION_REFUSED` | хост или порт отклонил подключение (например, источник не пускает сервер DWH в `pg_hba.conf`) |
| `CONNECT_TIMEOUT` | истекло время подключения |
| `DATABASE_NOT_FOUND` | базы данных нет на сервере |
| `SSL_ERROR` | ошибка SSL: проверьте режим SSL |
| `ACCESS_DENIED` | у пользователя нет доступа к базе |
| `NO_CREDENTIAL` | учётные данные не заданы или отозваны |
| `NOT_READ_ONLY` | не удалось открыть сессию только на чтение |

**Где хранится пароль источника.** Пароль шифруется (AES-256-GCM) в хранилище секретов на сервере DWH (`/var/lib/dwh/secrets`). Мастер-ключ защищён `systemd-creds` и расшифровывается только на этом сервере. Пароль не выдаётся ни в интерфейсе, ни в журналах, ни администраторам. Каждое задание, чтение и отзыв записывается в журнал.

### 5.2. Объекты источника

«Создать объект источника»: исходная система, схема и объект источника, тип объекта, порядок загрузки. «Отключить» убирает объект из загрузок, не удаляя историю.

### 5.3. «Маппинг»: источник → STG

Кнопка «Маппинг» у объекта, вкладка «Источник → STG».
1. Нужен снимок структуры (раздел 5.1). Строка «Снимок структуры №N: колонок M».
2. «Целевая схема» и «Целевая таблица». Можно выбрать существующую таблицу или ввести имя новой: строчная латиница, цифры и `_`.
3. Поля:
   - «В маппинг»;
   - «Поле источника» → «Целевое поле»;
   - «Целевой тип» и «Совместимость»: тот же тип, безопасно, условно — нужно «подтвердить», несовместимо;
   - «Правило записи»;
   - «Явный NULL»;
   - «Ключ» — бизнес-ключ, обязателен.
4. «Стратегия загрузки» — раздел 2.3.
5. «Сохранить черновик» → «Проверить» → при успехе «Опубликовать». Опубликованная версия не меняется; изменения — новой версией.
6. **Новая таблица или колонка:** «Создать проект изменения (DDL)». Интерфейс DDL не выполняет: проект применяется отдельным пакетом БД (проверка на копии, затем на рабочей базе). До этого проверка покажет «целевой таблицы ещё нет».
7. «Проверить drift» сравнивает опубликованную версию с последним снимком. При расхождении статус `DRIFT` — новые, удалённые колонки или изменённые типы; без расхождений — `READY`.

### 5.4. «Маппинг»: STG → ODS

Вкладка «STG → ODS». Нужен опубликованный маппинг STG.
- «Таблица ODS (схема ods)».
- У каждого поля одно преобразование из закрытого списка:

| Преобразование | Что делает |
|---|---|
| «Копировать» | значение как есть |
| «Привести тип» | меняет тип значения |
| «Убрать пробелы» | убирает пробелы по краям |
| «Верхний регистр», «Нижний регистр» | меняет регистр |
| «Пустое → NULL» | пустую строку превращает в NULL |
| «Значение, если пусто» | подставляет значение вместо пустого |
| «Константа» | одно и то же значение во всех строках |
| «Дата из текста» | разбирает дату по формату, например `DD.MM.YYYY` |
| «Номер запуска», «Время загрузки» | технические поля, только при вставке |

- Значения — только данные, не SQL.
- Порядок тот же: «Сохранить черновик» → «Проверить» → «Опубликовать». Следующий запуск переносит STG в ODS по новой версии.
- Если «Дата из текста» падает на неверных значениях, ошибка покажет примеры (раздел 2.5).

### 5.5. Контракты, сопоставления, правила DQ (контур CRM)

Настройки контура CRM ETL; у каждой записи версия и «Причина изменения».
- **«Контракты»** — ожидаемые столбцы и типы источника для таблиц STG.
- **«Сопоставления»** — преобразования STG → целевой объект. Правка требует права `ADMIN_MAPPING_MANAGE`, без него — «Только чтение».
- **«Правила DQ»** — код, название, важность, категория, целевой объект и столбец, лимит проблем.

### 5.6. «Витрины DM»: ключи и конструктор витрин

**Сущности и ключи.** Сущность — то, о чём строки витрины (например, «Клиент»). Для каждой таблицы ODS укажите её колонку-ключ: названия могут различаться (`client_id`, `cust_id`, `customer_no`), а типы должны быть совместимы (числа с числами, текст с текстом) — иначе ключ не сохранится.

**Витрина.** Код витрины — имя таблицы `dm.<код>`, после создания не меняется. Укажите название, нужное право для просмотра (обычно `REPORT_VIEW`), «Доступна ИИ-помощнику» (тогда после публикации витрина попадает в белый список помощника с этим правом) и «Обновлять после ODS».

**Версия.** «Новый черновик» копирует опубликованную версию. В черновике:
1. **Сущность зерна** — одна строка витрины на её ключ.
2. **Таблицы ODS**, у каждой псевдоним и вид:
   - «Основная (зерно)» — ровно одна, задаёт строки витрины;
   - «Тот же ключ» — дополняет строку (у одного ключа одна строка);
   - «Дочерняя (агрегаты)» — много строк на ключ, поля только через сумму, количество, количество различных, минимум, максимум, среднее;
   - «Справочник» — соединяется с колонкой более ранней таблицы, например «код статуса → название». Одну таблицу можно подключить несколько раз под разными псевдонимами — например, «основной» и «запасной» менеджер.
   «Все колонки в поля» добавляет колонки таблицы полями витрины.
3. **Поля**: имя, подпись, тип, отметка «Ключ» (ключ основной таблицы) и откуда брать значение. Если источников несколько, берётся первое непустое по порядку.
4. **Фильтры**: таблица, колонка, оператор, значение (для `IN` — через запятую).

«Сохранить» показывает замечания: нет ключа, у дочерней колонки нет агрегата и т. п. Ниже — «Структура таблицы витрины» (будет ли таблица создана или перестроена и какие поля удаляются) и SQL заполнения: каждая таблица сначала сводится к ключу, потом соединяется, поэтому суммы не умножаются.

**Публикация.** «Опубликовать» делает всё сама, без SQL и пакетов:
- **структура не меняется** (другой фильтр, приоритет, справочник) — версия публикуется сразу, витрина обновляется из ODS;
- **новая витрина или изменились поля** — рядом строится новая таблица, диспетчер заполняет её из ODS, затем таблицы меняются местами. Пока идёт построение, отчёты и помощник видят прежние данные; в черновике видна надпись «Идёт построение таблицы витрины», статус обновляется сам;
- **поля удаляются или меняют тип** — сначала показывается, что это затронет: сохранённые отчёты, примеры и колонки-справочники ИИ-помощника, которые используют эти поля. Публикация идёт только после подтверждения; колонки-справочники на удалённых полях отключаются, а сохранённые отчёты с ними перестают работать — их нужно поправить или удалить;
- **если заполнение не удалось** (например, повторяется ключ), новая таблица удаляется, опубликованная версия и её данные остаются. В черновике видна причина; исправьте его и опубликуйте снова.

Опубликованную версию изменить нельзя — только новым черновиком.

**Удаление витрины.** Кнопка «Удалить витрину» в списке витрин. Сначала показывается, какие сохранённые отчёты и примеры помощника её используют; после подтверждения таблица витрины удаляется, витрина пропадает из «Загрузок», «Отчётности» и у помощника. Код витрины остаётся занят, история запусков сохраняется.

## 7. Эксплуатация сервера
<!-- access: level=SUPERADMIN -->

Команды выполняются в SSH-сессии на сервере `app-dwh-srv` (`ssh elshad@10.1.20.20`), не на ПК. Подробно — `docs/DWH_SERVER_RUNBOOK.md`.

### 7.1. Обновление и откат

1. На ПК соберите пакет выпуска:
   ```powershell
   & "C:\Users\elshad.asgarov\Desktop\DWH\dwh\tools\make_release.ps1" -Version <версия>
   ```
2. Скопируйте его на сервер:
   ```powershell
   scp "C:\Users\elshad.asgarov\Desktop\DWH\dwh\runtime\releases\dwh_release_<версия>.zip" "C:\Users\elshad.asgarov\Desktop\DWH\dwh\runtime\releases\dwh_release_<версия>.sha256" elshad@10.1.20.20:/srv/dwh/incoming/
   ```
3. Проверьте пакет на сервере:
   ```bash
   cd /srv/dwh/incoming && sha256sum -c dwh_release_<версия>.sha256
   ```
4. Установите:
   ```bash
   sudo python3 /opt/dwh/current/src/tools/server/dwh_update.py /srv/dwh/incoming/dwh_release_<версия>.zip
   ```
   Перед переключением делается копия базы. Итог `UPDATE_RESULT: PASS`. При сбое нового выпуска сервер сам возвращает прежний: `ROLLED_BACK`.
5. Ручной откат:
   ```bash
   sudo python3 /opt/dwh/releases/<новый>/src/tools/server/dwh_update.py --rollback-to <прежний>
   ```

### 7.2. Копии базы

- Копия делается каждую ночь в 02:30 (`/backup/dwh`, хранится 14 копий) и перед каждым обновлением.
- Сделать копию вручную:
  ```bash
  sudo -u postgres python3 /opt/dwh/current/src/tools/server/dwh_backup.py --dir /backup/dwh --keep 14 --label manual
  ```
- Проверить, что копия восстанавливается (в отдельную базу `dwh_restore_test`, рабочая не меняется):
  ```bash
  sudo -u postgres python3 /opt/dwh/current/src/tools/server/dwh_backup.py --verify-restore /backup/dwh/<файл>.dump
  ```

### 7.3. Службы

- Состояние служб:
  ```bash
  systemctl status dwh-api dwh-dispatcher
  ```
- Журнал диспетчера:
  ```bash
  journalctl -u dwh-dispatcher -n 100
  ```

### 7.4. SQL-пакеты базы

Изменения структуры базы ставятся только пакетами, с разрешения:
- сначала проверка на копии (`--stage e1`);
- затем применение к рабочей базе (`--stage e2`, ввод `APPLY`) — `tools/server/dwh_sql_package.py`, раздел 4a инструкции сервера.
