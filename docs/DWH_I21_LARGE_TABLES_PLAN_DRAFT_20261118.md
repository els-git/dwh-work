# I21 «Загрузка больших таблиц» — проект плана (18.11.2026)

Статус: **проект**. ID I21 и решения Б1–Б6 — после утверждения пользователем.

## 1. Зачем

**Требование пользователя (18.11.2026):**
- миллионы строк в таблице — норма для DWH; при интеграции с core таблицы будут намного больше;
- первая загрузка всегда самая большая, затем большие сущности переводятся на INCREMENTAL;
- как грузить — целиком или частями — решать разработчику.

**Сейчас** (`etl/src/run_object.py`, I06–I13-08) весь объект проходит одной транзакцией DWH:
1. Чтение источника одним курсором.
2. Временная текстовая таблица.
3. Проверка типов.
4. Типизированная временная таблица.
5. Проверка ключа.
6. Запись и журнал «было/стало».

**Ограничения этой схемы:**
- **предел R6 — 1 000 000 строк за запуск.** `integration_retail.integration_log` его не проходит;
- все строки сразу лежат во временных таблицах и в одной транзакции DWH;
- журнал «было/стало» для каждой новой строки хранит все её значения. При первой загрузке он равен по объёму самой таблице;
- запись временной таблицы идёт пакетами `INSERT … VALUES`. `COPY` был отключён из-за зависания на Windows-ПК (05.11.2026); сейчас DWH на Linux-сервере;
- предельное время заявки — 3600 с (`DWH_OBJECT_RUN_TIMEOUT_SECONDS`);
- источник держит один снимок данных (транзакцию) всё время чтения.

## 2. Решения (рекомендации)

| № | Вопрос | Рекомендация |
|---|---|---|
| Б1 | Целиком или частями | **Частями.** Порция по умолчанию — 100 000 строк, настройка `DWH_LOAD_CHUNK_ROWS`. Каждая порция проходит проверку типов, проверку ключа и запись и фиксируется отдельной транзакцией DWH. Временные таблицы — только на порцию. |
| Б2 | Как читать источник частями | **По ключу** (keyset): `WHERE key > последний ORDER BY key LIMIT N`. Каждая порция — отдельный короткий запрос, долгого снимка на источнике нет. Это только `SELECT`, шлюз `source_gateway` не меняется. Нужен индекс по ключу в источнике. Если ключ объекта — первичный ключ источника (это видно по снимку структуры), индекс есть. Если нет — одно чтение курсором, но порции в DWH всё равно фиксируются отдельно. |
| Б3 | Предел R6 | **Убрать** для чтения частями. Вместо него — защита по времени и месту: сторож ответа источника остаётся; время заявки — с учётом порций; проверка свободного места в DWH до старта (оценка строк × средний размер). |
| Б4 | Журнал «было/стало» для новых строк | **Только ключ** (`INSERT`, `record_key`, без значений). Значения новой строки и так лежат в таблице, а первое обновление запишет «было». Обновления и удаления — как сейчас, с «было/стало». Сведения не теряются, журнал первой загрузки становится в десятки раз меньше. |
| Б5 | Ошибка в середине загрузки | Уже записанные порции **остаются** — запись идемпотентна (вставка новых ключей, обновление изменившихся). Запуск — `FAILED` с числом записанных строк и номером порции. Повтор «Заново полностью» дочитывает всё: записанные строки окажутся «без изменений». Для INCREMENTAL отметка (watermark) записывается только после успешной последней порции. |
| Б6 | Запись в DWH | **`COPY`** во временную таблицу порции вместо `INSERT … VALUES` — в разы быстрее на Linux. Если `COPY` не сработает, вариант `INSERT` сохраняется настройкой. |

**Шаг ODS** работает так же: порции по ключу из таблицы STG, каждая со своей транзакцией.

**Без изменений:**
- проверки типов и сообщения об ошибках I13-08 — в пределах порции, в ошибке указан номер порции;
- повторы ключа внутри порции проверяются как сейчас. Повтор ключа между порциями при чтении по ключу невозможен — порядок строгий;
- интерфейс заявок и экранов. В «Последний запуск» добавится «порция N из ~M».

## 3. Шаги до `DONE`

| Шаг | Содержание | Режим |
|---|---|---|
| 1 | Утверждение плана, ID I21 | решение пользователя |
| 2 | Пакет 022 — только если для Б5 нужны новые поля запуска (`chunks_done`, `last_key`). Иначе пакета нет. Решаем на шаге 3 по коду функций 010/011 | песочница, E0/E1/E2 с разрешения |
| 3 | Движок: порции по ключу (STG и ODS), `COPY`, журнал Б4, время заявки, прогресс в журнале; тесты | песочница |
| 4 | Нагрузочная проверка в песочнице: источник 3–5 млн строк, 100+ полей, FULL; повтор; INCREMENTAL после FULL; ошибка в середине и повтор | песочница |
| 5 | Выпуск; на сервере — `integration_log` (> 1 млн) FULL, затем INCREMENTAL; регрессия CRM и `OPERATION_COLLECTOR`; реестр | сервер |
| 6 | Подтверждение пользователя — I21 `DONE` | решение пользователя |

**Место в плане:** I21 вставляется в шаг 5 I18. Остальные объекты CRM уже загружаются нынешним движком, витрину CRM можно строить параллельно. `integration_log` — после I21.

## 4. Ограничения

- Чтение по ключу — только для объектов, где ключ — первичный ключ источника или для ключа есть индекс. Иначе одно чтение курсором (Б2).
- Запись в DWH одной транзакцией на всю таблицу больше не гарантируется. Во время загрузки часть порций уже видна в STG/ODS. Витрина обновляется после успешного шага ODS, как сейчас.
- Объём диска сервера: `/var/lib/postgresql` — 500 ГБ. Таблицы core нужно оценить отдельно, вместе с хранением истории.
