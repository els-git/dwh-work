**Статус итерации:** I16 `IN_PROGRESS` с 12.11.2026 (I16-01…I16-06); шаг 1 выполнен утверждением. Порядок: после I08 (`DONE` 12.11.2026), до I09.

**Требования пользователя:**
- 11.11.2026: сервер без интернета (GitHub в том числе); обновление офлайн-пакетом с ПК со сверкой SHA256; диски — по ожидаемым объёмам.
- 12.11.2026:
  - сервер локальный и закрыт извне;
  - нужен способ доставлять обновления;
  - в будущем на сервере — небольшая LLM, которая генерирует SQL для отчётности.

## 1. Что получится в итоге

- DWH работает на сервере Linux (Debian или Ubuntu, С1а) круглосуточно: веб-интерфейс, API, диспетчер, ETL, PostgreSQL 17 `dwh`, ключи SecretStore. Рабочий ПК для работы DWH больше не нужен.
- Пользователи открывают `https://<имя сервера>` в браузере внутренней сети.
- Сервер ходит только к источникам и только на чтение (шлюз I13-07). В интернет не ходит.
- **Обновления:**
  1. на ПК одна команда собирает пакет выпуска — архив + SHA256;
  2. архив копируется на сервер по внутренней сети (SFTP) в папку приёма;
  3. на сервере одна команда сверяет пакет, делает копию базы, ставит обновление и проверяет работу; при ошибке возвращает прежнюю версию.
- Службы поднимаются сами после перезагрузки. База копируется каждую ночь, копия проверяемо восстанавливается.
- LLM — отдельная будущая итерация (раздел 7). Сервер подготовлен так, чтобы её можно было добавить.

## 2. Сервер — итоговые параметры

| Параметр | Значение | Комментарий |
|---|---|---|
| Процессор | 16 ядер x86-64 | С запасом: DWH использует 2–4 ядра, остальное — под будущую LLM на процессоре |
| Память | 32 ГБ | Достаточно для DWH (PostgreSQL ~8 ГБ, приложения ~3 ГБ, ОС ~1 ГБ). Для будущей LLM без видеокарты помещается модель ~7 млрд параметров (раздел 7). Если позже понадобится модель 14 млрд — расширить до 64 ГБ |
| Видеокарта | нет | Можно добавить позже, если сервер физический и есть слот PCIe; для LLM это ускорение в 5–10 раз |
| Диск 1 — система | SSD 200 ГБ | `/` — ОС, программы, код DWH, журналы |
| Диск 2 — база | SSD/NVMe 500 ГБ | `/var/lib/postgresql` — только данные PostgreSQL. **Не HDD:** PostgreSQL на HDD заметно медленнее |
| Диск 3 — копии | HDD 1–2 ТБ | `/backup` — ночные копии базы, архив пакетов выпуска. Здесь HDD подходит |
| Диск 4 — модели LLM | — | позже, SSD 100–200 ГБ, когда начнётся итерация LLM |

Размер диска базы уточняется в шаге 1 по ожидаемым объёмам: число источников и объектов, срок хранения истории. Для оценки: CRM `app_retail.application` — 44 301 строка, `dwh` сейчас 23 МБ.

## 4. Полный чек-лист для администраторов (шаг 4)

### 4.1 Машина и ОС
- [ ] Сервер или ВМ: 16 ядер, 32 ГБ памяти, диски по разделу 2. Сообщить: физический или виртуальный, есть ли TPM 2.0 (или vTPM), есть ли слот под видеокарту.
- [ ] Debian 13 (решение С1а), минимальная установка, без графической оболочки, актуальные обновления безопасности из внутреннего зеркала.
- [ ] Имя хоста (например `dwh-srv`), постоянный IP, DNS-имя для пользователей.
- [ ] Часовой пояс `Asia/Baku`; синхронизация времени (`chrony`) с внутренним сервером времени.
- [ ] Локаль `en_US.UTF-8`, дополнительно `ru_RU.UTF-8`.

### 4.2 Диски
- [ ] Диск 2 смонтирован в `/var/lib/postgresql` (ext4 или xfs, `noatime`).
- [ ] Диск 3 смонтирован в `/backup`.
- [ ] Монтирование прописано в `/etc/fstab` по UUID; переживает перезагрузку.

### 4.3 Пользователи и доступ
- [ ] Системный пользователь и группа `dwh` (`/usr/sbin/nologin`), домашний каталог `/opt/dwh`.
- [ ] Учётные записи администраторов: вход по SSH-ключу, вход по паролю и вход `root` по SSH выключены.
- [ ] Папка приёма пакетов `/srv/dwh/incoming`: запись — только администраторам DWH, чтение — `dwh`.
- [ ] Папки `/opt/dwh` (код), `/etc/dwh` (настройки, права `0750 root:dwh`), `/var/lib/dwh` (зашифрованные учётные данные источников, ключи), `/var/log/dwh`.

### 4.4 Программы (из внутреннего зеркала apt или набором .deb)
- [ ] `postgresql-17`, `postgresql-client-17` (репозиторий PGDG `apt.postgresql.org`).
- [ ] `python3`, `python3-venv` (Python 3.13 из Debian 13).
- [ ] `nginx`.
- [ ] `git`, `unzip`, `ca-certificates`, `openssh-server`, `chrony`, `ufw`.
- [ ] `tpm2-tools` — если есть TPM.

Node.js, компиляторы и доступ в интернет **не нужны**. Python-пакеты DWH приходят в пакете выпуска.

### 4.5 Сеть и межсетевой экран
- [ ] Входящие: 443/tcp — из сети пользователей; 22/tcp — из сети администраторов. Остальное закрыто.
- [ ] Исходящие:
  - `10.30.58.64:5432` (CRM);
  - `10.1.42.6:54320` (`OPERATION_COLLECTOR`, `dev-db.vtbdc.tech`);
  - DNS, NTP;
  - будущие источники — по заявке.

  Интернет закрыт.
- [ ] PostgreSQL слушает только `localhost` (`listen_addresses = 'localhost'`), снаружи недоступен.

### 4.6 Сертификат
- [ ] Сертификат внутреннего удостоверяющего центра на DNS-имя сервера: файл сертификата с цепочкой и закрытый ключ. Кладутся в `/etc/dwh/tls/`, права `0640 root:www-data`.
- [ ] Корневой сертификат УЦ установлен на ПК пользователей (обычно уже есть в домене).

### 4.7 PostgreSQL (начальные настройки под 32 ГБ)
- [ ] Кластер `17/main`, кодировка `UTF8`.
- [ ] `shared_buffers = 8GB`, `effective_cache_size = 20GB`, `work_mem = 32MB`, `maintenance_work_mem = 1GB`, `max_connections = 100`.
- [ ] `password_encryption = scram-sha-256`, `timezone = 'Asia/Baku'`.
- [ ] Базу `dwh` и роли **не создавать**: они приходят из копии в шаге 7.

## 5. Как доставляются обновления

1. **На ПК:** `tools\make_release.ps1 -Version <N>`. Собирает:
   - `git bundle` с кодом (коммит `main`, его SHA);
   - собранный frontend `dist` (Node.js только на ПК);
   - Python-пакеты под Linux — `pip download --platform manylinux2014_x86_64 --python-version <версия Python сервера> --only-binary=:all:`, только если изменились;
   - SQL-пакеты выпуска;
   - `manifest.json` с SHA256 каждого файла.

   Результат — `dwh_release_<N>.zip` и `dwh_release_<N>.sha256`.
2. **Перенос:** SFTP (WinSCP или `scp`) с ПК в `/srv/dwh/incoming`.
3. **На сервере:** `sudo /opt/dwh/current/tools/dwh-update /srv/dwh/incoming/dwh_release_<N>.zip`. По шагам:
   1. сверяет SHA256 архива и каждого файла;
   2. делает копию базы в `/backup`;
   3. разворачивает выпуск в `/opt/dwh/releases/<N>` и окружение Python из пакетов;
   4. останавливает службы и переключает ссылку `/opt/dwh/current`;
   5. запускает службы и делает короткую проверку: `/api/health`, вход, подключение к базе;
   6. **при ошибке** возвращает ссылку на прежний выпуск и запускает его.

   Прежние выпуски хранятся (3 последних).
4. **SQL-пакеты (E2)** ставятся отдельной командой с подтверждением `APPLY`, как сейчас на ПК. Новые проверки E1/E2 пишутся на Python, чтобы одна и та же проверка работала на ПК и на сервере.

## 7. Будущая LLM для SQL — что учтено (без установки в I16)

Отдельная итерация; ID — только с согласия пользователя.
- **На 32 ГБ без видеокарты:** модель ~7 млрд параметров (например, Qwen2.5-Coder-7B) в сжатом виде занимает ~5 ГБ памяти. На 16 ядрах она пишет примерно 8–12 токенов в секунду: SQL-запрос — 15–30 секунд. Для пробы и небольшого числа пользователей хватает.
- **Модель на 14 млрд** (точнее на сложных запросах) — нужно 64 ГБ памяти, либо видеокарта с 16–24 ГБ.
- **Программа:** llama.cpp (сервер с OpenAI-совместимым API) — один исполняемый файл, ставится офлайн пакетом выпуска.
- **Безопасность:**
  - модель видит только описание витрин отчётности, не данные;
  - SQL выполняется только через отдельную роль «только чтение» с фильтром «только SELECT», пределом времени и числа строк;
  - пользователь видит SQL до запуска;
  - всё пишется в журнал;
  - служба LLM слушает только `localhost`.
- **Что нужно от I16:** запас процессора и памяти (есть), место под диск моделей (раздел 2), возможность добавить видеокарту.

## 8. Ограничения и риски

- **Доступ к источникам с сервера** — по правилам сети. Если закрыт, шаг 5 ждёт администраторов.
- **Локали Windows и Linux разные.** При переносе базы сравнение строк может дать другой порядок сортировки. Индексы перестраиваются; отчёты, где важен порядок, проверяются в шаге 10.
- **`systemd-creds` без TPM** защищает ключ ключом самого сервера: копия диска без сервера ключ не раскрывает, но `root` на сервере может его прочитать. Это сопоставимо с DPAPI на Windows.
- **Повторная приёмка SecretStore** — только хранения ключа (шаг 8). Шифрование, журнал и функции БД не меняются.
- **Команды для сервера** — bash через SSH: их выполняют пользователь или администраторы. Для ПК команды остаются PowerShell.
