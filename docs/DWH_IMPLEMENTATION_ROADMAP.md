# DWH — согласованный план реализации и журнал итераций

**Версия плана:** 1.0.0 · **Дата базового среза:** 19.10.2026 · **Статус:** план подготовлен по согласованиям 15–16.10.2026; **I01 завершена 19.10.2026; аудит архитектуры I02 начат; реализация нового функционала I02-I14 не начиналась**.

**Связанный реестр фактического функционала:** `docs/DWH_CURRENT_FUNCTIONALITY.md` (первичная версия 1.0.0). Оба файла размещены в `docs`, проверены по SHA256 и приняты пользователем 19.10.2026.

## 0. Обязательные правила ведения плана

- План — **не одноразовый чеклист**. После начала каждой согласованной итерации меняем `PLANNED → IN_PROGRESS`; при блокировке — `BLOCKED` с причиной; при проверенном завершении — `DONE`, фиксируя доказательства. Если решение изменилось, ставим `CANCELLED` или `DEFERRED` и записываем причину/дату; **строки и идентификаторы задач не удаляем**.
- Статус `DONE` допустим **только** после фактической проверки и подтверждения результата пользователем. Выполнение кода и административные действия на его компьютере не утверждать без вывода диагностик.
- Одновременно с переходом в `DONE` обновлять `DWH_CURRENT_FUNCTIONALITY.md`: что сделано, где реализовано, как проверено, какие ограничения; повышать версию и добавлять **короткую** запись в историю функционального документа.
- Не переносить формулировки «планируем реализовать» в реестр текущего функционала как факт.
- Переход между чатами: сначала читать оба документа, потом подтверждать актуальную конфигурацию/код; если версии не совпали с реальными файлами — `STOP`, отдельная диагностика.
- Строго **один согласованный шаг за ответ**; использовать метки `ДЕЙСТВИЕ: выполни целиком` или `ДЕЙСТВИЕ: ничего пока не запускай`; Windows 11 / PowerShell 5.1.
- Перед изменением источников — точечный аудит ожидаемого фрагмента, резервная копия каждого файла, SHA256, минимальный diff, UTF-8/переносы, возможность отката, проверки. Для frontend production-сборка TypeScript/Vite и полный ESLint **0 ошибок / 0 предупреждений**. При провале откат с SHA256. Не отключать lint-правила.
- Без отдельного согласования **не менять** backend, API, PostgreSQL, данные, ETL, DQ и бизнес-логику. Для БД диагностика только через штатные `get_api_config()/connect_readonly()`, после `SHOW transaction_read_only=on`, без вывода секретов.
- Обнаруженные сторонние проблемы: фиксировать и устранять отдельным шагом после завершения текущего (при критическом риске остановиться немедленно).
- Регламент предусматривает аудит миграций и актуальных контрактов **до** предложения новой DDL-модели. Не исполнять миграции, тестовые загрузки, DDL/DML без явного согласования.

**Словарь статусов:** `PLANNED` — согласовано, не начато; `IN_PROGRESS` — фактически начато; `BLOCKED` — работа остановлена конкретным препятствием; `DONE` — реализовано, прошло требуемые проверки и принято; `CANCELLED` — отменено с причиной; `DEFERRED` — отложено, остаётся в реестре.

## 1. Согласованные продуктовые решения (не изменять молча)

### 1.1. Три типа источников

1. **БД:** PostgreSQL и Oracle являются первоочередными; тип коннектора расширяем для других СУБД без переделки ядра. Через UI настраивается профиль, проверяется доступ, выбирается таблица/представление, извлекается структура. Принудительно совпадающие типы не требовать: сопоставление по **совместимости**; автоматическое безопасное соответствие и явное разрешение конвертаций.
2. **API:** настройка URL/endpoint/метода, headers/query/body, обязательных параметров, авторизации, тайм-аутов, повторов, лимитов и пагинации, пути к массиву записей; **импорт и экспорт cURL-конфигурации обязателен**. Не исполнять shell-команды из cURL. Поддерживать получение структуры из ответов и ручное добавление полей/типов; одним тестовым ответом не ограничиваться.
3. **Папки:** серверные/сетевые каталоги, доступные DWH, **только чтение JSON/XML**, без экспорта DWH в эти форматы. Дата и время берутся из имени, например `asan_pension_requests_2026-10-15_143025.json` (`YYYY-MM-DD_HHMMSS`), а не из метаданных создания файла. Пользователь настраивает шаблон/путь к записям; структуру можно дополнять вручную.

### 1.2. Универсальный цикл

**Исходная система → Профиль подключения → Объект интеграции → Обнаружение полей → Выбор уникального ключа → Маппинг → Проверка конфигурации → READY.**

- **Одна система → несколько профилей → несколько объектов**; каждый объект имеет ровно один явно выбранный профиль на заданный момент. Один профиль может обслуживать несколько объектов.
- Параметры соединения разделить с каталогом логических систем. Безопасное хранение секретов — серверный механизм без возврата паролей в UI, логирование без секретов. Изменение профиля требует повторной проверки структуры.
- **Создание/сохранение не активирует запуск**. Состояния конфигурации и выполнения не смешивать; `DRAFT`, `READY` и `DISABLED`/аналоги согласовать с действующими кодами после аудита API/БД.
- Управление **настройкой** остаётся в Administration → Integrations; **расписание, ручные запуски, история и повторный запуск** должны находиться в отдельном меню. Администратор запускает объект вручную либо задаёт расписание. Ручной запуск не включает расписание.
- Формы коннекторов разные, но полевая модель, проверка, редактор маппинга и исполнение — общие.

### 1.3. Ключи, данные и стратегия

- Уникальный ключ, простой или составной, задаётся **один раз для логического объекта**, а не на каждый файл, ответ API или физический batch. Ключ закрепляется за версией конфигурации и используется всеми будущими загрузками объекта.
- Бизнес-ключ отдельно от внутреннего технического ID DWH; при конфликтах/NULL — ошибка, а не автоматическое «исправление». Изменение ключа требует отдельного согласования и проверки влияния на историю.
- Стратегии объекта: **FULL** и **INCREMENTAL UPSERT**. При полном снимке допускается выбор самого нового файла и безопасное обновление цели только после полной успешной проверки снимка.
- При incremental обрабатываются **все** необработанные файлы в порядке timestamp, данные выбираются по настраиваемым колонкам создания/изменения (`created_at`, `updated_at` либо аналоги); повторные файлы не должны применяться дважды.
- Выгрузки incremental включают новые и изменённые строки. Даты, границы интервалов и запоздавшие данные требуют корректного правила overlap/водяного знака без пропуска событий. Не перетирать более новую версию старой.
- Удаления — **только по явному признаку/событию**; отсутствие строки в incremental не означает удаление.
- Смена структуры относительно утверждённого контракта **останавливает процесс**, пишет ошибку, требует администраторского решения. Нельзя самостоятельно применять несовместимые изменения.
- Маппинг целевых полей: список существующих по совместимому типу плюс возможность заявить новое поле. Физическое изменение ODS/STG только по отдельному проверенному плану с подтверждением, без автоматического произвольного `ALTER TABLE`.
- Чётко разделены техническая приёмка в STG и преобразование в ODS. Не менять технические коды ради локализации.

### 1.4. Ошибки и повторные запуски

- Ошибка подключения/структуры/загрузки **останавливает обработку**, формируется подробный журнал, незавершённый объект не должен оставлять частично применённые целевые данные.
- Единица восстановления — **логический объект**, не последняя строка. «Продолжить» значит заново выполнить первый неуспешный объект, не затрагивая уже подтверждённые успешные объекты; «Запустить заново» — пройти весь выбранный объём с начала.
- Существующий `CRM_RETAIL` ODS `FULL/CONTINUE` сохранять и использовать как проверяемый образец, **не переносить без аудита** в новые коннекторы.
- История и контрольные точки обязательны для проверяемой повторяемости. Ошибки не должны раскрывать пароли, токены, DSN и несанкционированные бизнес-данные.

### 1.5. Группы

- Для **первой версии групповые загрузки исключены**, и это осознанное решение от 16.10.2026. Весь согласованный функционал v1 — **на уровне отдельного объекта**.
- В дальнейшем допускаются группы объектов из разных систем/типов источников, общий порядок, отдельное расписание и возобновление с неуспешного объекта.
- Архитектура исполнения должна допускать будущую группировку, **но без редактора групп и графа зависимостей в v1**.

## 4. Не включать в v1 без отдельного согласования

- Универсальные генераторы Dataset, Dashboard, Scheme и Report Definition; углубление локализации оставшихся строк; редизайн ролей; автоматическая миграция произвольных физических таблиц без approval.
- Непрошенные изменения существующего CRM-пайплайна, создание групп, новый язык визуализации SQL или произвольный пользовательский код.
- Экспорт DWH в XML/JSON: согласован **только импорт** файлов из папки.

Эти направления не объявляются отменёнными навсегда: если появится отдельное согласование, добавлять новые итерации с новыми постоянными ID, не переписывая историю уже согласованных задач.

## 5. Процедура исполнения одной итерации

1. Подтвердить исходное состояние, точные контракты, разрешение пользователя на конкретный шаг; при недостатке данных — отдельная read-only диагностика.
2. Для изменяемых файлов сделать SHA256-подтверждённые копии, проверить анкер точечного изменения; при расхождении `STOP` до мутации.
3. Выполнить только согласованную операцию, затем diff и запланированные технические проверки. БД/ETL запускать только с разрешения и согласованным объёмом.
4. Если проверка не проходит — откатить все затронутые артефакты, сверить SHA256, зафиксировать причину, не ставить `DONE`.
5. Если всё проверено — получить подтверждение пользователя, отметить задачу `DONE`, зафиксировать даты/артефакты, обновить документ 1 и его историю/версию.
6. Если в ходе работы обнаружена иная проблема — записать её как отдельную задачу; при критическом риске остановить работы.

## 7. Согласованные проектные требования I02-02 (20.10.2026)

**Статус:** утверждено пользователем, проектирование IN_PROGRESS. Это требования, а не реализованный функционал.

1. Иерархия обязательна: система -> техническая группа -> объект. Группы могут иметь тип БД, API или файлы. Групповой запуск отложен до I15.
2. Для группы БД выбирается СУБД и задается общее подключение для ее таблиц. Архитектура расширяется адаптерами; PostgreSQL и Oracle являются первыми запланированными реализациями, а не ограничением списка СУБД.
3. Для файловой группы задается каталог и доступ. Каждый объект определяет файл или маску, формат и правила обработки.
4. Для API-группы общие настройки необязательны. Каждый API-объект может определять и переопределять URL, метод, авторизацию, headers, параметры, body и пагинацию.
5. Один API-ответ может содержать несколько связанных сущностей. Пользователь определяет маппинг на несколько целевых таблиц, включая вложенные массивы; связи и атомарность применения обязательны.
6. Краткие сведения о связанных сущностях не перезаписывают полноценные данные автоматически. Обновляемые поля выбираются явно; отсутствие поля в ответе само по себе не означает очистку значения.
7. Настройки версионируются. Действующая проверенная версия продолжает работать при подготовке DRAFT; новая версия публикуется только после проверки. Запуск использует зафиксированную версию.
8. Для каждой целевой таблицы определяется простой или составной ключ. По ключу выполняется идентификация, затем сравнение разрешенных полей. Новая запись добавляется; изменяются только отличающиеся поля; идентичные записи пропускаются. Ошибочные и дублирующиеся ключи требуют остановки без частичного применения.
9. История значений обязательна. Сохраняются предыдущие версии, происхождение данных и время обнаружения изменения. Идентичные повторные загрузки не создают историю заново. Физическое удаление записей запрещено.
10. Для API и БД полученные данные считаются актуальными при отсутствии надежного признака версии в источнике. Конкурирующие загрузки не должны перезаписывать более новый успешный результат более старым.
11. Для файлов дата актуальности берется из содержимого. При новой дате применяются разрешенные изменения с историей. Повторный файл с той же датой и файл с более старой датой могут добавить отсутствующие ключи, но не изменяют существующие записи. Дата источника и обработка журналируются.
12. При успешной полной выгрузке контролируется присутствие записей. Исчезнувшие записи сохраняются, получают предупреждение, дату первого отсутствия, дату последнего присутствия и счетчик пропусков. Возвращение записи фиксируется в истории. Исчезновение не означает закрытие или удаление.
13. Контроль исчезновения включается отдельно для каждой целевой таблицы или набора данных и только при доказанной полноте выгрузки в согласованных границах. Частичные, ошибочные, старые и незавершенные выгрузки, в том числе API с неполной пагинацией, не формируют ложных исчезновений.
14. Сохранение настроек не запускает интеграцию. Ручной запуск и расписание отдельного объекта находятся вне Administration. Существующую CRM-интеграцию сохраняем без регрессий.

Детальные контракты БД, миграций, API и исполнения требуют дальнейшего проектирования и отдельных согласований.

### Публикация схемы  дополнение I02-02 (20.10.2026)

1. Изменения систем, групп и объектов сохраняются в черновике. До успешной публикации они не влияют на действующую интеграцию.
2. Галочка активности определяет включение объекта в следующую публикацию. Установка галочки запускает проверку доступности и настроек, но не публикацию и не загрузку.
3. Публикация выполняется отдельно для каждой системы, охватывая все её группы и отмеченные объекты. Другие системы не затрагиваются.
4. Если выбранный объект не прошёл обязательную проверку, публикация всей системы блокируется. Предыдущая опубликованная версия продолжает работать.
5. Снятие галочки без публикации ничего не отключает. После успешной публикации объект исключается из следующих загрузок; его данные и история сохраняются.
6. Новые запуски используют новую опубликованную версию. Уже начатые запуски завершаются со своей прежней версией настроек.
7. Публикация не запускает ETL и не включает расписание. Ручной запуск и расписания управляются отдельно.

Детальный технический контракт публикации будет уточнён в рамках I02-02 до изменений БД.

### Ручной возврат опубликованной версии  I02-02 (20.10.2026)

1. Администратор может выбрать ранее опубликованную версию схемы конкретной системы.
2. Перед возвратом DWH проверяет доступность подключений, целевых объектов, ключей, маппингов и совместимость прежней конфигурации с текущей структурой.
3. Если проверка неуспешна, возврат блокируется. Действующая версия не изменяется.
4. Успешный возврат атомарно переключает конфигурацию системы для будущих загрузок. Другие системы не затрагиваются.
5. Уже начатые загрузки завершаются с закрепленными за ними версиями настроек.
6. Возврат конфигурации не отменяет завершенные загрузки, не удаляет данные STG/ODS и не стирает историю.
7. Все версии и события публикации или возврата сохраняются в журнале. Возврат не запускает ETL автоматически.

Технический контракт и ограничения возврата уточняются до реализации.

### Владение целевыми полями  I02-02 (20.10.2026)

1. Для каждого физического целевого поля допускается не более одного ответственного источника с правом AUTHORITATIVE: обновлять существующее значение. Правило относится к источникам DATABASE, API и FILE.
2. Остальные источники могут использовать INSERT_ONLY: заполнять разрешенные поля только при создании новой записи. Существующие записи таким источником не обновляются.
3. Режим NO_WRITE запрещает запись значения поля. Использование поля для идентификации и проверки определяется отдельным маппингом.
4. При проектировании публикации необходимо обеспечить выявление конфликтов владения полями между объектами, включая разные системы. Точный механизм проверки и взаимодействие с действующей CRM уточняются до реализации.
5. Отсутствующее поле в данных источника не означает очистку. Действующие данные и история сохраняются согласно ранее утвержденным требованиям.

Решение подтверждено пользователем 20.10.2026. Физические ограничения БД и миграции пока не утверждены.

### Защита истории и конкурентных загрузок — I02-02 (20.10.2026)

1. Бизнес-ключ каждой целевой таблицы может быть простым или составным. Состав и порядок компонентов ключа фиксируются в опубликованной версии конфигурации.
2. При фактическом изменении разрешенного поля сохраняются предыдущее и новое значения, источник изменения, время, идентификатор запуска и версия опубликованной конфигурации. История ранее примененных изменений не удаляется.
3. Повторное получение идентичных значений разрешенных полей не изменяет существующую бизнес-запись и не создает повторную историю.
4. Конкурирующие применения изменений к пересекающимся целевым данным синхронизируются. Устаревший запуск не вправе перезаписать результат более нового успешно примененного запуска. Для DATABASE и API при отсутствии достоверной версии данных источника применяется порядок запусков DWH; этот порядок сам по себе не доказывает фактическую актуальность данных источника.
5. Все связанные целевые таблицы одного API-объекта применяются атомарно в одной транзакции. Ошибка ключа, маппинга, проверки или записи любой связанной сущности отменяет применение всего соответствующего набора.
6. Для FILE актуальность определяется датой внутри файла, а не временем создания или изменения файла в файловой системе. Файл с той же или более ранней датой может добавлять отсутствующие бизнес-ключи, но не обновляет уже существующие записи.
7. Отсутствие ранее загруженной записи определяется только после успешной, полной и подтвержденной выгрузки соответствующего целевого набора данных при явно включенном контроле исчезновения. Частичные, ошибочные, неполные и устаревшие загрузки не являются доказательством исчезновения. Данные сохраняются; отсутствие и повторное появление журналируются с предупреждением.

Все семь правил подтверждены пользователем 20.10.2026. Механизмы транзакционных блокировок, физические ограничения, миграции и реализация пока не утверждены.

### Ограничения целостности ER-модели — I02-02 (21.10.2026)

1. Система, техническая группа и объект образуют обязательную иерархию. Каждая группа принадлежит ровно одной системе, каждый объект — ровно одной группе. Связи с чужими группами или системами запрещены.
2. Конфигурации групп и объектов должны принадлежать одной версии одной системы. При физическом проектировании используются ключи и составные внешние связи, исключающие смешивание настроек разных систем и версий.
3. Целевые таблицы, компоненты простых и составных ключей, маппинги полей и отношения целевых сущностей должны относиться к правильному объекту и версии. Межобъектные и межсистемные ссылки, нарушающие принадлежность, отклоняются.
4. Указатель текущей конфигурации системы может ссылаться только на опубликованную версию этой же системы. Проверка статуса публикации и переключение выполняются атомарно с защитой от конкурентных операций. Запущенные ранее загрузки сохраняют закрепленную за ними версию.

Решение подтверждено пользователем 21.10.2026. Это требования к будущей ER-модели, а не подтверждение реализации. Физические SQL-ограничения, миграции и изменение PostgreSQL отдельно не разрешены.

### Безопасность подключений  I02-03 (22.10.2026)

1. Для DATABASE, API и FILE предусмотрен единый интерфейс SecretStore. Конфигурации содержат secret_ref вместо значений паролей, токенов и ключей.
2. Секреты защищаются шифрованием при хранении. Ключ шифрования защищен отдельно от данных. При невозможности безопасного доступа к ключу операция завершается ошибкой без небезопасного резервного режима.
3. Ответы API, журналы, исключения и диагностические отчеты не раскрывают значения секретов. Запрещено включать секреты в экспорт конфигураций.
4. Создание, замена и использование секретов проверяются через существующую систему аутентификации и разграничения прав DWH. Право просмотра интеграции не означает право получения секрета.
5. Проверка подключения использует разрешенную конфигурацию и не запускает ETL, загрузку или изменение бизнес-данных.
6. Создание, замена, проверка и использование секретов журналируются без записи их значений. Аудит должен учитывать пользователя или служебного исполнителя и результат операции.
7. Для PostgreSQL, Oracle, API и FILE используются отдельные учетные данные и минимально необходимые права. Административные подключения не используются для обычного чтения источников.
8. До реализации проверяются среда запуска backend и ETL, доступность защищенного криптографического провайдера, хранение ключа, ротация секретов и сценарии отказа. runtime/secrets рассматривается только как возможное расположение зашифрованных данных; окончательный механизм еще не утвержден.

Контракт принят в рамках I02-03. Наличие существующих механизмов авторизации не означает, что безопасность новых коннекторов уже реализована. До завершения практических проверок задача остается IN_PROGRESS.

### I02-03  Уточнение механизма хранения секретов (22.10.2026)

1. Учетные записи пользователей DWH не зависят от учетных записей Windows. Доступ к веб-интерфейсу определяется существующей аутентификацией и правами DWH.
2. SecretStore работает на серверной стороне и не связывает пользовательский вход в DWH с учетной записью операционной системы.
3. Для переносимого хранилища рассматривается AES-256-GCM из поддерживаемой библиотеки cryptography. Провайдер и зависимости должны пройти проверку перед реализацией.
4. Мастер-ключ защищается отдельно от зашифрованных секретов. Его запрещено сохранять в коде, PostgreSQL, конфигурациях интеграций, обычных журналах и общих резервных копиях.
5. Без доступного и корректного ключа SecretStore отказывает в операции. Запрещен переход к открытому хранению или выводу секрета.
6. Backend и ETL получают только минимально необходимые служебные права. Пользователь с правом просмотра интеграции не может получить значение секрета.
7. Ротация, восстановление и перенос хранилища должны быть проверены до эксплуатации. Расположение runtime/secrets не считается защищенным без проверки прав файловой системы.
8. Windows DPAPI успешно проверен только для текущего пользователя ОС, но не выбран обязательным механизмом. Реализация, проверка API, аудита и прав доступа пока не выполнены.

### I02-03 - approved security contracts 28.10.2026

**Decision status:** APPROVED BY USER on 28.10.2026.
**Implementation status:** NOT IMPLEMENTED by this approval.
**Scope:** SecretStore security architecture. No new SQL, API, ETL, DQ,
frontend, operational keys or filesystem changes were authorized.

#### S01-S08 - secret binding and lifecycle

- S01: Each secret_ref belongs to exactly one source_system_id.
- S02: Rebinding an existing secret_ref to another source is prohibited.
- S03: PENDING and REVOKED secrets cannot be read by the service.
- S04: Audit events contain no plaintext credentials.
- S05: Audit failure blocks the operation.
- S06: Failed replacement preserves the previous ACTIVE binding.
- S07: Repeated trusted operation IDs must not create uncontrolled duplicates.
- S08: File/SQL crash recovery must not activate a secret automatically.

Approved lifecycle: PENDING -> ACTIVE -> REVOKED.
CREATE and REPLACE require scoped human authorization; plaintext human
READ is prohibited, including for administrators. A durable binding registry
and safe publishing/recovery protocol are still required.

#### A01-A10 - durable audit

- A01: Assign a unique server-generated operation_id.
- A02: Persist ATTEMPT before accessing secret storage.
- A03: Record DENIED attempts.
- A04: Persist ATTEMPT and OUTCOME independently.
- A05: Record source, operation, verified actor, outcome and timestamp.
- A06: Never record plaintext, credentials, DSN or raw secret_ref.
- A07: Audit failure blocks activation or secret use.
- A08: Missing OUTCOME is incomplete, never successful.
- A09: Event retries are idempotent and cannot conflict.
- A10: Retain audit history after secret replacement or revocation.

ATTEMPT: DENIED or PERMITTED_ATTEMPT.
OUTCOME: SUCCEEDED or FAILED.
Each required event must have a verified durable COMMIT.
The existing audit.security_event infrastructure is a candidate, not a
verified final implementation. Grant no broad direct audit write access.

#### K01-K10 - master key

- K01: Generate the key using cryptographically secure randomness.
- K02: Keep the key separate from ciphertext and PostgreSQL backups.
- K03: Prevent arbitrary key export by backend/ETL processes.
- K04: Missing or damaged key causes fail-closed behavior.
- K05: Encrypt and restrict key backups.
- K06: Test recovery in isolation with synthetic secrets.
- K07: Preserve old keys until rotation is fully verified.
- K08: Identify key versions with a non-secret key_id.
- K09: Exclude key material from logs, API, diagnostics and Git.
- K10: Document backup, recovery and rotation before production use.

The current environment-variable provider is isolated code only.
Secure delivery, key management and rotation remain unimplemented.

#### F01-F07 - encrypted file storage

- F01: Keep storage outside publicly served frontend paths.
- F02: Restrict filesystem ACLs to necessary server identities.
- F03: Give DWH human users no direct filesystem access to secrets.
- F04: Reject path escape, symlinks and invalid secret_ref values.
- F05: Create encrypted files without overwriting existing secrets.
- F06: Keep encrypted backups consistent with bindings and key versions.
- F07: ACL/filesystem errors must fail closed with no plaintext fallback.

Actual filesystem ACLs and service identities require environment-specific
verification. A separate trusted secret-resolution boundary is preferred;
ordinary ETL processes must not gain arbitrary key/file access.

#### E01-E12 - trusted ETL service identity

- E01: Service identity is separate from DWH sessions and SUPERADMIN.
- E02: Authenticate the executor through a trusted server mechanism.
- E03: Verify job existence and permitted state in a trusted registry.
- E04: Resolve source, object and configuration version from trusted job data.
- E05: Resolve secret_ref server-side, not from arbitrary worker parameters.
- E06: Limit permissions to the specific job, source and operation.
- E07: Bound permissions by time and job state.
- E08: Reject use outside the authorized scenario, including replay.
- E09: Enforce S01-S08 and A01-A10 on every service READ.
- E10: Cancellation or revocation blocks new READ operations.
- E11: Verification or audit failure causes denial.
- E12: Service authority grants no CREATE/REPLACE/REVOKE capability.

Worker-provided execution IDs, source IDs and secret references are not
proof of authorization. The transport and attestation mechanism remain
open pending verification of the deployed backend/ETL environment.
Revocation blocks new reads; termination of already established external
connections requires a separate technical decision.
