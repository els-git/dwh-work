## 1. Что получится в итоге (простыми словами)

Опубликованный (`READY`) объект нового источника загружается **по своей конфигурации**, без специального кода под источник:

1. оператор запускает объект командой на сервере (первый объект — `OPERATION_COLLECTOR` / `public.asan_pension_requests` → `stg.operation_collector_asan_pension_requests`);
2. движок проверяет, что версия в силе `READY` и структура источника не изменилась (drift → STOP);
3. читает объект источника целиком (учётные данные — из SecretStore с записью `READ`, роль `dwh_etl`);
4. проверяет весь набор до записи: ключ без `NULL` и без дублей, значения приводятся к целевым типам;
5. **одной транзакцией** применяет набор к целевой таблице по правилам полей: новая запись — вставка, изменённые разрешённые поля — обновление (с историей «было/стало»), равные — пропуск; `INSERT_ONLY` не перезаписывает, `NO_WRITE` не пишет, `NULL` очищает значение только при «Explicit NULL»;
6. любая ошибка — откат всей записи объекта, понятный код ошибки в журнале; запуск, его версия и счётчики видны в истории.

Повторный запуск того же набора не создаёт дублей и истории (все записи — «пропуск»).

## 6. Риски

- Объём `public.asan_pension_requests` неизвестен: при превышении предела Р6 запуск остановится до записи.
- Значения источника, не приводимые к целевому типу (например, строка длиннее 16 символов в `pin`), остановят запуск — по правилу «ошибка, а не исправление» (roadmap 1.3).
- Если шаг 2 покажет, что `etl.job_run` нельзя использовать без изменения его структуры, Р4 вернётся на согласование до шага 3.
