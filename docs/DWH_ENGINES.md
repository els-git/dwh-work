# DWH — движки приложения

<sub>Версия **1.3.1** · **20.11.2026** · Описывает устройство движков по коду репозитория `els-git/dwh-work`. Документ обновляется вместе с изменением движков. Что из этого подтверждено на сервере — см. реестр `docs/DWH_CURRENT_FUNCTIONALITY.md`.</sub>

## 0. Общая картина

```
 Источник (PostgreSQL CRM, …)
        │  только чтение, через шлюз источников (§3)
        ▼
 STG  ── движок загрузки, шаг STG (§1)      stg.<схема>_<объект>  — копия источника, типы проверены
        │
        ▼
 ODS  ── движок загрузки, шаг ODS (§1)      ods.<схема>_<объект>  — рабочий вид: преобразования
        │  после успешного ODS — заявки на витрины, читающие таблицу
        ▼
 DM   ── движок витрин (§4)                 dm.<код>              — конструктор или готовый SQL
        │
        ▼
 Отчётность (§7), ИИ-помощник (§6), выгрузки
```

Кто запускает: пользователь из «Загрузок» создаёт **заявку** → **диспетчер** (§2) берёт её и выполняет движок → результат и ошибки пишутся в журнал (`etl.*`) и видны в «Загрузках». Структуру таблиц STG / ODS / DM создаёт и меняет **сама база** при публикации (§5).

Роли базы данных:

| Роль | Кто под ней работает | Что может |
|---|---|---|
| `dwh_app` | API (веб-приложение) | читает служебные представления; меняет данные только через функции `app.*` с проверкой сессии |
| `dwh_etl` | диспетчер и движки | пишет в `stg`, `ods`, `dm` и журналы `etl.*` через функции `etl.*` |
| `dwh_ai_ro` | ИИ-помощник, просмотр витрин | только чтение `dm` |
| `dwh_dm_sql_ro` | витрины по готовому SQL | только чтение `ods` |
| `dwh_admin` | SQL-пакеты (владелец объектов) | DDL; используется только пакетами и функциями публикации |

## 1. Движок загрузки объектов

**Файлы:** `etl/src/run_object.py`, вызов — `etl/src/object_request_worker.py`. **Роль:** `dwh_etl`. **Запуск:** заявки «Запустить», «Заново полностью», «Продолжить (ODS)» в «Загрузки → Объекты».

### 1.1. Шаг STG — из источника в `stg`

1. **Проверки перед чтением:**
   - структура источника не изменилась после публикации маппинга (`SCHEMA_DRIFT`);
   - таблица STG совпадает с опубликованной версией (`TARGET_DRIFT`);
   - на диске сервера есть место — размер таблицы источника × 3 (`DISK_SPACE`).
2. **Пароль источника** берётся из SecretStore (§8); каждое чтение пароля пишется в журнал (`READ`).
3. **Чтение источника** через шлюз (§3) порциями по `DWH_LOAD_CHUNK_ROWS` (100 000) строк:
   - если у ключа есть уникальный индекс — по ключу: `WHERE (ключ) > последний ORDER BY ключ LIMIT N`;
   - иначе (представления) — одним курсором, нарезанным на порции.
4. **Проверка каждой порции до записи:**
   - каждое значение проверяется на соответствие типу поля (`pg_input_is_valid`); строка длиннее `varchar(n)` — ошибка, а не обрезка (`TYPE_CONVERSION`);
   - ключ не пуст (`KEY_NULL`) и не повторяется (`KEY_DUPLICATE`).
5. **Запись порции** через `COPY` во временную таблицу, затем слияние в `stg`:
   - новые ключи вставляются;
   - изменённые поля обновляются по политике поля:
     - `AUTHORITATIVE` — обновлять;
     - `INSERT_ONLY` — только при вставке;
     - `NULL` пишется, только если включено «Explicit NULL»;
   - удалений нет (кроме мягкого удаления по флагу INCREMENTAL).
   - Каждая порция фиксируется отдельно (`COMMIT`).
6. **История «было/стало»** (`etl.object_record_change`): у изменённых строк — значения до и после, у новых — только ключ. Для широких таблиц журнал собирается частями по 50 полей.
7. **Стратегии:**
   - **FULL** — читается вся таблица;
   - **INCREMENTAL** — строки с полем изменения `>= отметка − перекрытие` (минуты); отметка сдвигается только после последней порции.
8. **При сбое** записанные порции остаются. Запуск `FAILED` со счётчиками и номером порции, повторный запуск догружает остальное.

### 1.2. Шаг ODS — из `stg` в `ods`

- Порции по первичному ключу таблицы STG.
- Преобразования из белого списка: `COPY`, `CAST`, `TRIM`, `UPPER`, `LOWER`, `EMPTY_TO_NULL`, `DEFAULT`, `CONSTANT`, `DATE_FROM_TEXT` (по формату, например `DD.MM.YYYY`), технические `LOAD_RUN_ID`, `LOADED_AT`.
- Если преобразование упало на данных — разбор по каждому полю: какое поле, правило, сколько строк, до 5 значений с количеством, до 10 ключей.
- История — `etl.object_ods_record_change`.
- После успешного ODS ставятся заявки на витрины, читающие эту таблицу (`etl.dm_mart_enqueue_after_ods`).

### 1.3. Журнал, ошибки, настройки

- **Журнал:**
  - запуски — `etl.object_run`, `etl.object_ods_run`, `etl.batch_run`, `etl.job_run`;
  - ошибки — `etl.error_log` (код, поле, `bad_value`, `diagnostic_context` в JSON);
  - экран — «Загрузки → Запуски», «Ошибки и история».
- **Коды ошибок:** `TYPE_CONVERSION`, `KEY_NULL`, `KEY_DUPLICATE`, `SCHEMA_DRIFT`, `TARGET_DRIFT`, `DISK_SPACE`, `LOCK_TIMEOUT`, `SOURCE_NO_RESPONSE`, `SOURCE_CONNECT_FAILED`, `SOURCE_NOT_READ_ONLY`, `TIMEOUT`, `DISPATCHER_LOST`, `DATABASE_ERROR` (по `SQLSTATE`).
- **Настройки** (`/etc/dwh/dwh.env`):
  - `DWH_LOAD_CHUNK_ROWS` — размер порции;
  - `DWH_STAGE_COPY` — `0`: прежние `INSERT` вместо `COPY`;
  - `DWH_PG_DATA_DIR` — диск для проверки места;
  - `DWH_SOURCE_REPLY_TIMEOUT_SECONDS` (300) — сколько ждать ответа источника;
  - `DWH_OBJECT_RUN_TIMEOUT_SECONDS` (3600) — предел заявки без признаков хода;
  - `DWH_RUN_OBJECT_STACK_DUMP_SECONDS` — снимок стека зависшего запуска.

## 2. Диспетчер заявок

**Файлы:** `etl/src/run_request_dispatcher.py`, `etl/src/object_request_worker.py`, служба `dwh-dispatcher` (`tools/server/dispatcher_service.py`). **Роль:** `dwh_etl`.

- Очереди:
  - объектов — `etl.object_run_request`: `RUN`, `CONTINUE_ODS`, `FULL_RERUN`; по объекту одна активная заявка;
  - витрин — `etl.dm_mart_run_request`: `MANUAL`, `AFTER_ODS`, `PUBLISH`.
- Захват заявки — функцией `*_claim` под сессионной блокировкой. Если диспетчер перезапустился посреди заявки, база закрывает её `DISPATCHER_LOST`.
- Каждая загрузка объекта — отдельный дочерний процесс `run_object.py`. Время считается от последней строки хода (`STAGE:`); по пределу — `TIMEOUT`.
- Витрины выполняются в процессе диспетчера: они работают только с базой DWH.
- Заявки создаёт API функциями `app.integration_object_run_request_create/_cancel` и `app.dm_mart_run_request_create/_cancel` с проверкой права.

## 3. Шлюз источников

**Файл:** `backend/src/dwh_api/source_gateway.py`. Единственная дорога к базам-источникам — новый код обращается к источникам только через него (тест-«сторож» `backend/tests/test_source_gateway.py` проверяет, что прямых подключений нет).

- До первого запроса включает в сессии источника режим «только чтение» и проверяет его (`SOURCE_NOT_READ_ONLY`).
- Пропускает только `SELECT`, `DECLARE`/`FETCH` и служебные команды чтения; запись — `SOURCE_WRITE_BLOCKED`.
- Защита от зависания:
  - `lock_timeout` (60 с) → `LOCK_TIMEOUT`;
  - TCP keepalive;
  - сторож ответа: отмена запроса, затем разрыв соединения → `SOURCE_NO_RESPONSE`;
  - «подталкивание» драйвера раз в секунду, чтобы принятые данные не застревали.
- Через шлюз работают проверка подключения, список объектов, снимок структуры («Интеграции») и движок загрузки.

## 4. Движок витрин DM

**Файлы:** `etl/src/dm_mart_worker.py`, генератор SQL `backend/src/dwh_api/dm_sql.py`, витрины по SQL `backend/src/dwh_api/sql_mart.py`. **Роль:** `dwh_etl` (чтение `ods`, запись `dm`).

### 4.1. Витрина из конструктора

- **Зерно** — сущность (например, «Клиент») и её ключ; у каждой таблицы ODS своя колонка-ключ (каталог «Сущности и ключи»).
- **Источники:**
  - `GRAIN` — основная таблица, задаёт строки витрины;
  - `SAME_KEY` — дополняет строку (одна строка на ключ);
  - `CHILD` — много строк на ключ, поля только через агрегаты `SUM`, `COUNT`, `COUNT_DISTINCT`, `MIN`, `MAX`, `AVG`;
  - `LOOKUP` — справочник, соединяется с колонкой более ранней таблицы; одна таблица может подключаться несколько раз под разными псевдонимами.
- **Поля** с приоритетом источников: берётся первое непустое значение. **Фильтры** — по каждому источнику.
- **Генератор** сначала сводит каждую таблицу к ключу и только потом соединяет — суммы не умножаются.
- **Проверки до записи:**
  - нет пустого ключа зерна (`DM_KEY_NULL`);
  - ключи `GRAIN` / `SAME_KEY` уникальны (`DM_KEY_NOT_UNIQUE`);
  - колонки `LOOKUP` уникальны (`DM_LOOKUP_NOT_UNIQUE`) — с примерами значений;
  - таблицы и колонки ODS на месте (`DM_SOURCE_MISSING`).

### 4.2. Витрина по готовому SQL-запросу

- Один запрос `SELECT`, `WITH … SELECT` или с `UNION` / `INTERSECT` / `EXCEPT`.
- **Проверка запроса** выполняется под ролью `dwh_dm_sql_ro`, которая читает только `ods` и только на чтение:
  - план `EXPLAIN (VERBOSE)` — читаются только таблицы `ods`;
  - колонки с типами, первые 50 строк;
  - имена колонок допустимы.
- **Движок** читает строки в одном снимке данных (`REPEATABLE READ`):
  - колонки витрины на месте (`DM_SQL_COLUMNS_CHANGED`);
  - ключ не пуст и уникален;
  - запись через `COPY` под `dwh_etl`.

### 4.3. Запись и публикация

- **Обычное обновление:** `DELETE` + `INSERT` (или `COPY`) в одной транзакции — читатели видят прежние строки до фиксации. При ошибке прежние строки остаются.
- **Публикация новой структуры:** база создаёт `dm.<код>__next`, движок заполняет её (заявка `PUBLISH`), функция завершения подменяет таблицы и публикует версию. При ошибке новая таблица удаляется.
- **Когда обновляется:** при публикации, вручную («Загрузки → Витрины») и после ODS таблиц, которые читает витрина (если включено «Обновлять после ODS»).
- **Журнал:** `etl.dm_mart_run`, состояние — `etl.v_dm_mart_status`. **Настройка:** `DWH_DM_STATEMENT_TIMEOUT_SECONDS` (1800).

## 5. Публикация структуры таблиц (DDL из интерфейса)

**Где:** функции базы пакетов 019 и 021 — `app.object_table_preview/_publish` (STG/ODS), `app.mart_builder_preview/_publish/_delete` (DM).

- DDL строит **сама база** по белому списку типов полей; текст DDL от клиента не выполняется.
- «Опубликовать» в «Маппинге» или конструкторе витрин:
  - новые таблицы и поля создаются сразу;
  - удаление поля, смена типа и смена ключа — только после подтверждения, со списком затронутого (ODS, витрины, сохранённые отчёты, примеры помощника);
  - если смена типа испортила бы значения — отказ.
- Удаление витрины: таблица удаляется, витрина помечается `deleted_at`, её код остаётся занят.

## 6. ИИ-помощник

**Файлы:** `backend/src/dwh_api/ai_assistant.py` (`/api/ai/*`), `ai_core.py`, `ai_knowledge.py`, `ai_sql_guard.py`, `ai_llm.py`, `ai_diagnosis.py`. **Модель:** служба `dwh-llm` — llama.cpp, Gemma 4 26B A4B, только `127.0.0.1:8081`, без интернета; одна модель отвечает на один вопрос за раз (очередь, «Стоп» отменяет на сервере).

- **Справка:**
  - поиск разделов `docs/DWH_USER_GUIDE.md`, доступных роли пользователя — каждый раздел помечен нужными правами;
  - вопрос не по-русски переводится для поиска; ответ — на языке вопроса;
  - к вопросу можно приложить снимок экрана — он не сохраняется.
- **Отчёт по описанию:**
  - модель видит только описание витрин белого списка, доступных роли: колонки, справочные значения, термины, примеры; строк данных не видит;
  - SQL проверяет `ai_sql_guard`: один `SELECT`, без запрещённых слов и схем, затем по плану `EXPLAIN` — только разрешённые витрины;
  - выполняет `dwh_ai_ro` только на чтение, с пределом строк;
  - после ошибки PostgreSQL — одна попытка самоисправления.
- **Разбор ошибок загрузок** (кнопка «Разобрать с помощником»):
  - сервер собирает досье фактов: ошибка, история запусков, поле и ключ в «Маппинге», изменения структуры, последняя проверка подключения без учётных данных, определение витрины;
  - добавляет базу знаний причин по 33 кодам;
  - сразу показывается карточка без модели, затем модель пишет «Что случилось / Где / Почему / Что сделать / Как проверить».
- **Память диалога:** последние 10 сообщений хранятся на странице браузера; с отчётом передаётся прежний SQL.
- **Журнал** `app.ai_request_log`: вопрос, SQL, результат, без строк данных и без изображений.
- **Настройки:** `DWH_AI_LLM_URL`, `DWH_AI_MODEL_LABEL`, `DWH_AI_DB_PASSWORD`, `DWH_AI_TIMEOUT_SECONDS`, `DWH_AI_QUEUE_SECONDS`; администрирование — «Администрирование → ИИ-помощник».

## 7. Отчётность и просмотр витрин

**Файлы:** `backend/src/dwh_api/mart_view.py` (`/api/reports/marts`), `saved_reports.py` (`/api/reports/saved/*`).

- **Витрины роли** — по белому списку и праву витрины.
- **Просмотр:**
  - запрос строит сервер: колонки — из каталога, значения фильтров — параметрами;
  - фильтры, сортировка, страницы по 100 строк;
  - читает `dwh_ai_ro`.
- **Выгрузка:**
  - CSV — потоком, до 1 000 000 строк;
  - XLSX — до 1 000 000 строк;
  - PDF — до 5 000 строк, таблицы по 8 колонок;
  - сверх предела — понятный отказ с числом строк и другими форматами.
- **Сохранённые отчёты помощника** — личные и общие папки.
- **Журнал:** каждое открытие и выгрузка — `MART_VIEW`.

## 8. SecretStore (пароли источников)

**Файлы:** `backend/src/dwh_api/secret_*.py`, `etl/src/dwh/source_secret.py`; схема `secret_store`.

- **Хранение:**
  - пароль источника зашифрован (AES-256-GCM) в файле `/var/lib/dwh/secrets`;
  - мастер-ключи на сервере — `systemd-creds` (`/etc/dwh/keyring`), действующий ключ — `DWH_SECRET_ACTIVE_KEY_ID`.
- **Журнал операций** (`secret_store`): `CREATE`, `REPLACE`, `REVOKE`, `READ` — с актором и `key_id`.
- **Чтение пароля** движком — функциями `etl.source_secret_read_begin/_finish` (актор `SERVICE`).
- **Через API и интерфейс** пароль не выдаётся никогда; задать или заменить его может администратор в «Интеграции → источник → Подключение».

## 8a. Вход пользователей (локальный и через домен, I20)

**Файлы:** `backend/src/dwh_api/auth.py` (`POST /api/auth/login`), `backend/src/dwh_api/directory_login.py`; функции базы `app.auth_*` (вход, сессия, журнал), `app.auth_get_directory_user`, `app.auth_bind_external_subject` (пакет 024); настройка — `tools/server/dwh_ldap_setup.py`.

- **Локальный вход** (`LOCAL`): пароль сверяется с хешем `app.user_account`; без изменений.
- **Вход через домен** (`LDAP` / `AD`, если `DWH_LDAP_ENABLED=true`) — только когда локального пользователя с таким именем нет:
  1. имя `user`, `VTBAZE\user` или `user@vtbaze.local` приводится к `user`; пользователь должен быть заведён в DWH с входом через домен и быть активным;
  2. соединение с контроллером: StartTLS на обычном порту (LDAPS на 636 / 3269); сертификат сверяется с отпечатками `DWH_LDAP_PINS` (или с УЦ `DWH_LDAP_CA_FILE`) **до** отправки любого пароля; порт без StartTLS отклоняется;
  3. служебная учётная запись (пароль — systemd-кредитив `dwh-ldap-bind`, только у `dwh-api`) ищет `sAMAccountName` в папках `DWH_LDAP_BASE_DNS`; значения запроса передаются в BER, а не строкой фильтра — подстановка фильтра невозможна;
  4. отключённая учётная запись (`userAccountControl`) — отказ без проверки пароля; иначе пароль проверяется входом от имени найденного DN; коды AD `data 52e/533/775/532/773/701` → причины `INVALID_CREDENTIALS`, `LDAP_ACCOUNT_DISABLED`, `LDAP_ACCOUNT_LOCKED`, `LDAP_PASSWORD_EXPIRED`, `LDAP_ACCOUNT_EXPIRED`;
  5. `objectGUID` записывается при первом входе и дальше сверяется (`LDAP_GUID_MISMATCH` при другом);
  6. сессия создаётся той же функцией, что для локального входа.
- **Отказоустойчивость:** контроллеры по порядку `DWH_LDAP_SERVERS`, следующий — только если предыдущий недоступен по сети; при недоступности всех — ответ 503 «Domain login service is unavailable» (`LDAP_UNAVAILABLE`), локальный вход работает.
- **Журнал:** неудачи — `LOGIN_FAILED` с причиной; привязка — `DIRECTORY_SUBJECT_BOUND`, расхождение GUID — `LDAP_GUID_MISMATCH`; пароли и GUID в журнал не пишутся. Пользователю всегда общий текст «Invalid username or password».
- **Пустой пароль** не отправляется никогда (в AD он означал бы анонимный вход).
- **Смена способа входа** (пакет 025, `POST /api/admin/users/{id}/auth-provider`, функция `app.user_catalog_set_auth_provider`): правила — как у сброса пароля (сессия администратора и `ADMIN_USER_MANAGE`, `can_manage_user`, не системные и не `SUPERADMIN`). `LOCAL` → `LDAP`: пароль стирается, привязка GUID — при следующем входе; `LDAP`/`AD` → `LOCAL`: временный пароль (политика и хеш — в API), смена при входе; GUID снимается, сессии пользователя завершаются, событие `AUTH_PROVIDER_CHANGED`.

| Выпуск | `tools/make_release.ps1` (ПК) → `tools/server/dwh_update.py` | архив с SHA256 и колёсами Python; копия базы перед обновлением; проверка служб; откат `--rollback-to` |
| SQL-пакеты | `tools/server/dwh_sql_package.py --package N --stage e1 / e2` | SHA256 файлов по `sql_packages.json`; E1 — на копии базы (проверка, тест, откат, повтор), E2 — на `dwh` с копией `pre-N` и подтверждением `APPLY` |
| Копии базы | `tools/server/dwh_backup.py`, таймер systemd | ежедневная копия в `/backup/dwh`, проверочное восстановление |
| Службы | systemd: `dwh-api`, `dwh-dispatcher`, `dwh-llm`, nginx (HTTPS) | переживают перезагрузку |
| Настройка ролей | `dwh_ai_setup.py` (`dwh_ai_ro`, модель), `dwh_dm_sql_setup.py` (`dwh_dm_sql_ro`) | пароли случайные, только в `/etc/dwh/dwh.env`, на экран не выводятся |
| Диагностика | `tools/server/dwh_readonly_sql.py <файл.sql>` | `dwh_app`, только чтение, отчёт рядом с файлом |
| Проверка домена (I20) | `tools/server/dwh_ldap_check.py` | DNS, порт, LDAPS / StartTLS, сертификат и отпечаток, вход интеграционной учётной записью |
| Сертификат HTTPS (I13-10) | `tools/server/dwh_tls.py install / check / rollback` | PFX от УЦ: проверка ключа, имени, срока и цепочки до замены, копия прежних файлов, файл nginx из шаблона (перенаправление адреса на DNS-имя), `nginx -t`, живая проверка, возврат при ошибке |
| Вход через домен (I20) | `tools/server/dwh_ldap_setup.py` | параметры в `dwh.env`, пароль служебной учётной записи в `systemd-creds`, drop-in для `dwh-api`, проверка контроллеров, включение после `PASS`, `--disable` |
