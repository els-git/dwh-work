# DWH — движки приложения

<sub>Версия **1.23.0** · **27.11.2026** · Описывает устройство движков по коду репозитория `els-git/dwh-work`. Документ обновляется вместе с изменением движков. Что из этого подтверждено на сервере — см. реестр `docs/DWH_CURRENT_FUNCTIONALITY.md`.</sub>

## 0. Общая картина

```
 Источник (PostgreSQL CRM, …)
        │  только чтение, через шлюз источников (§3)
        ▼
 STG  ── движок загрузки, шаг STG (§1)      stg.<схема>_<объект>  — копия источника, типы проверены
        │
        ▼
 ODS  ── движок загрузки, шаг ODS (§1)      ods.<схема>_<объект>  — рабочий вид: преобразования
        │  после успешного ODS — заявки на витрины, читающие таблицу
        ▼
 DM   ── движок витрин (§4)                 dm.<код>              — конструктор или готовый SQL
        │
        ▼
 Отчётность (§7), ИИ-помощник (§6), выгрузки
```

Кто запускает: пользователь из «Загрузок» создаёт **заявку** → **диспетчер** (§2) берёт её и выполняет движок → результат и ошибки пишутся в журнал (`etl.*`) и видны в «Загрузках». Структуру таблиц STG / ODS / DM создаёт и меняет **сама база** при публикации (§5).

Роли базы данных:

| Роль | Кто под ней работает | Что может |
|---|---|---|
| `dwh_app` | API (веб-приложение) | читает служебные представления; меняет данные только через функции `app.*` с проверкой сессии |
| `dwh_etl` | диспетчер и движки | пишет в `stg`, `ods`, `dm` и журналы `etl.*` через функции `etl.*` |
| `dwh_ai_ro` | ИИ-помощник, просмотр витрин | только чтение `dm` |
| `dwh_dm_sql_ro` | витрины по готовому SQL | только чтение `ods` |
| `dwh_admin` | SQL-пакеты (владелец объектов) | DDL; используется только пакетами и функциями публикации |

## 1. Движок загрузки объектов

**Файлы:** `etl/src/run_object.py`, вызов — `etl/src/object_request_worker.py`. **Роль:** `dwh_etl`. **Запуск:** заявки «Запустить», «Заново полностью», «Продолжить (ODS)» в «Загрузки → Объекты».

### 1.1. Шаг STG — из источника в `stg`

1. **Проверки перед чтением:**
   - структура источника не изменилась после публикации маппинга (`SCHEMA_DRIFT`);
   - таблица STG совпадает с опубликованной версией (`TARGET_DRIFT`);
   - на диске сервера есть место — размер таблицы источника × 3 (`DISK_SPACE`).
2. **Пароль источника** берётся из SecretStore (§8); каждое чтение пароля пишется в журнал (`READ`).
3. **Чтение источника** через шлюз (§3) порциями по `DWH_LOAD_CHUNK_ROWS` (100 000) строк:
   - если у ключа есть уникальный индекс — по ключу: `WHERE (ключ) > последний ORDER BY ключ LIMIT N`;
   - иначе (представления) — одним курсором, нарезанным на порции.
4. **Проверка каждой порции до записи:**
   - каждое значение проверяется на соответствие типу поля (`pg_input_is_valid`); строка длиннее `varchar(n)` — ошибка, а не обрезка (`TYPE_CONVERSION`);
   - ключ не пуст (`KEY_NULL`) и не повторяется (`KEY_DUPLICATE`).
5. **Запись порции** через `COPY` во временную таблицу, затем слияние в `stg`:
   - новые ключи вставляются;
   - изменённые поля обновляются по политике поля:
     - `AUTHORITATIVE` — обновлять;
     - `INSERT_ONLY` — только при вставке;
     - `NULL` пишется, только если включено «Explicit NULL»;
   - удалений нет (кроме мягкого удаления по флагу INCREMENTAL).
   - Каждая порция фиксируется отдельно (`COMMIT`).
6. **История «было/стало»** (`etl.object_record_change`): у изменённых строк — значения до и после, у новых — только ключ. Для широких таблиц журнал собирается частями по 50 полей.
7. **Стратегии:**
   - **FULL** — читается вся таблица;
   - **INCREMENTAL** — строки с полем изменения `>= отметка − перекрытие` (минуты); отметка сдвигается только после последней порции.
8. **При сбое** записанные порции остаются. Запуск `FAILED` со счётчиками и номером порции, повторный запуск догружает остальное.

### 1.2. Шаг ODS — из `stg` в `ods`

- Порции по первичному ключу таблицы STG.
- Преобразования из белого списка: `COPY`, `CAST`, `TRIM`, `UPPER`, `LOWER`, `EMPTY_TO_NULL`, `DEFAULT`, `CONSTANT`, `DATE_FROM_TEXT` (по формату, например `DD.MM.YYYY`), технические `LOAD_RUN_ID`, `LOADED_AT`.
- Если преобразование упало на данных — разбор по каждому полю: какое поле, правило, сколько строк, до 5 значений с количеством, до 10 ключей.
- История — `etl.object_ods_record_change`.
- После успешного ODS ставятся заявки на витрины, читающие эту таблицу (`etl.dm_mart_enqueue_after_ods`).

### 1.3. Журнал, ошибки, настройки

- **Права роли загрузок `dwh_etl`** (пакет 036, I13-03): журналы запусков, ошибок, заявок и реестр файлов пишутся только функциями базы; прямая запись — только добавление в историю «было/стало» (`etl.object_record_change`, `etl.object_ods_record_change`), загрузка в таблицы `stg`/`ods`/`dm`; старые права на `dq.*`, `meta.*` и старую очередь CRM сняты, функции старого контура CRM никем не вызываются.
- **Журнал:**
  - запуски — `etl.object_run`, `etl.object_ods_run`, `etl.batch_run`, `etl.job_run`;
  - ошибки — `etl.error_log` (код, поле, `bad_value`, `diagnostic_context` в JSON);
  - экран — «Загрузки → Запуски», «Ошибки и история».
- **Коды ошибок:** `TYPE_CONVERSION`, `KEY_NULL`, `KEY_DUPLICATE`, `SCHEMA_DRIFT`, `TARGET_DRIFT`, `DISK_SPACE`, `LOCK_TIMEOUT`, `SOURCE_NO_RESPONSE`, `SOURCE_CONNECT_FAILED`, `SOURCE_NOT_READ_ONLY`, `TIMEOUT`, `DISPATCHER_LOST`, `DATABASE_ERROR` (по `SQLSTATE`).
- **Вид ошибки** (I13-02): каждый код относится к одной группе — `CONNECTION`, `STRUCTURE`, `FORMAT`, `FIELD`, `KEY`, `CONVERSION`, `DQ` (зарезервирована), `SCHEDULE`, `CONFIG`, `LIMIT`, `SYSTEM`, неизвестный код — `OTHER`; справочник — `backend/src/dwh_api/error_groups.py` (`HTTP_<код>` — `CONNECTION`), коды не меняются; `/api/admin/integrations/history/etl-errors` отдаёт `error_group`; тест `test_error_groups.py` не пропускает код движка без группы. В «Ошибках ETL» — вид, фильтр по виду и «Повторить» у самой новой ошибки объекта (заявка `RUN`, у ошибки `ODS_LOAD` — `CONTINUE_ODS`, тот же `POST /api/admin/integrations/object-run-requests`).
- **Сбои и восстановление** (I13-04, проверено в песочнице): процесс убит или соединение с DWH разорвано посреди STG или ODS — записанные порции остаются (I21, Б5), блокировка объекта снимается вместе с сеансом, следующий запуск закрывает зависший запуск `ABANDONED` и дописывает остальное без дублей; второй запуск того же объекта, пока идёт первый, — `RUN_REFUSED` без записи; вторая активная заявка, потерянная заявка (`DISPATCHER_LOST`) и наложение расписания на занятый объект — по тестам пакетов 015 и 032.
- **Настройки** (`/etc/dwh/dwh.env`):
  - `DWH_LOAD_CHUNK_ROWS` — размер порции;
  - `DWH_STAGE_COPY` — `0`: прежние `INSERT` вместо `COPY`;
  - `DWH_PG_DATA_DIR` — диск для проверки места;
  - `DWH_SOURCE_REPLY_TIMEOUT_SECONDS` (300) — сколько ждать ответа источника;
  - `DWH_OBJECT_RUN_TIMEOUT_SECONDS` (3600) — предел заявки без признаков хода;
  - `DWH_RUN_OBJECT_STACK_DUMP_SECONDS` — снимок стека зависшего запуска.

## 2. Диспетчер заявок

**Файлы:** `etl/src/run_request_dispatcher.py`, `etl/src/object_request_worker.py`, служба `dwh-dispatcher` (`tools/server/dispatcher_service.py`). **Роль:** `dwh_etl`.

- Очереди:
  - объектов — `etl.object_run_request`: `RUN`, `CONTINUE_ODS`, `FULL_RERUN`; по объекту одна активная заявка;
  - витрин — `etl.dm_mart_run_request`: `MANUAL`, `AFTER_ODS`, `PUBLISH`.
- Захват заявки — функцией `*_claim` под сессионной блокировкой. Если диспетчер перезапустился посреди заявки, база закрывает её `DISPATCHER_LOST`.
- Каждая загрузка объекта — отдельный дочерний процесс `run_object.py`. Время считается от последней строки хода (`STAGE:`); по пределу — `TIMEOUT`.
- Витрины выполняются в процессе диспетчера: они работают только с базой DWH.
- Заявки создаёт API функциями `app.integration_object_run_request_create/_cancel` и `app.dm_mart_run_request_create/_cancel` с проверкой права.
- **Расписания (I09, пакет 032).** На каждом цикле до очереди объектов диспетчер вызывает `etl.object_schedule_fire(worker)` (`fire_schedules()`; без пакета 032 — ничего). Наступившее расписание `etl.object_schedule` даёт заявку `SCHEDULED` от пользователя, включившего расписание; занятый объект — пропуск `SKIPPED_BUSY`, неготовый — `SKIPPED_NOT_READY` (`etl.object_schedule_event`); после простоя — один запуск, следующий считается от текущего времени (`etl.object_schedule_next`, пояс `Asia/Baku`, минуты и часы — по сетке от 2026-01-01 00:00). Неудачная заявка `SCHEDULED`/`RETRY` повторяется `RETRY` (до `retry_count` раз, через `retry_delay_minutes`), если после неё не было новой заявки объекта. Вид запуска — `etl.object_run_request.trigger_kind` (`MANUAL`/`SCHEDULED`/`RETRY`), номер попытки — `attempt`. Расписание сохраняет API `PUT /api/admin/integrations/object-schedules/{id}` (`app.object_schedule_save`, сохранение заявку не создаёт), список — `GET …/object-schedules` (`app.object_schedule_list`); экран — «Загрузки» → «Расписания».

## 3. Шлюз источников

**Файл:** `backend/src/dwh_api/source_gateway.py`. Единственная дорога к базам-источникам — новый код обращается к источникам только через него (тест-«сторож» `backend/tests/test_source_gateway.py` проверяет, что прямых подключений нет).

- До первого запроса включает в сессии источника режим «только чтение» и проверяет его (`SOURCE_NOT_READ_ONLY`).
- Пропускает только `SELECT`, `DECLARE`/`FETCH` и служебные команды чтения; запись — `SOURCE_WRITE_BLOCKED`.
- Защита от зависания:
  - `lock_timeout` (60 с) → `LOCK_TIMEOUT`;
  - TCP keepalive;
  - сторож ответа: отмена запроса, затем разрыв соединения → `SOURCE_NO_RESPONSE`;
  - «подталкивание» драйвера раз в секунду, чтобы принятые данные не застревали.
- Через шлюз работают проверка подключения, список объектов, снимок структуры («Интеграции») и движок загрузки.

### 3a. HTTP-шлюз и источник API (I11)

**Файлы:** `backend/src/dwh_api/http_gateway.py`, `api_request.py`, `api_source_admin.py`; пакет 033 (`database/migrations/033_api_source.sql`).

- **Шлюз** — единственная дорога к API-источникам (тест-«сторож» разрешает `urllib.request` только ему): только `GET`; только `https` (`http` — для хостов из `DWH_HTTP_PLAIN_HOSTS`); хост — из `DWH_HTTP_ALLOWED_HOSTS` (`tools/server/dwh_http_hosts.py`); перенаправления не выполняются; без прокси окружения; ответ до `DWH_HTTP_MAX_BYTES` (50 МБ); сертификаты — системные плюс `DWH_HTTP_CA_FILE` (по умолчанию `/etc/dwh/tls/ca.crt`). Сообщения — без строки запроса и секретов.
- **HTTP-запрос объекта** — документ в `meta.object_api_request` (одна строка на версию настроек, меняется только в черновике, копируется в новый черновик; ключи-секреты запрещены): адрес, параметры, заголовки, авторизация (`NONE`/`BEARER`/`BASIC`/`HEADER`/`QUERY`), формат `JSON`/`XML`, путь к записям, постраничная выдача (`PAGE`/`OFFSET`/`CURSOR`/`NEXT_LINK`, предел страниц), параметр инкремента, таймаут, повторы, пауза.
- **Секрет объекта** — привязка SecretStore источника с профилем `OBJECT_<id>`: `app.integration_object_secret_begin/_complete/_revoke`, чтение администратором — `_read_begin/_finish`, чтение загрузкой — `etl.object_secret_read_begin(объект, заявка)` только для заявки `RUNNING` этого объекта (как пакет 026), окончание — `etl.source_secret_read_finish`.
- **cURL** — `import_curl` разбирает команду на слова (`shlex`, оболочка не запускается): `-X GET`, `-H`, `-u`, `-G` с `-d`/`--data-urlencode`; секрет из `Authorization`, ключевого заголовка, `-u` или ключевого параметра уходит в SecretStore; `export_curl` показывает секрет как `***`. Черновик сохраняется и без пути к записям XML (`normalize(doc, draft=True)` — импорт cURL с `format=xml`, сохранение запроса, cURL-экспорт); «Проверить запрос», публикация и загрузка требуют путь (`API_CONFIG_INVALID`).
- **Чтение** — `read_pages`: страница за страницей, повтор на `429`/`5xx`/таймаут/нет связи (до `retries`, пауза по `Retry-After` или 2ⁿ с, не больше 60 с); ссылка «следующая» — только на тот же хост; ключ `QUERY` не берётся из ответа.
- **Структура** — «Проверить запрос» читает первую страницу, `infer_columns` предлагает типы (`bigint`, `numeric`, `boolean`, `date`, `timestamp with time zone`, `jsonb`, `text`), вложенные объекты — колонки `a.b`; «Сохранить структуру» — снимок одного объекта (`app.integration_api_object_capture`), его читает редактор маппинга.
- **Загрузка** — `run_object`: для объекта `API` (`etl.object_run_begin` пакета 033 отдаёт запрос опубликованной версии, подключение не нужно) секрет читается по заявке, `api_chunks` превращает записи в строки текстовых значений (списки и объекты — JSON) и отдаёт их общим шагам STG (проверка типов, ключ, запись порциями); инкремент — параметр с отметкой минус перекрытие; поле маппинга, которого нет в ответе первой страницы, — `SOURCE_DRIFT`. Коды ошибок: `HTTP_<код>`, `API_TIMEOUT`, `API_UNREACHABLE`, `API_TLS`, `API_HOST_NOT_ALLOWED`, `API_PLAIN_HTTP`, `API_RESPONSE_TOO_LARGE`, `API_BAD_JSON`, `API_BAD_XML`, `API_BAD_RECORDS`, `API_TOO_MANY_PAGES`, `API_NEXT_LINK_HOST`, `API_CREDENTIAL_MISSING`, `CREDENTIAL_UNAVAILABLE`.
- **API** — `/api/admin/integrations/source-systems/{id}/api-objects`, `/source-objects/{id}/api-request` (+ `/import-curl`, `/credential`, `/probe`, `/structure`); экран — вкладка «HTTP-запрос» в «Маппинге» (`frontend/src/ApiRequestPanel.tsx`).
- **Проверка полей ответа** (I13-01, решение Р1 = A′): поле маппинга, которого нет ни в одной записи первой непустой страницы или любой следующей страницы из 10 и более записей (`API_DRIFT_MIN_RECORDS`), останавливает запуск `SOURCE_DRIFT` с номером страницы до записи этой страницы; короткие страницы (обычно последняя) не оцениваются — API часто не присылает пустые поля.

### 3b. Источник «файлы JSON/XML» (I12)

**Файлы:** `backend/src/dwh_api/file_gateway.py`, `file_source_admin.py`; ветка `FILE` в `etl/src/run_object.py` (`load_files`, `choose_files`); пакет 034 (`database/migrations/034_file_source.sql`); тестовые файлы — `tools/server/dwh_test_files.py` (I12-07).

- **Только чтение (Ф1, Ф7):** папка источника — `<DWH_FILE_ROOT>/<код источника>` (по умолчанию `/srv/dwh/files/<код>`), это не настройка: пути от пользователя нет. Видны только обычные файлы прямо в этой папке по маске (с учётом регистра, без скрытых); файл или ссылка, которые после разворота ведут за пределы папки, пропускаются. DWH файлы не меняет, не переносит и не удаляет (тест-«сторож» `test_file_gateway.ReadOnlyGuardTest`). У служб `ProtectSystem=strict` — `/srv` доступен им только на чтение.
- **Объект** — вид `FILE`, схема `file`, имя — код (`app.integration_file_object_create`, только в источнике вида `FILE`). Подключения и пароля нет.
- **Настройки файла** — документ в `meta.object_file_config` (одна строка на версию настроек объекта, меняется только в черновике, копируется в новый черновик, ключи-секреты запрещены): маска, формат `JSON`/`JSONL`/`XML`, путь к записям, **путь к дате актуальности внутри файла** (Ф2′), режим `LATEST`/`ALL_NEW`, пояс даты без смещения (`Asia/Baku`), ожидание недописанного файла (60 с). Неизвестные ключи отбрасываются.
- **Разбор** — UTF-8 (с BOM или без); JSON — записи по пути, дата по пути того же документа; JSON Lines — строка = запись, дата — по пути в **первой** строке; XML — записи по пути элементов, дата — текст элемента или его атрибут `value`; `DOCTYPE`/`ENTITY` — отказ `FILE_XML_DTD_FORBIDDEN`; вложенность до 64; размер до `DWH_FILE_MAX_BYTES` (200 МБ). Дата: ISO 8601 (дата или дата-время, со смещением или без) или `ДД.ММ.ГГГГ[ ЧЧ:ММ[:СС]]`; без смещения — пояс настроек.
- **Реестр** — `etl.object_file`: одна строка на объект и содержимое (SHA-256): имя, размер, дата из файла, статус `LOADED`/`FAILED`/`NO_DATE`/`NOT_ACTUAL`, запуск, записей, попыток, сообщение. Пишет только загрузка (`dwh_etl`) через `etl.object_file_record` для своего запуска `RUNNING`; `LOADED` больше не меняется; `FAILED` повторяется следующим запуском (попытки +1); `TRUNCATE` запрещён. Читает администратор (`app.integration_file_registry`).
- **Выбор файлов (Ф4′, Ф5′, Ф11)** — `etl.object_file_state` отдаёт дату последнего загруженного файла и известные содержимые. Файл с известным содержимым (`LOADED`/`NOT_ACTUAL`/`NO_DATE`) пропускается — копия под другим именем не грузится второй раз. Не разбирается и менялся меньше 60 с назад — «ещё пишется», ждёт без записи в реестр; старше — `FAILED` (`FILE_BROKEN`). Без даты — `NO_DATE`. Дата не новее последнего загруженного — `NOT_ACTUAL`. Из остальных: `LATEST` — один файл с самой новой датой (прочие `NOT_ACTUAL`), `ALL_NEW` — все по возрастанию даты (файл с той же датой, что и предыдущий в этом запуске, — `NOT_ACTUAL`).
- **Загрузка** — файлы по одному: записи превращаются в строки текстовых значений, как у API (`file_records_chunks`; вложенные — `a.b`, списки и объекты — JSON), и идут общими шагами STG (проверка типов, ключ, запись порциями с фиксацией). Загруженный файл — `LOADED` с датой и числом записей. Ошибка файла (поле маппинга нет ни в одной записи — `SOURCE_DRIFT`, типы, ключ) — `FAILED` в реестре и остановка запуска с именем файла; строки прежних файлов остаются. Нет нового актуального файла — запуск `SUCCESS` с 0 строк. Коды: `FILE_FOLDER_MISSING`, `FILE_FOLDER_INVALID`, `FILE_FOLDER_UNREADABLE`, `FILE_TOO_MANY` (>10 000 по маске), `FILE_TOO_LARGE`, `FILE_UNREADABLE`, `FILE_BROKEN`, `FILE_BAD_RECORDS`, `FILE_XML_DTD_FORBIDDEN`, `FILE_CONFIG_INVALID`.
- **Предупреждения об отклонённых файлах (пакет 035):** файл `FAILED` при отборе или `NO_DATE` (код `FILE_NO_DATE`) не останавливает запуск, но `_warn_file` пишет в `etl.error_log` строку этапа `FILE_CHECK` с `diagnostic_context.severity = WARNING`, именем и SHA-256 (`etl.object_file_warning`, только `dwh_etl`, только свой запуск `RUNNING`, один раз на объект + код + содержимое). `etl.v_object_load_status.file_errors` — число таких файлов последнего запуска; `FILE_CHECK` не попадает в `stg_error_message`. Без пакета 035 загрузка идёт без предупреждений (сообщение в журнале службы).
- **API** — `/api/admin/integrations/source-systems/{id}/file-objects`, `/source-objects/{id}/file-config` (+ `/check` — до 20 последних изменённых файлов: дата, записей, что сделает следующая загрузка, колонки самого нового файла без значений; `/structure`), `/source-objects/{id}/files` — реестр; публикация объекта `FILE` требует полные настройки файла. Экран — вкладка «Файлы» в «Маппинге» (`frontend/src/FileSourcePanel.tsx`), поле вручную по пути (Ф9).
- **Настройки сервера** (`/etc/dwh/dwh.env`, не обязательны): `DWH_FILE_ROOT`, `DWH_FILE_MAX_BYTES`.

## 4. Движок витрин DM

**Файлы:** `etl/src/dm_mart_worker.py`, генератор SQL `backend/src/dwh_api/dm_sql.py`, витрины по SQL `backend/src/dwh_api/sql_mart.py`. **Роль:** `dwh_etl` (чтение `ods`, запись `dm`).

### 4.1. Витрина из конструктора

- **Зерно** — сущность (например, «Клиент») и её ключ; у каждой таблицы ODS своя колонка-ключ (каталог «Сущности и ключи»).
- **Источники:**
  - `GRAIN` — основная таблица, задаёт строки витрины;
  - `SAME_KEY` — дополняет строку (одна строка на ключ);
  - `CHILD` — много строк на ключ, поля только через агрегаты `SUM`, `COUNT`, `COUNT_DISTINCT`, `MIN`, `MAX`, `AVG`;
  - `LOOKUP` — справочник, соединяется с колонкой более ранней таблицы; одна таблица может подключаться несколько раз под разными псевдонимами.
- **Поля** с приоритетом источников: берётся первое непустое значение. **Фильтры** — по каждому источнику.
- **Генератор** сначала сводит каждую таблицу к ключу и только потом соединяет — суммы не умножаются.
- **Проверки до записи:**
  - нет пустого ключа зерна (`DM_KEY_NULL`);
  - ключи `GRAIN` / `SAME_KEY` уникальны (`DM_KEY_NOT_UNIQUE`);
  - колонки `LOOKUP` уникальны (`DM_LOOKUP_NOT_UNIQUE`) — с примерами значений;
  - таблицы и колонки ODS на месте (`DM_SOURCE_MISSING`).

### 4.2. Витрина по готовому SQL-запросу

- Один запрос `SELECT`, `WITH … SELECT` или с `UNION` / `INTERSECT` / `EXCEPT`.
- **Проверка запроса** выполняется под ролью `dwh_dm_sql_ro`, которая читает только `ods` и только на чтение:
  - план `EXPLAIN (VERBOSE)` — читаются только таблицы `ods`;
  - колонки с типами, первые 50 строк;
  - имена колонок допустимы.
- **Движок** читает строки в одном снимке данных (`REPEATABLE READ`):
  - колонки витрины на месте (`DM_SQL_COLUMNS_CHANGED`);
  - ключ не пуст и уникален;
  - запись через `COPY` под `dwh_etl`.

### 4.3. Запись и публикация

- **Обычное обновление:** `DELETE` + `INSERT` (или `COPY`) в одной транзакции — читатели видят прежние строки до фиксации. При ошибке прежние строки остаются.
- **Публикация новой структуры:** база создаёт `dm.<код>__next`, движок заполняет её (заявка `PUBLISH`), функция завершения подменяет таблицы и публикует версию. При ошибке новая таблица удаляется.
- **Когда обновляется:** при публикации, вручную («Загрузки → Витрины») и после ODS таблиц, которые читает витрина (если включено «Обновлять после ODS»).
- **Журнал:** `etl.dm_mart_run`, состояние — `etl.v_dm_mart_status`. **Настройка:** `DWH_DM_STATEMENT_TIMEOUT_SECONDS` (1800).

## 5. Публикация структуры таблиц (DDL из интерфейса)

**Где:** функции базы пакетов 019 и 021 — `app.object_table_preview/_publish` (STG/ODS), `app.mart_builder_preview/_publish/_delete` (DM).

- DDL строит **сама база** по белому списку типов полей; текст DDL от клиента не выполняется.
- «Опубликовать» в «Маппинге» или конструкторе витрин:
  - новые таблицы и поля создаются сразу;
  - удаление поля, смена типа и смена ключа — только после подтверждения, со списком затронутого (ODS, витрины, сохранённые отчёты, примеры помощника);
  - если смена типа испортила бы значения — отказ.
- Удаление витрины: таблица удаляется, витрина помечается `deleted_at`, её код остаётся занят.

## 6. ИИ-помощник

**Файлы:** `backend/src/dwh_api/ai_assistant.py` (`/api/ai/*`), `ai_core.py`, `ai_knowledge.py`, `ai_sql_guard.py`, `ai_llm.py`, `ai_diagnosis.py`. **Модель:** служба `dwh-llm` — llama.cpp, Gemma 4 26B A4B, только `127.0.0.1:8081`, без интернета; одна модель отвечает на один вопрос за раз (очередь, «Стоп» отменяет на сервере), поэтому у `llama-server` один слот (`-np 1`, окно `LLM_CONTEXT` = 16 384 токена).

- **Справка:**
  - поиск разделов `docs/DWH_USER_GUIDE.md`, доступных роли пользователя — каждый раздел помечен нужными правами;
  - **быстрый ответ без модели (I17-12, по умолчанию, `mode: script` в `/api/ai/help`):** строки найденных разделов взвешиваются по редким словам вопроса (обратная частота, как в поиске); остаются строки не слабее половины лучшей, не больше 6, под жирным заголовком «родительский раздел → раздел» (`ai_core.script_answer`, `KnowledgeIndex.parents`); к шагу списка добавляется строка, открывающая список, к строке с названием «…» — строка того же раздела с этим названием и словами «вкладка», «кнопка», «меню» или «→» (не больше 2, `SCRIPT_PLACE_LINES`). Строки берутся только из разделов не слабее 0,7 лучшего (`SCRIPT_SECTION_SHARE`); названные в кавычках подразделы того же раздела, доступные роли, раскрываются первым предложением (до 4); вопрос «где…» без строки с местом получает лучшую такую строку из остальных найденных разделов. После «нет ответа» `ai_may_help` (`ai_assistant.model_may_find`): модель предлагается для вопроса не по-русски и для уточнения (местоимение или начало «а»/«и»), если с прошлым вопросом поиск находит раздел. Прошлый вопрос — последний вопрос пользователя во всей истории, отличный от текущего (`last_user_text(history, question)`): модели уходят только 4 последних сообщения, прошлый вопрос в них может не попасть. Ищется только сам вопрос (слова прошлого вопроса не подмешиваются — иначе новый вопрос получил бы прошлый раздел). Вопрос со снимком экрана — всегда модель. С «Снимком экрана» интерфейс передаёт поле `screen` — выбранный пункт меню и вкладки на языке интерфейса и по-русски (`frontend/src/screenLabels.ts`, до 12, по 80 знаков); тогда вопрос не переводится моделью, справка ищется по русским названиям, карта всех разделов не отправляется, модель получает названия и правило называть элементы как в интерфейсе (`ai_core.SCREEN_NOTE`). Без `screen` (приложенный файл) — карта разделов, как раньше. Язык ответа решает приложение (`ai_knowledge.answer_language`: кириллица — ru, латиница с английскими словами — en, иная латиница — az) и передаёт модели явным правилом `ai_core.LANGUAGE_NOTE`. Со снимком поле `screen` несёт выбранные пункт меню и вкладки (`selected`) и заголовки, колонки, кнопки экрана (до 30, по 80 знаков) с названиями `ru`/`en`/`az` из словаря интерфейса; модель получает их на языке ответа с русским соответствием (`screen_lines`). В журнал — `HELP`, `OK` с кодом `AI_HELP_SCRIPT` (без названия модели) или `NO_DATA`. Модель — по кнопке («Объяснить подробнее (ИИ)», `mode: ai`); набор приёмки справки: 27 из 29 русских вопросов получают ожидаемый раздел без модели;
  - модели уходят не разделы целиком, а строки найденных разделов, в которых есть слова вопроса (заголовок раздела — всегда), всего до 2400 знаков (`ai_core.trim_found`, `HELP_CONTEXT_CHARS`); первые два раздела без совпадений дают начальные строки, дальние — отбрасываются; из диалога для вопроса по справке берутся последние 4 сообщения (`HELP_HISTORY_MESSAGES`). Причина — модель на сервере читает запрос со скоростью единиц токенов в секунду;
  - вопрос не по-русски переводится для поиска; ответ — на языке вопроса;
  - к вопросу можно приложить снимок экрана — он не сохраняется.
- **Отчёт по описанию:**
  - модель видит только описание витрин белого списка, доступных роли: колонки, справочные значения, термины, примеры; строк данных не видит;
  - SQL проверяет `ai_sql_guard`: один `SELECT`, без запрещённых слов и схем, без строк `E'…'`/`U&'…'` и без функций, выполняющих запрос из текста (всё с `xml` в имени, `ts_stat`, `ts_rewrite` — их чтение не видно в плане; I14-07, Н1), затем по плану `EXPLAIN` — только разрешённые витрины; пакет 037 дополнительно снимает `EXECUTE` на `*_to_xml*`, `ts_stat`, `ts_rewrite` у `PUBLIC` и рабочих ролей;
  - текст сравнивается без учёта регистра (`ai_core.fold_text_equality`, 20.11.2026): для текстовой колонки, сравниваемой со строками (`=`, `<>`, `LIKE`, `ILIKE`, `IN (…)`), колонка становится `translate(upper(колонка), 'İ', 'I')`, строки приводятся так же (`i`, `ı`, `İ` → `I`); показанный и сохранённый SQL — уже выровненный;
  - выполняет `dwh_ai_ro` только на чтение, с пределом строк;
  - после ошибки PostgreSQL — одна попытка самоисправления.
- **Разбор ошибок загрузок** (кнопка «Разобрать с помощником»):
  - сервер собирает досье фактов: ошибка, история запусков, поле и ключ в «Маппинге», изменения структуры, последняя проверка подключения без учётных данных, определение витрины;
  - добавляет базу знаний причин по 33 кодам;
  - сразу показывается карточка без модели, затем модель пишет «Что случилось / Где / Почему / Что сделать / Как проверить».
- **Память диалога:** последние 10 сообщений хранятся на странице браузера; с отчётом передаётся прежний SQL.
- **Журнал** `app.ai_request_log`: вопрос, SQL, результат, без строк данных и без изображений.
- **Журнал изменений настроек** (пакет 036, I13-03): новая или изменённая строка белого списка, колонки-справочника, термина или примера (`meta.ai_report_object` / `ai_value_column` / `ai_glossary` / `ai_example`) — событие `AI_SETTINGS_CHANGED` в `audit.security_event` (триггер `audit.audit_ai_settings`: кто, какая строка, витрина и право, изменённые поля; тексты терминов, примеров и SQL не копируются). Публикация витрины, меняющая белый список, тоже попадает в журнал.

## 8a. Вход пользователей (локальный и через домен, I20)

**Файлы:** `backend/src/dwh_api/auth.py` (`POST /api/auth/login`), `backend/src/dwh_api/directory_login.py`; функции базы `app.auth_*` (вход, сессия, журнал), `app.auth_get_directory_user`, `app.auth_bind_external_subject` (пакет 024); настройка — `tools/server/dwh_ldap_setup.py`.

- **Локальный вход** (`LOCAL`): пароль сверяется с хешем `app.user_account`; без изменений.
- **Вход через домен** (`LDAP` / `AD`, если `DWH_LDAP_ENABLED=true`) — только когда локального пользователя с таким именем нет:
  1. имя `user`, `VTBAZE\user` или `user@vtbaze.local` приводится к `user`; пользователь должен быть заведён в DWH с входом через домен и быть активным;
  2. соединение с контроллером: StartTLS на обычном порту (LDAPS на 636 / 3269); сертификат сверяется с отпечатками `DWH_LDAP_PINS` (или с УЦ `DWH_LDAP_CA_FILE`) **до** отправки любого пароля; порт без StartTLS отклоняется;
  3. служебная учётная запись (пароль — systemd-кредитив `dwh-ldap-bind`, только у `dwh-api`) ищет `sAMAccountName` в папках `DWH_LDAP_BASE_DNS`; значения запроса передаются в BER, а не строкой фильтра — подстановка фильтра невозможна;
  4. отключённая учётная запись (`userAccountControl`) — отказ без проверки пароля; иначе пароль проверяется входом от имени найденного DN; коды AD `data 52e/533/775/532/773/701` → причины `INVALID_CREDENTIALS`, `LDAP_ACCOUNT_DISABLED`, `LDAP_ACCOUNT_LOCKED`, `LDAP_PASSWORD_EXPIRED`, `LDAP_ACCOUNT_EXPIRED`;
  5. `objectGUID` записывается при первом входе и дальше сверяется (`LDAP_GUID_MISMATCH` при другом);
  6. сессия создаётся той же функцией, что для локального входа.
- **Отказоустойчивость:** контроллеры по порядку `DWH_LDAP_SERVERS`, следующий — только если предыдущий недоступен по сети; при недоступности всех — ответ 503 «Domain login service is unavailable» (`LDAP_UNAVAILABLE`), локальный вход работает.
- **Журнал:** неудачи — `LOGIN_FAILED` с причиной; привязка — `DIRECTORY_SUBJECT_BOUND`, расхождение GUID — `LDAP_GUID_MISMATCH`; пароли и GUID в журнал не пишутся. Пользователю всегда общий текст «Invalid username or password».
- **Пустой пароль** не отправляется никогда (в AD он означал бы анонимный вход).
- **Смена способа входа** (пакет 025, `POST /api/admin/users/{id}/auth-provider`, функция `app.user_catalog_set_auth_provider`): правила — как у сброса пароля (сессия администратора и `ADMIN_USER_MANAGE`, `can_manage_user`, не системные и не `SUPERADMIN`). `LOCAL` → `LDAP`: пароль стирается, привязка GUID — при следующем входе; `LDAP`/`AD` → `LOCAL`: временный пароль (политика и хеш — в API), смена при входе; GUID снимается, сессии пользователя завершаются, событие `AUTH_PROVIDER_CHANGED`.

| Проверка SecretStore (I02-03) | `tools/server/dwh_secret_check.py` | только чтение: права папок ключей и паролей, привязки ↔ файлы (SHA-256), `PENDING` и операции без итога, права ролей на функции; журнал от `postgres` в транзакции только чтения |

| Вход через домен (I20) | `tools/server/dwh_ldap_setup.py` | параметры в `dwh.env`, пароль служебной учётной записи в `systemd-creds`, drop-in для `dwh-api`, проверка контроллеров, включение после `PASS`, `--disable` |
| Проверка сервера для приёмки v1 (I14) | `tools/server/dwh_v1_check.py` | только чтение: службы, выпуск, свежесть и SHA-256 копии, итоги `dwh_tls.py check` и `dwh_secret_check.py`, маркеры пакетов 016–038, check 038/037/036 под `dwh_app`, заявки и запуски дольше 2 ч, опоздавшие расписания; объекты, ошибки по видам и события аудита — для сведения; итог `V1_CHECK_RESULT` |
| Проверка безопасности сервера (I14-07) | `tools/server/dwh_security_check.py` | только чтение: роли базы и права `PUBLIC`, `SECURITY DEFINER` с `search_path`, границы `dwh_ai_ro`/`dwh_dm_sql_ro` и их настройки, защита журнала аудита и `secret_store` (Б3, Б11); поиск паролей, токенов и ключей в журнале служб и отчётах — только счётчики (Б7); порты, nginx, ограничения служб, права файлов, SSH (Б9); итог `SECURITY_CHECK_RESULT` |
| Отрицательные запросы (I14-07) | `tools/server/dwh_negative_check.py` | под тестовой учётной записью без уровня администратора: флаги cookie сессии, выход, все маршруты без сессии — 401/403, все `/api/admin/*` с сессией — 401/403 (изменяющие — с пустым телом и номером 0), CORS; по флагам — подбор пароля (`--web` — через nginx, там это проверка, а не предупреждение), CSP страницы (`--web`) и попытка обойти помощника; итог `NEGATIVE_CHECK_RESULT` |
| Защита входа и страницы (I14-07) | `deploy/nginx/dwh.conf`, `DWH_COOKIE_SECURE` | nginx: `limit_req_zone … zone=dwh_login rate=5r/m`, `location = /api/auth/login` с `burst=5 nodelay`, сверх — `429` и JSON `too_many_requests` (форма входа показывает `message`); заголовок `Content-Security-Policy` (`default-src 'self'`, картинки ещё `data:`/`blob:`, `frame-ancestors 'none'`, без `unsafe-inline`); `DWH_COOKIE_SECURE=true` в `/etc/dwh/dwh.env` — cookie `dwh_session` с `Secure`; маршрут `/api/meta` удалён (Н2) |

**Журналы для администратора (I13-05).** Пакет 029: `app.audit_log_page(token, с, по, тип, пользователь, объект, итог, до_id, размер)`, `app.audit_log_filters(token)`, `app.secret_journal_page(token, источник, с, по, тип операции, до_id, размер)` — `SECURITY DEFINER`, `EXECUTE` только `dwh_app`; сессия — `app.audit_admin_session_user` (активный `ADMIN`/`SUPERADMIN` без обязательной смены пароля, иначе `Audit log access denied` / `Password change required`); страница до 200 строк по убыванию номера, следующая — по `next_before_id`; `details` проходят `app.audit_mask_details` (значения под именами `secret|passw|pwd|token|dsn|cipher|credential|private|salt|api_key` → `***`, кроме `true/false`; пароль в `…://user:пароль@…` → `***`); первая страница запроса пишет `AUDIT_LOG_VIEWED` / `SECRET_JOURNAL_VIEWED` с фильтрами. API `backend/src/dwh_api/audit_log_view.py`: `GET /api/admin/audit/events|filters|secret-operations` — уровень проверяет `server_load.require_server_admin`, вызов на управляющем подключении с фиксацией (запись события просмотра); ошибки: 401 (сессия), 403 (уровень, смена пароля), 422 (размер > 200, неизвестный тип операции). Интерфейс — `frontend/src/AuditLogPanel.tsx` («Администрирование» → «Журналы», вкладка видна только `ADMIN`/`SUPERADMIN`; ответ на устаревший запрос отбрасывается).

**Имена объектов в журнале (I13-15).** Пакет 031: `app.audit_entity_name(тип, ключ)` — имя из справочников при показе (`SOURCE_OBJECT` → `<код источника> · <схема>.<объект>`, `SOURCE_SYSTEM`, `DM_MART`, `DM_ENTITY` → код, `USER_ACCOUNT` → логин; номер без строки — `deleted: true`, удалённая витрина — код и `deleted: true`); `app.audit_entity_search(текст)` — объекты по части имени; `app.audit_log_page` (та же подпись, `CREATE OR REPLACE`) отдаёт `entity_name`, `entity_deleted`, фильтр «объект» ищет и по имени. Новые функции не исполняются `PUBLIC`/`dwh_app`. События журнала не меняются.

**Нагрузка сервера (I13-13).** `backend/src/dwh_api/server_load.py`: поток в процессе `dwh-api` раз в 2 с читает `/proc/stat` (ЦП всего и по ядрам: занято = 100 − idle − iowait, как `top`), `/proc/meminfo` (занято = MemTotal − MemAvailable, как `free`), `/proc/loadavg`, `/proc/diskstats` (только диски с `/sys/block/<диск>/device`, без CD-приводов `sr*`: чтение, запись, активность по времени ввода-вывода), `/proc/net/dev` (без `lo`), `statvfs` разделов, счётчики cgroup v2 служб (`cpu.stat` `usage_usec`, `memory.current`; шаблон `postgresql@17-main` — в `system-postgresql.slice`) и раз в 10 с — число подключений по ролям из `pg_stat_activity` (`dwh_app`, `connect_readonly`; при ошибке — «нет данных», повтор через 60 с). История — 1800 замеров (60 мин) в памяти; в базу и на диск ничего не пишется. API `GET /api/admin/server/load[?since=<время>]` — только `SUPERADMIN`/`ADMIN` (`auth.require_admin`) с выполненной сменой пароля; без `since` — текущие значения, с `since` — ещё замеры после этого времени. Настройки (`/etc/dwh/dwh.env`, не обязательны): `DWH_SERVER_LOAD_ENABLED` (`0` выключает сбор), `DWH_SERVER_LOAD_UNITS`, `DWH_SERVER_LOAD_MOUNTS` — списки через запятую. Интерфейс — `frontend/src/ServerLoadBadge.tsx` (плашка: опрос раз в 5 с; панель: раз в 2 с с `since`, ответ после смены режима отбрасывается; при 401/403 плашка скрывается).
