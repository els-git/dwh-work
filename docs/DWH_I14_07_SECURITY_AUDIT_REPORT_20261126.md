## Находки

### Н1 — высокий: отчёт помощника читает витрины `dm` вне белого списка роли — исправляется (песочница)

**Где:** `backend/src/dwh_api/ai_sql_guard.py` (проверка SQL отчёта по описанию, I17).

**Суть.** SQL отчёта выполняет роль `dwh_ai_ro`, которая читает **всю** схему `dm` (пакет 016); ограничение «только витрины, разрешённые роли пользователя» держится только на двух проверках кода: по тексту и по плану `EXPLAIN`. Обе обходятся:
1. XML-функции PostgreSQL выполняют запрос внутри себя, и прочитанные таблицы **не видны в плане**: `schema_to_xml('dm', …)` и `database_to_xml(…)` выгружают все таблицы схемы; в списке запрещённых слов их нет (есть только `query_to_xml`, `table_to_xml`, `cursor_to_xml`).
2. Строка вида `E'\''` (экранирование обратной косой чертой) сбивает разбор строк в текстовой проверке: часть настоящего кода считается строкой и не проверяется — так проходит и запрещённое `query_to_xml(...)`.

**Доказательство (песочница, база `sec1407`, роль-владелец):**
- `check_text("SELECT schema_to_xml('dm', true, false, '') FROM dm.cdp_clients LIMIT 1", белый список = cdp_clients)` — проходит; `EXPLAIN (FORMAT JSON, VERBOSE)` показывает только `cdp_clients`; результат содержит строку из `dm.secret_mart`.
- `SELECT E'\'' , query_to_xml(chr(115)||…, true, false, chr(32)) , '' AS x FROM dm.cdp_clients` — проходит текстовую проверку, план — только `cdp_clients`, результат — данные `dm.secret_mart`.

**Кто может:** пользователь с правом `AI_REPORT_RUN` и доступом хотя бы к одной витрине; модель пишет SQL по описанию пользователя, и нужный текст можно получить прямой просьбой. Сохранённый отчёт (I17-09) хранит SQL и выполняет его так же.

**Что получает:** все строки всех витрин `dm` (на сервере — витрины CRM с персональными данными клиентов), включая выгрузку CSV.

**Не проверено на сервере** (по плану — шаг 3, тестовая учётная запись).

**Предложение исправления (на решение, А3):**
- код: запретить в тексте SQL все функции с `xml` в имени и все строки с префиксом `E`/`e` и обратной косой чертой; лучше — **белый список функций** (агрегаты, дата/время, строки, математика) вместо списка запретов;
- база (пакет 037, E0→E1→E2): `REVOKE EXECUTE ON FUNCTION` для `query_to_xml*`, `schema_to_xml*`, `database_to_xml*`, `table_to_xml*`, `cursor_to_xml*` у `PUBLIC` (их выполняют только приложения, DWH ими не пользуется) — защита не зависит от кода проверки;
- временная мера до исправления: снять право `AI_REPORT_RUN` с ролей, кроме администраторов (интерфейс «Администрирование» → «Роли»).

### Н3 — низкий: нет заголовка Content-Security-Policy

`deploy/nginx/dwh.conf` ставит HSTS, `X-Content-Type-Options`, `X-Frame-Options DENY`, `Referrer-Policy`, `server_tokens off`, TLS 1.2/1.3 — но не CSP. ### Н4 — средний (повышен 26.11.2026): `dwh_etl` может менять `audit.revoked_grant_036`

Пакет 036 создал `audit.revoked_grant_036` и снял права только у `PUBLIC`; право по умолчанию схемы `audit` дало таблице права `dwh_etl`. **Сервер (`dwh_security_check.py`, 26.11.2026):** у `dwh_etl` на таблицу есть `SELECT`, `UPDATE`, `DELETE`, `TRUNCATE` (и, по правам по умолчанию, вероятно `INSERT` — уточняет опись `database/diagnostics/i14_07_audit_schema_inventory.sql`). Откат 036 выдаёт права **по строкам этой таблицы без проверки** — значит, процесс под `dwh_etl` может заранее вписать строку, и при откате суперпользователь выдаст `dwh_etl` право на любую таблицу; удаление строк сделает откат неполным. Срабатывает только при откате 036 — поэтому средний, а не высокий.

**Предложение (на решение):** пакет 038 — проверить строки `audit.revoked_grant_036` по списку 036 (объекты из списка, получатель только `dwh_etl`; при расхождении — STOP), снять права `dwh_etl` на таблицу, снять права по умолчанию схемы `audit` для `dwh_etl` (новые таблицы не получат их); откат 036 — проверять каждую строку по тому же списку.

### Н5 — низкий: копии базы создаются с правами 0644

`/backup/dwh/*.dump` (ночные и `pre-*`) — `-rw-r--r--`: копию целиком может прочитать любой пользователь сервера, если папка его пускает. Права папки `/backup/dwh` проверяются отдельно (у пользователя без `sudo` шаблон `/backup/dwh/*` не раскрывается — папка, вероятно, закрыта). Копия содержит все данные, хэши паролей входа и зашифрованные привязки. **Предложение:** создавать копии с правами 0600 (`dwh_backup.py`, `dwh_update.py`, `dwh_sql_package.py`) и один раз `chmod 600` существующие.

**Решение пользователя 26.11.2026 — A.** Исправление: `dwh_backup.py` создаёт копию и её `.sha256` с правами 0600 (umask 077 на время `pg_dump`), а каждый запуск переводит в 0600 и прежние копии папки (`tighten_modes`); копии `dwh_update.py` и `dwh_sql_package.py` (`pre-update-*`, `pre-<пакет>`) делает тот же `dwh_backup.py`, временный дамп E1 лежит в закрытой папке `postgres` и удаляется. Тест `test_server_tools.BackupTests.test_copies_are_private_i14_07_n5`. Существующие копии станут 0600 при первой же копии после установки выпуска (её делает `dwh_update.py`).

### Н7 — низкий: у cookie сессии нет флага `Secure`

Сервер, 26.11.2026 (`dwh_negative_check.py`, выпуск `2026.11.87`): `Set-Cookie: dwh_session=…` — `HttpOnly`, `SameSite=Strict`, но без `Secure`. ### Н8 — средний: нет защиты от подбора пароля

Сервер, 26.11.2026: 10 неверных паролей подряд — все `401`, затем верный пароль — `200` (вход выполнен). `auth.login` при неудаче только пишет событие (`app.auth_log_login_failure`); блокировки учётной записи, задержки или ограничения по адресу нет ни в API, ни в nginx. Для учётных записей домена (I20) действует политика блокировки контроллера; для локальных учётных записей (в том числе администраторов) подбор ограничен только скоростью проверки хэша. Сеть закрытая, неудачные входы видны в «Журналах» (фильтр `AUTH`). **Варианты (на решение):** A — ограничение частоты в nginx для `/api/auth/login` (`limit_req`, например 5 в минуту с адреса; без кода и пакета); B — временная блокировка учётной записи после N неудач в базе (пакет БД и код входа); C — принять риск до промышленной эксплуатации.
