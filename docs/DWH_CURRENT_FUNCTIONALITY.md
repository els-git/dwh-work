## 0. Как читать реестр

**Уровни подтверждения:**

- **КОД** — функциональность и маршруты найдены в исходниках; весь сценарий не тестировался в рамках этого аудита.
- **БД** — объект, столбец или ограничение подтверждены системными каталогами PostgreSQL в read-only отчёте; содержимое таблиц не анализировалось.
- **UI** — элемент интерфейса подтверждён исходниками и/или предоставленными скриншотами.
- **ПРАКТИКА** — пользователь предоставил фактический результат конкретного действия или диагностики.
- **НЕ ПОДТВЕРЖДЕНО** — недостаточно свидетельств для утверждения работоспособности.

Слово «реализовано» ниже означает **существует в коде/БД**, но не является гарантией, что вся функция прошла end-to-end тест на данной машине. По мере проверки статус и доказательства уточняются. Будущие возможности в этот документ как готовые **не включаются**.

## 1. Назначение и архитектура продукта

DWH — внутреннее веб-приложение управления хранилищем и контролем интеграций. Проектная цепочка: **источники → STG → ODS → DDS/семантика → витрины DM → наборы данных → отчётность**. Наличие архитектурного слоя в концепции **не означает**, что для него уже реализован универсальный редактор или исполняемый процесс.

| Контур | Реализация | Доказательство и ограничение |
|---|---|---|
| Frontend | React + TypeScript + Vite, клиентское приложение с разделами и формами | `frontend/src/App.tsx`, `main.tsx`, `package.json` — КОД |
| Backend | FastAPI, API `0.3.0`, бизнес-роутеры | `backend/src/dwh_api/main.py` и модули — КОД |
| Хранение | PostgreSQL `dwh`; слои `app`, `meta`, `etl`, `dq`, `stg`, `ods` (также предусмотрены DDS/DM в архитектуре) | Read-only аудит 16.10.2026 — БД; обследованы только выбранные схемы |
| ETL | Отдельные Python-процессы для CRM, загрузки STG, преобразований ODS, DQ, витрин и диспетчера | `etl/src/*.py` — КОД |
| Управление доступом | Сессии и RBAC через API и объекты `app` | `auth.py`, `access_control.py` и UI — КОД; часть БД-контрактов не представлена |
| Локальный запуск | PowerShell-обёртки, FastAPI и отдельный worker диспетчера; документация локального режима | `tools/run_local_dwh.ps1`, `tools/run_local_dwh_threaded.py`, `docs/LOCAL_DWH_RUNBOOK.md` — КОД; фактический статус сервисов на 19.10 не проверялся |

В интерфейсе определены пять основных страниц: **Integrations, ETL, DQ, Reporting, Administration**. `frontend/src/App.tsx` управляет выбранной страницей, загрузкой данных, состояниями фильтров, ошибок и загрузки. У администратора предусмотрены подпункты **Modules, Users, Roles, Access, Integrations** (`AdminPage.tsx`), видимость которых зависит от разрешений. **Уровень: КОД/UI.**

## 2. Аутентификация и управление сессией

**Файлы:** `backend/src/dwh_api/auth.py`, `security_password.py`, `models.py`, `frontend/src/AuthGate.tsx`, `auth.ts`, `authContext.ts`, `api.ts`.

- API `/api/auth/login`, `/api/auth/me`, `/api/auth/logout`, `/api/auth/change-password`. Состояние авторизации загружается frontend до доступа к защищённым разделам.
- Реализована серверная проверка учётных данных, хеширование паролей, хеширование токенов сессий и механизм HTTP cookie. Параметр времени жизни сессии `DWH_SESSION_TTL_HOURS` проверяется в диапазоне 1–24 часа.
- Для локальных (`LOCAL`) пользователей поддержана смена собственного пароля; алгоритм проверки сложности — `security_password.py`. При необходимости обязательной смены пароля состояние передаётся frontend.
- Выделены проверки `require_authenticated`, `require_admin`, `require_superadmin`, `require_permission`, `require_resource` и общий `authorize_api_access`.
- Для ошибок API реализованы унифицированные JSON-ответы `http_error`, `validation_error` (HTTP 422) и `internal_error` с `request_id`.
- Для обычных чтений backend использует `connect_readonly()` с транзакцией read-only; для разрешённых административных действий — отдельный `connect_control()` под ограниченной ролью и санкционированными DB-функциями. **Это не значит, что любая функция в БД безопасна без дополнительного аудита.**

**Уровень:** КОД; БД-политики и реальные сценарии логина полностью не регрессионно проверены этим документом. В отчёте PostgreSQL подтверждена диагностическая сессия `dwh`/`dwh_app` с `transaction_read_only=on`.

## 3. Уровни учётных записей, пользователи и роли

### 3.1. Пользователи

**Backend:** `user_catalog.py` (`/api/admin/users`); **frontend:** `AdminUsersPage.tsx`, `userCatalogApi.ts`.

- Просмотр списка пользователей; создание, редактирование профиля; включение/отключение учётной записи.
- Изменение уровня доступа учётной записи через специальный endpoint `/account-level`.
- Административный сброс пароля; проверка пароля до отправки; явное подтверждение действий, влияющих на доступ.
- В модели различаются уровень учётной записи и назначаемые бизнес-роли; в проекте используются `SUPERADMIN`, `ADMIN`, `USER`, а также варианты провайдера авторизации.
- Системные ограничения для SUPERADMIN и политики создания/редактирования заданы как отдельные проверки в коде/DB API. Не считать все сценарии изменения ролей полностью проверенными только по наличию контроллеров.

### 3.2. Каталог бизнес-ролей

**Backend:** `role_catalog.py` (`/api/admin/roles`); **frontend:** `AdminRolesPage.tsx`, `roleCatalogApi.ts`.

- Список бизнес-ролей; создание; редактирование названия/описания; активация/деактивация.
- Валидация кода роли и отдельные проверки допустимых административных операций.
- Структура бизнес-ролей отделена от уровня платформенной учётной записи.

### 3.3. Политики доступа, назначения и ресурсы

**Backend:** `access_control.py` (`/api/admin/access`); **frontend:** `AdminAccessPage.tsx`, `AdminAccessRolePolicies.tsx`, `AdminAccessUserAssignments.tsx`, `accessControlApi.ts`.

- Просмотр ролей и их разрешений; выдача/отзыв разрешения роли.
- Просмотр ресурсов; выдача/отзыв доступа роли к ресурсу.
- Просмотр пользователей и их бизнес-ролей; назначение и снятие роли у пользователя.
- Предусмотрены отдельные endpoints `/roles/{id}/permissions/...`, `/roles/{id}/resources/...`, `/users/{id}/roles/...`.
- Доступ к разделам UI фильтруется по разрешениям. Дополнительные проверки доступа к API реализованы сервером; полную проверку изоляции ресурсов необходимо поддерживать регрессионными тестами.
- Типы ресурсов в проверенном DB-контракте `app.resource`: `MODULE`, `DATASET`, `REPORT`, `DASHBOARD`, `SCHEME`. **Сам факт наличия типов не означает реализацию конструкторов Dataset/Dashboard/Scheme.**

**Уровень:** КОД, частично БД (`app.resource` и история назначений ресурсов в отчёте). Списки текущих пользователей, пароли, токены и конкретные разрешения в этот документ не переносим.

## 6. Администрирование интеграций (каталоги)

**Файлы:** `backend/src/dwh_api/integration_admin.py`, `frontend/src/AdminIntegrationsPage.tsx`, `integrationAdminApi.ts`, пять компонентов `AdminIntegration*.tsx`.

### 6.1. Исходные системы

- Каталог: `meta.source_system`, `app.integration_source_system_*`; endpoints `/api/admin/integrations/source-systems` для списка, создания, изменения, enable/disable.
- Атрибуты: `source_system_id`, код, название, тип, описание, флаг активности, даты изменений.
- На UI есть формы создания/правки, список и выбор системы.
- **Нет подтверждённой модели серверного профиля подключения:** в `meta.source_system` отсутствуют адрес, порт, база, endpoint, сетевой путь и защищённая ссылка на секрет. **Уровень: КОД + БД + UI.**

### 6.2. Исходные объекты

- Каталог `meta.source_object`: система, `source_schema`, `source_object`, `object_type`, `load_strategy`, `watermark_column`, `target_schema`, `target_object`, `load_order`, активность, описание.
- CRUD и enable/disable через `/source-objects`.
- В БД `object_type` ограничен `TABLE`/`VIEW`; стратегии: `FULL`, `INCREMENTAL`, `INCREMENTAL_OVERLAP`, `SNAPSHOT`. Это существующие технические значения, а не доказательство работоспособности всех режимов на любом источнике.
- **ПРАКТИКА:** в UI зарегистрирован `OPERATION_COLLECTOR` → `public.asan_pension_requests` (объект ID 16; `FULL`, цель `stg.operation_collector_asan_pension_requests`). Проверка 16.10: запись активна, но физическая STG-таблица отсутствует, связанных ETL jobs нет, snapshot структуры и столбцов — ноль. Это **метаданные, не готовая интеграция**.

### 6.3. Снимки структуры

- `meta.metadata_capture`, `meta.source_object_snapshot`, `meta.source_column_snapshot` и `meta.v_latest_source_structure`.
- Записываются позиции, имя и тип поля, nullable, признаки primary/unique key, identity, generated, default и комментарии; снимки связываются с запуском capture.
- `etl/src/capture_source_metadata.py` реализует чтение структуры **конкретного CRM-источника**. Универсальное определение PostgreSQL/Oracle/API/JSON/XML через UI не подтверждено.

### 6.4. Контракты столбцов

- `meta.column_contract` содержит привязку источника/поля к STG и целевой схеме/таблице/полю, ожидаемый тип PostgreSQL, required/allow_blank, активность, версию и историю изменения.
- `AdminIntegrationContracts.tsx` и `/api/admin/integrations/contracts`: просмотр, создание, версионирование и enable/disable.
- Снимки применённых к запуску версий: `meta.batch_contract_snapshot`, представление `meta.v_batch_contract_snapshot`.
- **ПРАКТИКА:** для `OPERATION_COLLECTOR` контрактов на дату экранной проверки не было.

### 6.5. Маппинг

- `meta.mapping_rule`, `meta.mapping_source_ref`, представления `v_current_mapping`, `v_current_mapping_detail`, `v_integration_control_mapping`.
- Этапы: `SOURCE_TO_STG`, `STG_TO_ODS`; типы: `DIRECT`, `CAST`, `DERIVED`, `CONSTANT`, `SYSTEM`.
- Сохранение `mapping_position`, `transform_name`, `transform_expression`, `expected_pg_type`, `source_layer` (`SOURCE`/`STG`), source refs, `definition_hash`, версий и времён действия.
- UI `AdminIntegrationMappings.tsx`: список, создание, изменение новой версии, добавление/удаление ссылок на источники, активация/деактивация.
- `etl/src/load_mapping_catalog.py`, `audit_mappings.py` работают с CRM-каталогом; наличие строк маппинга в БД **не означает** наличие универсального движка вычисления выражений.
- **ПРАКТИКА:** для `OPERATION_COLLECTOR` сопоставления ещё отсутствуют. Выбор полей по совместимости типов и создание физического целевого поля через визуальный мастер пока не подтверждены.

### 6.6. DQ-правила и связь с объектами

- UI `AdminIntegrationDqRules.tsx`: список, создание, версионирование, enable/disable.
- API `/api/admin/integrations/dq-rules` реализует административные операции.
- БД `dq.run_rule_snapshot` и представления `dq.v_integration_*`, `meta.v_integration_control_dq_rule` дают связь правил с источниками, историей и результатами.
- Не считать любую произвольно созданную строку DQ-правила автоматически исполняемой без проверки `etl/src/run_dq.py`.

### 6.7. Управление запусками внутри текущего интерфейса

- `AdminIntegrationRunControl.tsx`: просмотр кандидатов и очереди запусков, создание запроса, отмена ожидающего запроса.
- `GET /api/admin/integrations/run-candidates`, `GET/POST /run-requests`, `POST /run-requests/{id}/cancel`.
- Сохранённая модель очереди `etl.run_request` ограничена задачами `VALIDATE_STG`, `TRANSFORM_ODS`, `REFRESH_MARTS`, `RUN_DQ`; доступные поля `source_batch_run_id`, `load_mode`, статусы и результаты.
- **Важно:** согласованное будущее требование — вынести расписание и выполнение в **отдельный раздел**, не смешивая с настройкой. Текущий интерфейс пока имеет вкладку run-control в администрации; это не объявлять уже реализованным разделением.

### 6.8. История

- `AdminIntegrationHistory.tsx` отображает историю ETL-запусков, ошибок, DQ-запусков и замечаний; API `/history/etl-runs`, `/history/etl-errors`, `/history/dq-runs`, `/history/dq-issues`.
- Ошибки показывают объект, этап, код, сообщение, при наличии — идентификатор записи/столбца, ожидаемое и фактическое значение; интерфейс использует справочник Severity.

## 7. Движок загрузок (реализованный CRM-контур)

**Файлы:** `etl/src/dwh/config.py`, `dwh/db.py`, `extract_snapshot.py`, `plan_snapshot.py`, `load_snapshot.py`, `capture_source_metadata.py`, `validate_stg.py`, `transform_ods.py`, `refresh_marts.py`, `run_dq.py`.

1. **Конфигурация:** `get_dwh_config` для DWH и отдельная `get_crm_config` для источника CRM. Конфигурация читается из окружения; универсальные профили из административного каталога пока не используются.
2. **Извлечение:** `extract_snapshot.py` формирует выгрузку CRM, в том числе файловое представление snapshot; `plan_snapshot.py` проверяет/планирует пакет. Это **внутренний формат рабочего ETL**, не универсальный файловый коннектор JSON/XML из каталога пользователя.
3. **Загрузка в STG:** `load_snapshot.py` обрабатывает CRM snapshot, фиксирует идентификаторы batch/job, хеши и источники строк, watermark. В коде имеются привязки к `CRM_RETAIL` и целевым именам `crm_retail_*`.
4. **Обнаружение метаданных:** `capture_source_metadata.py` ориентирован на CRM, поддерживает снимки объектов и столбцов.
5. **Валидация STG:** `validate_stg.py` выполняет технические проверки до преобразования; записывает результаты и ошибки.
6. **Преобразование ODS:** `transform_ods.py` содержит конкретные SQL-трансформации CRM в списке `TRANSFORMS` и сверяет каталог маппингов. Транзакции выполняются на уровне объекта/задания; `FULL` и `CONTINUE` поддержаны в данном контуре, с проверкой совместимости конфигурации перед продолжением.
7. **Витрины:** `refresh_marts.py` обновляет текущие отчётные агрегаты; нет подтверждения универсального конструктора произвольных витрин.
8. **DQ:** `run_dq.py` выполняет проверки для CRM и пишет историю/проблемы; набор проверок ориентирован на существующую модель.

**Технические схемы STG:** read-only инвентаризация показала 12 таблиц, в том числе `stg.crm_retail_integration_log` с колонками `_dwh_landing_id`, `_dwh_batch_run_id`, `_dwh_job_run_id`, `_dwh_source_pk`, `_dwh_watermark_ts`, `_dwh_row_hash`, `_dwh_loaded_at`, `source_data jsonb`.

**Технические схемы ODS:** read-only инвентаризация показала 12 таблиц, в том числе `ods.crm_retail_integration_event` с полями события, исходным `jsonb` и `dwh_*` метаданными. Остальные таблицы STG/ODS не перечислялись поимённо в диагностике, поэтому здесь не приписываем им неподтверждённую схему.

**Ограничение:** новая таблица `OPERATION_COLLECTOR` не будет загружаться просто потому, что создана её карточка. Универсальный ETL, независимый от CRM и программирования, **не реализован/не подтверждён**.

## 8. Очередь, диспетчер, история и восстановление

**Файлы:** `etl/src/run_request_dispatcher.py`, `run_request_dispatcher_loop.py`, `backend/src/dwh_api/integration_admin.py`, `tools/run_dispatcher.ps1`, `run_local_dispatcher_worker.py`.

- `etl.run_request`: `run_request_id`, задача, привязка к исходному batch, опциональный режим загрузки, пользователь, времена запроса/захвата/начала/окончания, статус, ID результирующего batch/DQ и ошибки.
- Состояния очереди: `QUEUED`, `CLAIMED`, `RUNNING`, `SUCCESS`, `FAILED`, `CANCELLED` (БД).
- Диспетчер подбирает запрос и выполняет один из четырёх типов задач: `VALIDATE_STG`, `TRANSFORM_ODS`, `REFRESH_MARTS`, `RUN_DQ`. В коде есть обработка статусов запуска; соответствующие `etl.integration_run_request_*` функции существуют в БД.
- `etl.batch_run`: история batch с режимом `FULL`/`CONTINUE`, `root_batch_run_id`, `resume_from_batch_run_id`, `attempt_no`, `preflight_batch_run_id`; триггеры `MANUAL`, `SCHEDULED`, `RETRY` разрешены ограничением БД.
- `etl.job`: код, тип (`EXTRACT`, `TRANSFORM`, `MART`, `DQ`, `MAINTENANCE`), связанный источник/объект, назначение, порядок и активность.
- `etl.job_run`: статус объекта, метрики `rows_read`, `rows_inserted`, `rows_updated`, `rows_rejected`, `error_count`, возможность `reused_from_job_run_id` и `skip_reason`.
- `etl.error_log`: ошибки batch/job/объекта, этап, код, SQL state, exception type, diagnostic context, record key и отметка времени.
- `etl.watermark`: ключ по `job_id`, связанный исходный объект, тип/колонка контрольной точки, последнее успешно применённое значение и запуск.
- В **CRM ODS** режим `CONTINUE` повторяет неуспешный объект и позволяет переиспользовать результаты уже успешных объектов, при совпадении конфигурации. Это **частичная реализация** согласованного требования; не универсальная гарантия для PostgreSQL/Oracle/API/файлов.
- Наличие типа `SCHEDULED` не означает, что из UI можно задать произвольный календарь для любого объекта. Универсальный администрируемый планировщик **не подтверждён**.

**Уровень:** КОД + БД, для local-runbook есть ссылки на ранее выполненные smoke/crash-recovery проверки; свежего end-to-end теста всех путей 19.10 не проводилось.

### 12.9. Изолированная проверка готовности активации SecretStore — I02-03 (28.10.2026)

**Назначение (КОД):** `backend/src/dwh_api/secret_activation_readiness.py` проверяет внутреннюю согласованность переданных вызывающей стороной *синтетических* подтверждений для запрошенного перехода `PENDING → ACTIVE`. ### 12.36. Понятные причины ошибок загрузки — I13-08 (11.11.2026)

**Уровень: КОД + UI + ПРАКТИКА.** `etl/src/run_object.py` (SHA256 `1706B254…2FF6`), функции пакета 014.

- **STG:** значения источника сначала попадают во временную текстовую таблицу. Каждое значение проверяется на тип цели (`pg_input_is_valid`): неверный формат, переполнение числа, строка длиннее `varchar(n)`. Если хоть одно не проходит — запуск `FAILED` до записи в STG.
- **ODS:** при ошибке данных шаг откатывается, затем каждое поле проверяется отдельно временной функцией сессии.
- **Разбор** (код `TYPE_CONVERSION`):
  - поле и правило, число непрошедших строк из общего;
  - до 5 самых частых значений с количеством — значения показываются, решение Р1 = B;
  - до 10 ключей;
  - несколько полей — через ` | `.
- **Где видно:**
  - вывод `run-object`;
  - «History / Errors»: сообщение в «ETL Runs», в «ETL Errors» — «Problem», «Column», «Bad value», JSON в «Technical details»;
  - `etl.error_log`: `column_name`, `record_key`, `bad_value`, `diagnostic_context`.
- **На ПК 11.11.2026, `asan_pension_requests`:**
  - ODS v3 (`birth_date` — «Date from text» `DD.MM.YYYY`) — `FAILED`: «birth_date (DATE_FROM_TEXT DD.MM.YYYY -> date): 4 of 65 rows invalid; values: 'birthD' x4; keys: id=1, id=147, id=174, id=177»; в UI — «Column: birth_date», «Bad value: birthD»;
  - ODS v4 (без `birth_date`): полный запуск STG (INCREMENTAL, 3 строки, новая проверка значений пройдена) + ODS 65 без изменений — `SUCCESS`;
  - `check-crm` PASS;
  - после исправления 4 строк `birthD` в источнике: STG v3 (FULL) — прочитано 65 строк, 4 обновлены; ODS v5 (`birth_date` — «Date from text» `DD.MM.YYYY`) — 47 строк обновлены, 18 без изменений (`birth_date` пустая), `SUCCESS`.

**Ограничения:**
- строка длиннее `varchar(n)` в STG теперь останавливает загрузку (раньше обрезалась); в ODS «Convert type» к `varchar(n)` по-прежнему обрезает;
- число прочитанных строк упавшего запуска — 0, общее число указано в разборе;
- отдельного экрана разбора нет (I08-05).
