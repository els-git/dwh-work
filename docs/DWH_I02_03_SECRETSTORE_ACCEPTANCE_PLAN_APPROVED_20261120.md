# I02-03 — Эксплуатационная приёмка SecretStore

<sub>План утверждён пользователем 20.11.2026 · Р1–Р3, Р5, Р6 = A; Р4 = B (удалить неиспользуемые модули)</sub>

## 1. Цель и критерий

Критерий roadmap I02-03: **«Нельзя получить пароль через API/log, роли и журнал аудированы»**. Плюс обязательные условия раздела 8 и 9 roadmap (30.10.2026): мастер-ключ, ACL, служебная идентичность, авторизация, долговечный аудит, восстановление, отсутствие раскрытия секретов. Утверждённые правила — S01–S08, A01–A10, K01–K10, F01–F07, E01–E12 (28.10.2026). Правила не меняются; где предлагается отклонение — оно вынесено в решение.

Приёмка — **по рабочему контуру сервера**, а не по изолированным модулям 22–28.10.2026.

## 3. Требования против рабочего контура

Оценка по коду; «доказать» — проверка шагов 2–5.

| Группа | Закрыто кодом / прошлыми проверками | Пробел или что доказать |
|---|---|---|
| S01–S04 | привязка к одному источнику, `ACTIVE` один, READ только `ACTIVE` (003, 005–007) | доказать S03 (READ после REVOKE — отказ) на сервере |
| S05–S06 | ATTEMPT до файла, OUTCOME после (`store_source_credential`) | доказать: ошибка записи файла / журнала → прежний `ACTIVE` сохраняется |
| S07–S08 | `operation_id` сервера; восстановление не активирует автоматически | **нет инструмента**: незавершённые операции (ATTEMPT без OUTCOME, PENDING без файла) никто не показывает → Р5 |
| A01–A10 | журнал `secret_store`, независимые COMMIT ATTEMPT/OUTCOME, отказы (`record_denied_attempt`) | доказать на сервере: отказ без прав пишется; журнал не читается `dwh_app` (I13-05 — просмотр) |
| K01–K10 | I02-05 (резерв, восстановление, ротация — на ПК), I16 (`systemd-creds` на сервере) | K06 на сервере не повторялся; K03 — ключ в памяти процессов API и ETL (принято архитектурой, явно не записано) |
| F01–F05, F07 | папка вне `frontend/dist`, 0700 `dwh`, проверка `secret_ref`, без перезаписи | доказать фактические права и владельцев на сервере |
| **F06** | — | **зашифрованные файлы `/var/lib/dwh/secrets` не входят в ежедневную копию** (`dwh_backup.py` копирует только базу): при потере диска привязки в базе `ACTIVE`, файлов нет → Р3 |
| E01, E02, E11, E12 | отдельная роль `dwh_etl` (пароль в `/etc/dwh/dwh.env`), отказ при ошибке, нет CREATE/REPLACE/REVOKE | — |
| **E03–E08, E10** | — | **`etl.source_secret_read_begin(source_code)` выдаёт пароль любого источника** по коду, без проверки заявки/запуска; привязки к заданию, времени и отмене нет → Р2 |
| Раскрытие через API / журналы / ошибки | ответы API без значений, `SecretValue`, очистка сообщений | доказать «маркером»: синтетический пароль-маркер ищется в ответах API, журналах служб (`journalctl`), `etl.error_log`, журналах nginx, копии базы — 0 совпадений |

## 5. Шаги до `DONE`

1. Утверждение плана (Р1–Р6).
2. **Опись на сервере** (только чтение): `dwh_secret_check.py` — права и владельцы `/etc/dwh/keyring`, `/var/lib/dwh/secrets`, файлы и привязки по источникам, незавершённые операции, права на функции `secret_store`/`app.integration_source_secret_*`/`etl.source_secret_*`. Сначала песочница, затем выпуск. Две старые `ACTIVE` привязки `CRM_RETAIL` (G8) — фиксируются, отзыв — I02-06.
3. **Песочница:** удаление 21 модуля и 23 тестов (Р4 = B), пакет 026 (Р2, E0), изменение `source_secret.py`/`run_object.py`/диспетчера под заявку, копия файлов секретов в `dwh_backup.py` (Р3), тесты отказов (S05, S06, S03, E08, E10, K04, F07) и проверка «маркером»; `DWH_ENGINES.md`.
4. **Пакет 026:** E1 → E2 (каждый переход — с разрешения).
5. **Приёмка на сервере** (выпуск с шагом 3), на синтетическом источнике `SECRET_ACCEPT` (адрес не нужен, пароль — маркер):
   - CREATE → READ (проверка подключения) → REPLACE → REVOKE → READ после REVOKE — отказ; журнал: каждая операция с ATTEMPT и OUTCOME, отказ записан;
   - пользователь без прав — отказ, запись `DENIED`;
   - ETL: заявка `CRM_RETAIL` проходит; чтение без заявки / по завершённой заявке — отказ;
   - маркер не найден в ответах API, журналах служб, nginx, `etl.error_log`, копии базы;
   - копия файлов секретов и проверка привязок (Р3); `dwh_secret_check.py` — без незавершённых операций;
   - регрессия: загрузка объекта `CRM_RETAIL` заявкой — `SUCCESS`.
6. Реестр, подтверждение пользователя — I02-03 `DONE`.

Если Р2 = B: шаги 3–4 без пакета 026, в шаге 5 нет проверки ETL-заявки, отклонение E03–E08 записывается в roadmap.
