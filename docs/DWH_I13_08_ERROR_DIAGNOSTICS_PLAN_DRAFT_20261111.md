**Основа:**

- требование пользователя: «падение загрузки на некорректных данных — нормально, главное чётко получать причину / причины ошибки».

## 1. Что получится в итоге (простыми словами)

Если при загрузке в STG или ODS значение не преобразуется в тип цели, загрузка, как и сейчас, падает целиком: ничего не записывается. Но причина видна сразу, без дополнительных запросов — в выводе `run-object`, в `etl.error_log` и в «History / Errors»:

```
ODS_RESULT: FAILED | code=TYPE_CONVERSION | birth_date (Date from text, DD.MM.YYYY -> date): 47 of 65 rows invalid;
  values: '99.99.9999' x43, 'birthD' x4; keys: id=3, id=5, id=8, ... (10 of 47)
```

**Что показывается:**
- **поле** и правило: преобразование, формат, целевой тип;
- **сколько строк** не прошло из скольких;
- **сами значения** (Р1 = B, решение пользователя 11.11.2026) — до 5 самых частых разных значений с количеством, каждое не длиннее 50 символов (длиннее — обрезается с `…`);
- **ключи строк** — до 10 примеров;
- если не прошли **несколько полей** — каждое отдельной строкой.

## 2. Как устроено (пакет БД 014, без изменений UI)

- **STG:** значения источника сначала попадают во временную таблицу как текст. Перед приведением к типам цели каждое поле проверяется функцией PostgreSQL `pg_input_is_valid(значение, тип)` — она есть в PostgreSQL 16 и 17, и уже используется в `validate_stg.py`. Она ловит неверный формат, переполнение числа и превышение длины `varchar(n)`. Если есть непрошедшие значения — `FAILED` с разбором по полям, до записи в STG.
- **ODS:** если шаг упал на ошибке преобразования, движок откатывает шаг и проверяет каждое поле отдельно. Для каждого поля создаётся временная функция сессии, которая вычисляет то же выражение из белого списка в блоке с перехватом ошибки. Разбор выполняется только после ошибки, на успешные запуски он не влияет.
- **Где видно:**
  - вывод команды;
  - `etl.error_log`: текст — разбор (до 2000 символов), `column_name` — первое поле, `record_key` — первый ключ, `bad_value` — самое частое непрошедшее значение первого поля, `diagnostic_context` — JSON со всеми полями (Р2 = B);
  - «История / Ошибки» — уже показывает текст, столбец, «Некорректное значение» и «Технические детали» (JSON); правка UI не нужна.
- **Пакет 014** (`database/migrations/014_load_error_diagnostics.sql`): новые варианты `etl.object_run_finish` и `etl.object_ods_run_finish` с двумя дополнительными параметрами — `p_bad_value text`, `p_diagnostic jsonb`. Прежние варианты не меняются и не удаляются: число параметров разное, вызовы не путаются. `EXECUTE` — только `dwh_etl`, `SECURITY DEFINER`, фиксированный `search_path`, права по умолчанию снимаются явно. Откат удаляет только новые варианты; записи `etl.error_log` не трогает.
- **JSON `diagnostic_context`:** `{"kind": "TYPE_CONVERSION", "stage": "ODS", "total_rows": 65, "fields": [{"column": "birth_date", "rule": "DATE_FROM_TEXT DD.MM.YYYY -> date", "invalid_rows": 47, "values": [{"value": "99.99.9999", "count": 43}, {"value": "birthD", "count": 4}], "keys": [{"id": 3}, …]}]}`.
- **Ограничения разбора:** до 5 значений и 10 ключей на поле; разбор — один проход по набору на поле (до 1 000 000 строк, как и сама загрузка).
