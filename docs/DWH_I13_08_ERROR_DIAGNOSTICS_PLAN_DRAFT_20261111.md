# I13-08 — понятные причины ошибок загрузки: план (ПРОЕКТ)

**Статус документа:** проект, 11.11.2026; ждёт утверждения пользователя.
**Статус задачи:** I13-08 `PLANNED` (добавлена 11.11.2026 решением пользователя по итогам приёмки I06-05).
**Основа:**
- приёмка I06-05, шаг 8. ODS-версия v1 упала с `TYPE_CONVERSION (SQLSTATE 22007)` без указания поля. Поле `birth_date` и значение `birthD` в 4 строках найдены только отдельным запросом.
- требование пользователя: «падение загрузки на некорректных данных — нормально, главное чётко получать причину / причины ошибки».

## 1. Что получится в итоге (простыми словами)

Если при загрузке в STG или ODS значение не преобразуется в тип цели, загрузка, как и сейчас, падает целиком: ничего не записывается. Но причина видна сразу, без дополнительных запросов — в выводе `run-object`, в `etl.error_log` и в «History / Errors»:

```
ODS_RESULT: FAILED | code=TYPE_CONVERSION | birth_date (Date from text, DD.MM.YYYY): 4 of 65 rows invalid;
  values like: aaaaaA ×4; keys: id=12, id=31, id=40, id=57
```

**Что показывается:**
- **поле** и правило: преобразование, формат, целевой тип;
- **сколько строк** не прошло из скольких;
- **вид значений** — маска: цифры → `9`, строчные буквы → `a`, заглавные → `A`, остальные символы как есть. До 5 самых частых масок с количеством. Сами значения не показываются: в данных бывают персональные сведения;
- **ключи строк** — до 10 примеров;
- если не прошли **несколько полей** — каждое отдельной строкой.

## 2. Как устроено (без изменений БД и UI)

- **STG:** значения источника сначала попадают во временную таблицу как текст. Перед приведением к типам цели каждое поле проверяется функцией PostgreSQL `pg_input_is_valid(значение, тип)` — она есть в PostgreSQL 16 и 17, и уже используется в `validate_stg.py`. Она ловит неверный формат, переполнение числа и превышение длины `varchar(n)`. Если есть непрошедшие значения — `FAILED` с разбором по полям, до записи в STG.
- **ODS:** если шаг упал на ошибке преобразования, движок откатывает шаг и проверяет каждое поле отдельно. Для каждого поля создаётся временная функция сессии, которая вычисляет то же выражение из белого списка в блоке с перехватом ошибки. Разбор выполняется только после ошибки, на успешные запуски он не влияет.
- **Где видно:**
  - вывод команды;
  - `etl.error_log`: текст — разбор (до 2000 символов), `column_name` — первое поле, `record_key` — первый ключ;
  - «History / Errors» — уже показывает текст ошибки.

  Пакет БД и правка UI не нужны: функции завершения запуска уже принимают текст, колонку и ключ.
- **Ограничения разбора:** маски и ключи без значений; до 10 ключей и 5 масок на поле; разбор — один проход по набору на поле (до 1 000 000 строк, как и сама загрузка).
