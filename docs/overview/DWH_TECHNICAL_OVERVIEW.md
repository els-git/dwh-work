# DWH — техническое описание

**Версия документа:** 1.0 · 27.11.2026
**Выпуск приложения:** v1 = `2026.11.88` (тег `v1.0`)
**Назначение документа:** описание устройства, технологий, инфраструктуры и мер безопасности DWH — для согласования с инфраструктурой, информационной безопасностью и руководством ИТ.

---

## 1. Кратко

DWH — внутреннее веб-приложение, которое:
- забирает данные из систем-источников (базы PostgreSQL, REST-API, файлы JSON/XML) **только на чтение**;
- раскладывает их по слоям хранилища `STG → ODS → DM`;
- строит отчётные витрины;
- даёт пользователям просмотр и выгрузку витрин с учётом прав;
- включает локальный ИИ-помощник, который работает на своём сервере без выхода в интернет.

Всё настраивается из интерфейса: источники, маппинг полей, таблицы, расписания, витрины, пользователи и права. Программировать или вручную писать DDL для этого не нужно.

Приложение разработано по личной инициативе автора. Сейчас оно развёрнуто на одной виртуальной машине во внутренней сети и проверено на тестовых данных и тестовых источниках.

## 2. Архитектура

```
 Пользователь (браузер)                     Источники (только чтение)
        │ HTTPS 443                         ┌─ PostgreSQL: CRM, ProcessViewer …
        ▼                                   ├─ REST-API (GET, список разрешённых адресов)
 ┌───────────── сервер app-dwh-srv ─────────┴─ файлы JSON/XML в папке сервера
 │ nginx (TLS 1.2/1.3, CSP, лимит входа)
 │   ├─ статический интерфейс (React)
 │   └─ /api → dwh-api (FastAPI, 127.0.0.1:8000)
 │                  │
 │                  ├─ PostgreSQL 17 (база dwh)  ← dwh-dispatcher (заявки, расписания, движки)
 │                  ├─ SecretStore (пароли источников, шифрование AES-256-GCM)
 │                  ├─ LDAP-контроллеры домена (StartTLS) — вход доменных пользователей
 │                  └─ dwh-llm (llama.cpp, 127.0.0.1:8081) — ИИ-помощник
 │ ночная копия базы и зашифрованных файлов → /backup
 └──────────────────────────────────────────
```

**Слои данных:**

| Слой | Схема | Что хранит |
|---|---|---|
| STG | `stg` | Копия объекта источника. Типы значений проверены, ключ не пуст и не повторяется |
| ODS | `ods` | Рабочий вид: переименование, приведение типов, преобразования по белому списку, история изменений |
| DM | `dm` | Отчётные витрины: собираются из ODS конструктором или готовым SQL-запросом |
| Служебные | `app`, `meta`, `etl`, `audit`, `secret_store` | Пользователи и права, настройки объектов и витрин, очереди и журналы запусков, журнал аудита, журнал операций с секретами |

### 4.4. Доставка изменений

1. Код меняется в репозитории через pull request. Перед выпуском — автоматические тесты, сборка интерфейса, ESLint.
2. На ПК администратора собирается **пакет выпуска**: архив с кодом, собранным интерфейсом и всеми Python-зависимостями. К нему прилагается SHA256.
3. Пакет копируется на сервер по `scp`. `dwh_update.py` проверяет SHA256, ставит выпуск рядом с прежним (`/opt/dwh/releases/<версия>`), переключает ссылку `/opt/dwh/current` и перезапускает службы. Перед обновлением делается копия базы.
4. Если проверка после запуска не прошла, выпуск автоматически откатывается. Откат на любой прежний выпуск — одна команда (`--rollback-to`).
5. Изменения структуры базы — нумерованные **SQL-пакеты**, у каждого есть откат и тест. Порядок для каждого пакета:
   - E0 — песочница;
   - E1 — копия рабочей базы на сервере: применение, проверка, откат, повторное применение;
   - E2 — рабочая база, перед применением делается копия.

   Каждый переход — только с разрешения владельца.

## 5. Как работают основные механизмы

### 5.1. Подключение источников и загрузка

- **Источник** — система: PostgreSQL, API или файлы. У источника PostgreSQL одна учётная запись. Её пароль хранится в SecretStore, интерфейс его никогда не показывает.
- **Снимок структуры** читает из каталога источника список таблиц и колонок.
- **Маппинг** — версии настроек объекта:
  - поля, типы, ключ и стратегия загрузки (`FULL` или `INCREMENTAL` по полю-водяному знаку с перекрытием);
  - при публикации **база сама создаёт или меняет** таблицы STG и ODS;
  - опасные изменения требуют подтверждения со списком затронутого: удаление поля, смена типа или ключа.
- **Шлюз источников.** Все обращения к источникам идут через шлюз:
  - соединение открывается в режиме только чтения, это проверяется до первого запроса;
  - фильтр команд пропускает только `SELECT`;
  - для API разрешён только `GET` и только на адреса из списка на сервере, без перенаправлений.

  Это требование владельца: DWH никогда не пишет в источники.
- **Движок загрузки:**
  - читает источник порциями по 100 000 строк;
  - проверяет каждое значение на соответствие типу и проверяет ключ;
  - пишет в STG через `COPY`, затем строит ODS и ведёт историю изменений «было/стало».

  Ошибка данных останавливает загрузку с понятной причиной: поле, число строк, примеры значений и ключей. Частичной записи при этом нет.
- **Файлы.** Папка на сервере, дата актуальности берётся внутри файла. Реестр файлов исключает повторную загрузку. Отклонённые файлы показываются предупреждением. DTD в XML запрещены.

### 5.2. Запуск: заявки, диспетчер, расписания

- Любая загрузка — это **заявка** в очереди базы: «Запустить», «Заново полностью» или «Продолжить (ODS)». По одному объекту одновременно выполняется только одна заявка.
- **Диспетчер** забирает заявки и выполняет движок отдельным процессом с ограничением времени:
  - зависший источник прерывается по тайм-ауту;
  - заявки, потерянные при сбое, закрываются при восстановлении.
- **Расписания** задаются для каждого объекта: каждые N минут или часов, ежедневно, по дням недели. При ошибке — повторы, их число и паузу можно задать.
- После успешного ODS автоматически ставятся заявки на пересборку витрин, которые читают эту таблицу.

### 5.3. Витрины DM

- **Конструктор:**
  - основная таблица задаёт зерно витрины;
  - к ней подключаются таблицы с тем же ключом, дочерние таблицы с агрегатами (`SUM`, `COUNT`, …) и справочники;
  - у поля может быть несколько источников по приоритету;
  - можно задать фильтры.
- **Готовый SQL:** запрос проверяется под отдельной ролью `dwh_dm_sql_ro`. Она только читает и видит только `ods`.
- **Публикация** строит новую таблицу рядом (`dm.<код>__next`), заполняет её и подменяет старую без перерыва для пользователей.

### 5.4. Отчётность

- Пользователь видит только витрины, на которые есть право его роли.
- Доступны фильтры, сортировка, постраничный просмотр и выгрузка в CSV, XLSX или PDF с ограничением объёма.
- Сервер сам строит запросы: имена колонок берутся только из каталога, значения передаются параметрами.
- Каждое открытие и каждая выгрузка пишутся в журнал.

### 5.5. ИИ-помощник

- Модель работает **на сервере DWH**: слушает только `127.0.0.1`, в интернет не выходит, данные никуда не передаются.
- **Помощь по справке:**
  - быстрый ответ строится из текста справки без модели;
  - подробный ответ модели — по кнопке;
  - учитывается роль: разделы, закрытые для роли, не используются;
  - поддерживаются русский, английский и азербайджанский;
  - можно приложить снимок экрана.
- **Отчёт по описанию:**
  - модель пишет SQL;
  - сервер проверяет его по тексту и по плану `EXPLAIN`: только `SELECT`, только витрины из белого списка роли, без опасных функций;
  - запрос выполняется ролью `dwh_ai_ro`, которая только читает `dm`;
  - сами данные модель не видит.
- **Разбор ошибок загрузок** — по досье фактов (ошибка, история, маппинг) и базе знаний причин.
- Ограничение: скорость модели определяется процессором ВМ, развёрнутый ответ занимает минуты. Быстрые ответы по справке приходят сразу.

## 6. Безопасность

### 6.1. Вход и сессии

- Два способа входа:
  - **локальная учётная запись** — пароль хранится только в виде хеша, проверяется сложность, после выдачи администратором пароль нужно сменить;
  - **учётная запись домена** `vtbaze.local` — проверка через LDAP со StartTLS, сертификаты контроллеров закреплены по отпечаткам. Служебная учётная запись поиска хранится в `systemd-creds`.
- Сессия:
  - cookie с флагами `HttpOnly`, `Secure`, `SameSite=Strict`;
  - в базе хранится хеш токена;
  - срок жизни — 8 часов;
  - при входе выдаётся новый токен.
- Защита от подбора: не больше 5 попыток входа в минуту с одного адреса (nginx).
- Ответ и время ответа для несуществующего пользователя и для неверного пароля одинаковы — перечислить пользователей нельзя.

### 6.2. Права

- **Уровни учётной записи:** `USER`, `ADMIN`, `SUPERADMIN`. Администратор не может повысить себя или другого до `SUPERADMIN`.
- **Бизнес-роли:** набор прав (например, `REPORT_VIEW`, `ETL_VIEW`, `AI_REPORT_RUN`) и ресурсов (модуль `CDP`). Права назначаются ролям, роли — пользователям.
- Права проверяются **дважды**: в API и в базе. Функции базы сами проверяют сессию, клиентским данным не доверяют.

### 6.3. Роли базы данных (принцип минимальных прав)

| Роль | Кто использует | Что может |
|---|---|---|
| `dwh_app` | API | Читает служебные представления; меняет данные только через функции с проверкой сессии |
| `dwh_etl` | Диспетчер и движки | Пишет в `stg`, `ods`, `dm` и журналы через функции. Журнал аудита ему недоступен |
| `dwh_ai_ro` | ИИ-помощник, просмотр витрин | Только чтение `dm` |
| `dwh_dm_sql_ro` | Проверка готового SQL витрин | Только чтение `ods` |
| `dwh_admin` | Владелец объектов, SQL-пакеты | DDL. Входа нет, используется только пакетами |

### 6.4. Секреты

- **SecretStore** хранит пароли источников в зашифрованных файлах (AES-256-GCM). Мастер-ключи хранятся в `systemd-creds`, есть резервные копии ключей.
- Пароль источника получает только выполняемая заявка. Каждое чтение пароля пишется в журнал операций.
- Пароли, токены и строки подключения никогда не возвращаются через API, интерфейс, журналы или сообщения об ошибках.

### 6.5. Аудит

- Журнал безопасности `audit.security_event` фиксирует:
  - входы и неудачные попытки;
  - изменения пользователей, ролей и прав;
  - запуски загрузок, публикации витрин;
  - просмотры и выгрузки витрин;
  - операции с секретами.
- Журнал **неизменяем**: изменение, удаление и `TRUNCATE` запрещены на уровне базы.
- Администраторы просматривают журналы в интерфейсе с фильтрами. Выгрузки журнала нет, и сам просмотр тоже пишется в журнал.

### 6.6. Веб-защита

- TLS только 1.2 и 1.3, сертификат внутреннего УЦ `ROOT-CA` (VTBAZE).
- Заголовки:
  - `Content-Security-Policy` — только свой источник скриптов и стилей;
  - `Strict-Transport-Security`;
  - `X-Frame-Options`;
  - `X-Content-Type-Options`.
- Схема API (`/docs`, `/openapi.json`) снаружи не отдаётся.
- Любые данные — из источников, ответов модели, названий объектов — выводятся в интерфейсе как текст.

### 6.7. Проверки безопасности

- **Внутренний аудит (I14-07).** Найдено и закрыто восемь находок, среди них одна высокая — обход проверки SQL помощника. Есть инструменты проверки сервера:
  - `dwh_security_check.py` — права ролей, файлы, настройки nginx;
  - `dwh_negative_check.py` — отрицательные запросы под пользователем без прав.
- **Проверка «со стороны» (I24, 27.11.2026).** Атаки на копию выпуска и неразрушающая проверка рабочего сервера с ПК:
  - вход и сессии;
  - чужие отчёты и витрины;
  - 28 попыток обойти проверку SQL помощника;
  - внедрение скриптов в интерфейс;
  - запросы на внутренние адреса;
  - выход из папки файлов;
  - повышение прав администратором.

  Серьёзных и средних слабостей не найдено.
- Принятое ограничение: на экранах администрирования администратору может показываться текст ошибки базы. Независимый внешний пентест не проводился.

## 8. Текущее состояние и ограничения

- **Работает и проверено на сервере:**
  - источники PostgreSQL, API и файлы;
  - загрузка STG и ODS, расписания;
  - конструктор и SQL-витрины;
  - отчётность с выгрузкой;
  - ИИ-помощник;
  - вход через домен;
  - аудит, копии, обновление и откат.
- **Данные** — тестовые. Боевые источники к развёртыванию не подключены.
- **Не реализовано:**
  - Oracle — запланирован;
  - проверки качества данных (DQ);
  - группы объектов с зависимостями.
- **Не проверено на сервере:** большой объём (миллионы строк) — проверен только в песочнице, 3 млн строк.

## 9. Что нужно от ИТ для дев-развёртывания

1. **Согласование размещения:** сервер `app-dwh-srv` (уже выделен) или новый по тем же параметрам. Достаточно 8–16 ядер, 32 ГБ ОЗУ, SSD 200 + 500 ГБ.
2. **Доступы к дев-средам источников:** учётные записи **только на чтение** к нужным базам дев-контура и сетевые правила от `10.1.57.2` к ним (PostgreSQL 5432 / нужные порты).
3. **Список разрешённых адресов API** дев-контура, если они нужны.
4. **Вход через домен** — уже настроен: служебная учётная запись поиска выдана, работает StartTLS к двум контроллерам.
5. **DNS-имя и сертификат** — уже выданы (`dwh.vtbaze.local`, внутренний УЦ).
6. **Согласование ИБ:**
   - модель угроз и меры из раздела 6;
   - решение о внешнем пентесте;
   - правила доступа администраторов (сейчас SSH по паролю и ключу из внутренней сети).
7. **Резервные копии:** сейчас копии лежат на том же сервере (`/backup`). Для дев-контура этого достаточно; для промышленного — нужно внешнее хранилище копий.
