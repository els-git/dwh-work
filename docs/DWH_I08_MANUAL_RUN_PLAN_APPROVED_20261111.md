## 1. Что получится в итоге (простыми словами)

В меню появляется раздел **«Загрузки»** (англ. «Data Loads», азерб. «Yükləmələr»). В нём собрано всё, что относится к работе загрузок, а не к их настройке (вкладки — раздел 1a).

**Вкладка «Объекты»:**
- по каждому объекту видно: версия STG и ODS в силе, последний запуск STG и ODS со статусом и временем, текст последней ошибки (разбор I13-08);
- кнопки:
  - **«Запустить»** — STG + ODS по стратегии опубликованной версии, как `run-object`;
  - **«Продолжить»** — только ODS. Доступна, если последний STG успешен, а ODS после него упал;
  - **«Заново полностью»** — STG с чтением всего объекта (разово, без смены версии) + ODS;
- кнопки доступны только для объекта в статусе `READY`: черновик и непроверенный объект запустить нельзя. Сохранение настроек ничего не запускает;
- нажатие создаёт **заявку**. Её выполняет диспетчер, тот же, что для CRM: `run_local_dwh.ps1 -Mode Run`. Статус заявки и ссылка на запуск видны в списке.

**«Откат»:** запуск объекта — одна транзакция на STG и одна на ODS. При ошибке ничего не записывается, поэтому откатывать нечего. «Продолжить» не повторяет успешный STG; «Заново» не пропускает строки.

## 7. Шаг 2 — результат (11.11.2026, ПК)

Отчёт пользователя: `readonly_i08_step2_run_request_20261111_163244.txt`, роль `dwh_app`, `ro=on`.

**Очередь CRM** — `etl.run_request`:
- 16 колонок: задача, исходный пакет (обязателен), режим, статус `QUEUED/CLAIMED/RUNNING/SUCCESS/FAILED/CANCELLED`, кто и когда, результат, сообщения;
- задачи только `VALIDATE_STG/TRANSFORM_ODS/REFRESH_MARTS/RUN_DQ`;
- уникальный индекс активной заявки;
- представление `etl.v_integration_run_request` (`dwh_app` — чтение).

Под задачи объекта эта таблица не подходит: исходный пакет обязателен, список задач закрыт ограничением. Это подтверждает Р1 = A — своя очередь объектов.

**Функции очереди CRM:**
- `app.integration_run_request_create/_cancel` (`dwh_app`) проверяют сессию функцией `app.integration_run_admin_session_user` и пишут аудит;
- `etl.integration_run_request_claim/_start/_success/_fail` (`dwh_etl`). Захват берёт сессионную рекомендательную блокировку на заявку. Если блокировка свободна, а заявка висит в `CLAIMED`/`RUNNING`, значит диспетчер умер — заявка переводится в `FAILED`.

**Решения для пакета 015:**
- **Р2 = A:** заявка объекта проверяется той же функцией `app.integration_run_admin_session_user`, поэтому права на запуск объекта по построению совпадают с «Run Control». Читать её текст не нужно, отдельного права не требуется. Коды прав `dwh_app` прочитать не может (нет `SELECT` на `app.permission`) — для Р2 = A они и не нужны.
- **Захват:** тот же способ восстановления зависших заявок через блокировку, но в отдельном пространстве ключей (двухаргументная блокировка `hashtext('dwh.object_run_request')`).
- **Права:** у `dwh_etl` есть прямые права на `etl.run_request` по правам схемы по умолчанию. Новая таблица снимает права по умолчанию явно (правило с 005).
- **Статус для вкладки «Объекты»:** `dwh_app` не читает `etl.object_run` и `etl.object_ods_run` (пакеты 010 и 012). Поэтому пакет 015 даёт ему представление статуса объектов только на чтение: версии, последние запуски STG и ODS, последняя ошибка, активная заявка.

**Integration Control** (`meta.v_integration_control_object`):
- показывает объекты 1–12 (`CRM_RETAIL`) и 16 (`OPERATION_COLLECTOR asan_pension_requests`) — все 13 зарегистрированных;
- данные строятся по старой модели: последний снимок структуры, контракты, маппинги `STG_TO_ODS` CRM, поля `source_object`;
- по объекту 16 он показывает пустые маппинги и не видит версий STG/ODS — это подтверждает решение удалить Integration Control (Р4).

## 8. Шаг 3 — пакет 015, E0 (11.11.2026, песочница)

Разрешение пользователя 11.11.2026.

**Устройство:**
- **`etl.object_run_request`** — заявки объектов: вид `RUN` / `CONTINUE_ODS` / `FULL_RERUN`; статус `QUEUED` → `CLAIMED` → `RUNNING` → `SUCCESS` / `FAILED` (или `CANCELLED` из `QUEUED`); кто и когда; ссылки на запуски STG и ODS; код результата и сообщение. Не больше одной активной заявки на объект (частичный уникальный индекс).
- **`app.integration_object_run_request_create`** (`dwh_app`):
  - сессия и права — `app.integration_run_admin_session_user`, как у заявок CRM (Р2 = A);
  - объект активен и не legacy, источник активен, конфигурация STG в силе `READY`;
  - для `CONTINUE_ODS` дополнительно: ODS в силе `READY`, последний STG `SUCCESS`, последний ODS после него `FAILED`;
  - нет активной заявки; запись в аудит.
- **`app.integration_object_run_request_cancel`** (`dwh_app`) — только `QUEUED`, с аудитом.
- **`etl.object_run_request_claim/_start/_finish`** (`dwh_etl`):
  - захват берёт сессионную блокировку на заявку (ключ `hashtext('dwh.object_run_request')`, номер заявки);
  - заявка `CLAIMED`/`RUNNING` со свободной блокировкой переводится в `FAILED` / `DISPATCHER_LOST`; блокировки своего сеанса пропускаются;
  - `finish` проверяет, что запуски STG и ODS принадлежат объекту и начаты после старта заявки, и снимает блокировку.
- **`etl.v_object_load_status`** (`SELECT` — только `dwh_app`) — все объекты:
  - признак legacy, версии и статусы STG и ODS, стратегия;
  - последний запуск STG и ODS со строками, кодом и текстом ошибки (`etl.error_log`);
  - можно ли «Продолжить»; последняя и активная заявка.
- **Права:** права по умолчанию снимаются явно — в песочнице были сняты с таблицы, последовательности и представления для `dwh_app`/`dwh_etl`. Очередь CRM и функции 008–014 не меняются.
- **Откат** отказывает, если заявки уже есть.
