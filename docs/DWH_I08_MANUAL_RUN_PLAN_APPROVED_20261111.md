## 1. Что получится в итоге (простыми словами)

В меню появляется раздел **«Загрузки»** (англ. «Data Loads», азерб. «Yükləmələr»). В нём собрано всё, что относится к работе загрузок, а не к их настройке (вкладки — раздел 1a).

**Вкладка «Объекты»:**
- по каждому объекту видно: версия STG и ODS в силе, последний запуск STG и ODS со статусом и временем, текст последней ошибки (разбор I13-08);
- кнопки:
  - **«Запустить»** — STG + ODS по стратегии опубликованной версии, как `run-object`;
  - **«Продолжить»** — только ODS. Доступна, если последний STG успешен, а ODS после него упал;
  - **«Заново полностью»** — STG с чтением всего объекта (разово, без смены версии) + ODS;
- кнопки доступны только для объекта в статусе `READY`: черновик и непроверенный объект запустить нельзя. Сохранение настроек ничего не запускает;
- нажатие создаёт **заявку**. Её выполняет диспетчер, тот же, что для CRM: `run_local_dwh.ps1 -Mode Run`. Статус заявки и ссылка на запуск видны в списке.

**«Откат»:** запуск объекта — одна транзакция на STG и одна на ODS. При ошибке ничего не записывается, поэтому откатывать нечего. «Продолжить» не повторяет успешный STG; «Заново» не пропускает строки.

## 2. Как устроено

- **Очередь объектов** (пакет 015): таблица заявок по объекту — вид запуска `RUN` / `CONTINUE_ODS` / `FULL_RERUN`, кто и когда, статус, ссылки на запуски STG и ODS. Функции:
  - создание заявки — для `dwh_app`: проверка сессии и прав, объект `READY`, не legacy, нет активной заявки по объекту, журнал аудита;
  - захват, начало, завершение заявки — для `dwh_etl`.

  Очередь CRM (`etl.integration_run_request`) и её функции не меняются (Р1).
- **Диспетчер** (`etl/src/run_request_dispatcher.py`) дополнительно берёт заявки объектов и вызывает `run_object` / `run_ods`. Учётные данные берутся из SecretStore, как в команде.
- **Движок:** параметр «читать всё» для «Заново полностью» — водяной знак версии не используется, после запуска записывается новый.
- **API:**
  - список объектов со статусом последних запусков;
  - создание и отмена заявки;
  - права проверяет БД (Р2).
- **UI:** раздел «Загрузки» и вкладка «Объекты» (список объединяет объекты CRM и новые); перенос существующих экранов без изменения их логики, удаление Integration Control, перенос «Validations» (Р4).

## 6. Шаг 2 — диагностика только на чтение (подготовлено 11.11.2026)

Скрипт `database/diagnostics/i08_step2_run_request.sql`, запуск через `database/tools/run_readonly_sql.ps1` (роль `dwh_app`, `transaction_read_only = on`, откат).

Что читает:
- структура очереди CRM `etl.*run_request*`: колонки, ограничения, триггеры, представления;
- функции очереди и проверки прав (`app`/`etl` `*run_request*`, `app.has_scoped_permission`, `app.integration_admin_session_user`): текст, `SECURITY DEFINER`, владелец, кто может выполнять;
- права `dwh_app` и `dwh_etl` на очередь;
- коды прав (`app.permission`);
- какие объекты показывает старый Integration Control (`meta.v_integration_control_object`) и все объекты источников (`meta.source_object`).

Таблицы без права чтения дают пометку, а не ошибку. Данных бизнеса скрипт не читает. Проверен в песочнице под `dwh_app` и под владельцем.
