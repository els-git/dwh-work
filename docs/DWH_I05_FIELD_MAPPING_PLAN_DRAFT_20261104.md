# I05 — универсальная модель полей и маппинга: план (ПРОЕКТ)

**Статус документа:** проект от 04.11.2026, ждёт утверждения пользователя.
**Статус задачи:** I05 `PLANNED`.
**Основа:** согласованный проект I02-02 (`docs/DWH_I02_02_INTEGRATION_TECHNICAL_DESIGN_APPROVED.md`, 21.10.2026) и продуктовые решения roadmap, раздел 1. Изменения относительно I02-02 вынесены в решения М1–М7 и применяются только после утверждения.

## 1. Что получится в итоге (простыми словами)

Для объекта нового источника (первый — `OPERATION_COLLECTOR` / `public.asan_pension_requests`) администратор в интерфейсе:

1. выбирает целевую таблицу DWH (существующую или заявляет новую — см. п. 4);
2. в двустороннем редакторе сопоставляет поля: слева — поля из снимка структуры источника (I04) и добавленные вручную, справа — поля целевой таблицы; справа предлагаются только совместимые по типу поля;
3. выбирает бизнес-ключ объекта (одно или несколько полей) — один раз для объекта;
4. для каждого поля задаёт правило записи (`AUTHORITATIVE` / `INSERT_ONLY` / `NO_WRITE`) и разрешение явного `NULL`;
5. нажимает «Проверить», затем «Опубликовать»: опубликованная версия неизменяема, объект получает статус `READY`;
6. если структура источника изменилась относительно опубликованной версии (новый снимок), система показывает расхождение (schema drift) и не даёт объекту оставаться `READY` без решения администратора.

Загрузка данных по этой конфигурации — **I06** (не входит в I05). Существующий контур `CRM_RETAIL` не меняется.

## 3. Решения для утверждения

| № | Вопрос | Варианты | Рекомендация |
|---|---|---|---|
| М1 | Единица версии и публикации | **A.** Версия на **объект** — объекты публикуются независимо; **B.** версия на **систему** целиком, как в I02-02 (ошибка одного объекта блокирует публикацию всех) | **A**: v1 работает на уровне отдельного объекта (решение 16.10.2026, раздел 1.5); проверка конфликтов владения полями (A08) всё равно выполняется по всем опубликованным объектам |
| М2 | Объём модели I02-02 в I05 | только то, что нужно для маппинга и публикации: версия объекта, цель, части ключа, правила полей, проекты изменений, результаты проверок; таблицы истории/присутствия (`integration_record_*`, `run_binding`) — в I06 | так; таблицы групп и профилей не создаются (профили отменены 03.11.2026) |
| М3 | Объект | использовать существующий `meta.source_object` для источников БД (как допускает I02-02); API/FILE-объекты — в I11/I12 | так |
| М4 | Целевая таблица | только существующие таблицы схем `stg`/`ods`; новая таблица или поле — проект изменения (М5) | так |
| М5 | Применение проекта изменения | backend формирует DDL-файл (`CREATE TABLE` / `ADD COLUMN`) с откатом и проверкой; применяется как пакет БД через E0 → E1 → E2 с разрешением пользователя; из UI DDL не выполняется | так |
| М6 | Типы | справочник нормализованных типов (`TEXT`, `INTEGER`, `BIGINT`, `NUMERIC(p,s)`, `BOOLEAN`, `DATE`, `TIMESTAMP`, `TIMESTAMPTZ`, `UUID`, `JSON`, `BYTES`) и матрица: например `INTEGER→BIGINT` безопасно, `BIGINT→INTEGER` условно, `TEXT→DATE` условно, `BOOLEAN→DATE` несовместимо; условные требуют подтверждения у поля | так |
| М7 | Снимок `CRM_RETAIL` из UI (I05-06) | **A.** Запретить снимок из UI для источников legacy-контура (есть `meta.column_contract`/`mapping_rule`), пока они не переведены в новую модель; **B.** разрешить после оценки влияния на `v_latest_source_structure` | **A**: просто и безопасно; CRM продолжает пользоваться своим `capture_source_metadata.py` |

## 5. Что не входит в I05

- Загрузка данных по конфигурации, история изменений, присутствие записей, FULL/INCREMENTAL — I06–I07.
- Запуски и расписания — I08–I09.
- Oracle, API, файлы — I10–I12 (справочник типов к ним готовится, но адаптеров нет).
- Перевод `CRM_RETAIL` в новую модель.
- Произвольные выражения преобразований (`DERIVED`); в I05 — прямое сопоставление и типовые конвертации из матрицы.

## 6. Риски

- Целевая таблица для `asan_pension_requests` ещё не существует: без шага 7 публикацию на ПК проверить нельзя.
- Структура `stg`/`ods` и legacy-каталогов проверяется на шаге 2; если она не позволяет решения М3/М4, план вернётся на согласование до шага 3.
