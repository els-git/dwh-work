## 1. Что получится в итоге (простыми словами)

У опубликованной версии объекта появляется **стратегия загрузки**:

- **FULL** — как сейчас: читается весь объект, запись по ключу (вставка / обновление / пропуск), удалений нет;
- **INCREMENTAL UPSERT** — читаются только новые и изменённые строки: по колонке даты изменения (или создания) с запасом назад (overlap), начиная с отметки последнего успешного запуска (watermark).

Для обеих стратегий:
1. повторный запуск того же набора не создаёт дублей и истории (уже есть с I06);
2. **старая версия строки не затирает новую**: если у строки в DWH дата изменения новее, чем пришла из источника, обновление пропускается;
3. **удаление — только по явному признаку** в данных источника (например, `is_deleted`); отсутствие строки в инкременте удалением не считается;
4. стратегия, колонки дат, overlap и признак удаления задаются в редакторе «Маппинг», проверяются и публикуются вместе с версией (менять — только новой версией).

## 3. Решения для утверждения

| № | Вопрос | Варианты | Рекомендация |
|---|---|---|---|
| Д1 | Где хранится стратегия | **A.** В версии конфигурации объекта (пакет 008: неизменяемая после публикации, входит в хеш); **B.** в существующем `meta.source_object.load_strategy` | **A**: `meta.source_object.load_strategy` использует CRM-контур; новая модель версионирует всё, что влияет на загрузку |
| Д2 | Где хранится watermark | **A.** В запуске объекта (`etl.object_run`: отметка «до» успешного запуска; следующий инкремент начинается от последней успешной минус overlap); **B.** существующая `etl.watermark` (по `job_id`) | **A**: `etl.watermark` — таблица CRM-контура; своя отметка в истории запусков проверяема и не смешивает контуры |
| Д3 | Отбор инкремента | Строки с `колонка изменения >= watermark − overlap` (включительно: равные отметки не теряются); overlap — минуты, по умолчанию 10; первый инкрементный запуск без watermark читает объект целиком (как FULL); предел 1 000 000 строк сохраняется | так |
| Д4 | «Старая версия не затирает новую» | Если в маппинге указана колонка изменения: строка с ключом, уже существующим в DWH, обновляется только при `значение источника >= значение в DWH`; иначе пропуск со счётчиком `stale`; без колонки изменения — как в I06 | так |
| Д5 | Удаление по признаку | **A.** «Мягкое» удаление: признак (например, `is_deleted`) — обычное поле маппинга, записывается в цель как значение; физически строки не удаляются; в истории — `UPDATE` поля признака; **B.** физическое удаление строки цели при признаке | **A**: STG сохраняет полную картину; физическое удаление необратимо и для STG не требуется; можно вернуться отдельным решением |
| Д6 | Отсутствие строки в FULL | В I07 ничего не делается (нет удаления и нет отметки «пропала»); контроль присутствия (MISSING/REAPPEARED из I02-02) — отдельная задача позже | так; при желании — новая задача с отдельным ID |
| Д7 | Объект приёмки | `asan_pension_requests`: INCREMENTAL по `created_at` (у таблицы нет колонки изменения) — подходит, только если заявки после создания **не меняются**; иначе приёмку INCREMENTAL провести на синтетическом объекте в песочнице, а `asan_pension_requests` оставить FULL | **ответ пользователя 05.11.2026:** строки после создания не меняются — INCREMENTAL по `created_at`, приёмка на `asan_pension_requests` |

## 6. Риски

- Если строки источника меняются без изменения колонки даты, INCREMENTAL их не увидит — это свойство источника; для таких объектов — FULL.
- Запоздавшие изменения старше overlap инкремент не увидит; страховка — периодический FULL (вручную до I09).
- Часовые пояса: колонка `timestamp` без пояса сравнивается как есть; смешение поясов между запусками источника — риск источника.
