## 1. Решение пользователя (17.11.2026)

Вместо перевода старого контура по частям:
- **всё, что связано со старым CRM, удаляется**: данные тестовые, подстраиваться под старое не нужно;
- **CRM подключается заново** как обычный источник по текущей логике:
  - объекты и маппинг в интерфейсе;
  - STG → ODS;
  - заявки «Загрузки → Объекты»;
  - витрина в конструкторе.

Дополнительные решения:
- **Страница «Отчётность → Розничные заявки» удаляется** (вариант B): отчёты по CRM — через ИИ-помощника и сохранённые отчёты на новой витрине.
- **Данные старого контура удаляются без отдельной выгрузки.** Перед каждым SQL-пакетом сервер делает копию базы `pre-<пакет>`.
- **Подключение `CRM_RETAIL` сохраняется** — адрес и учётная запись в настройках подключения и SecretStore. Блокировка М7 (`meta.source_is_legacy`) определяется наличием контрактов и сопоставлений CRM: после их удаления `CRM_RETAIL` становится обычным источником.

**Что теряется (согласовано):**
- старые снимки (заявки, ODS, история версий витрины);
- 14 правил качества CRM — общие проверки появятся в I13;
- журналы старых запусков CRM.

## 2. Критерии `DONE`

1. В базе и коде нет старого контура CRM:
   - таблицы, функции и представления `stg/ods/dm` CRM;
   - контракты и сопоставления, задания и правила DQ CRM;
   - команды снимков и задачи старой очереди;
   - вкладки «Управление запусками CRM», контрактов и сопоставлений, страница «Розничные заявки».
2. `CRM_RETAIL` настроен в интерфейсе как обычный источник; нужные таблицы загружаются заявками объектов STG → ODS.
3. Витрина CRM построена конструктором. ИИ-помощник строит по ней отчёты, их можно сохранить в «Отчётность».
4. Регрессия: `OPERATION_COLLECTOR`, витрина `pension_request`, помощник, сохранённые отчёты, вход и администрирование работают.
5. Приёмка на сервере и подтверждение пользователя.

### 9.1. Как работает

`app.object_table_publish(сессия, 'LOAD' | 'ODS', объект, ревизия черновика, подтверждение)` в одной транзакции:
1. Проверяет, что черновик не изменён, и что объект не загружается: блокировки запусков 010/012 и активные заявки 015.
2. Строит план по полям черновика. Текст DDL строит сама база; типы — из белого списка, имена — проверенные 008/012, в кавычках `%I`.
3. Выполняет план:
   - нет таблицы — `CREATE TABLE` с `NOT NULL` и `PRIMARY KEY` по ключу;
   - новые поля — `ADD COLUMN`, без подтверждения;
   - удаление поля, смена типа, смена ключа — только с подтверждением. Без него ответ `NEEDS_CONFIRM` и ничего не меняется;
   - смена типа отменяется, если изменилось бы хотя бы одно значение (сверка «туда и обратно»; текст в другой тип — ошибкой приведения);
   - поле, которое пишет другой объект, остаётся (`KEPT`); смена его типа и смена ключа общей таблицы запрещены.
4. Публикует версию прежними функциями 008/012. Их проверки (валидация, поля, ключ, AUTHORITATIVE) остаются.
5. Пишет `INTEGRATION_OBJECT_TABLE_CHANGED` в журнал безопасности: изменения, затронутые настройки, SHA-256 текста DDL.

`app.object_table_preview` — тот же план без изменений.

**Что затронуто изменением:**
- у таблицы STG — действующие настройки ODS, которые читают поле;
- у таблицы ODS — версии витрин (опубликованные и черновики), которые читают поле в источниках, полях, фильтрах и связях.

**Права:**
- `dwh_app` — только 2 функции `app.object_table_*`;
- меняются только таблицы `stg`/`ods` владельца функций (`dwh_admin`);
- новые таблицы получают права по умолчанию, как таблицы пакетов 009/013: `dwh_etl` читает и пишет, `dwh_app` — нет.

### 9.2. API и интерфейс

**API:**

- новое предупреждение `TARGET_COLUMN_NOT_IN_VERSION`;
- `…/config/publish` и `…/ods-config/publish` принимают `confirm`;
- новые маршруты `GET …/config/table-plan` и `…/ods-config/table-plan`.

**Интерфейс:**

### 9.12. Широкие таблицы: ошибка STG `DATABASE_ERROR (SQLSTATE unknown)` (18.11.2026)

**Причина** (воспроизведена в песочнице):
- строки пишутся во временную таблицу STG пачками по 1000;
- каждое значение — отдельный параметр запроса, а протокол PostgreSQL допускает не больше 65 535 параметров;
- у таблиц больше 65 полей, то есть 1000 × 66 и больше — сверх предела;
- запрос отклоняет сам драйвер (`number of parameters must be between 0 and 65535`), поэтому SQLSTATE нет.

**Исправление** (`etl/src/run_object.py`):
- размер пачки — `stage_batch_rows`: строки × поля ≤ 65 535 (для 100 полей — 655 строк);
- если у ошибки нет SQLSTATE, в сообщении указан класс ошибки драйвера: `SQLSTATE unknown, OperationalError`. Текст ошибки не выводится, в нём могут быть значения.

**Проверки:** тесты 538 OK. На настоящем PostgreSQL песочницы таблица из 120 полей и 2500 строк загружена целиком.
