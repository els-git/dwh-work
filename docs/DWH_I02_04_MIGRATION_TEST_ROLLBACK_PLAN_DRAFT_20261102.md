## 2. Правила миграций

1. Каждый пакет: `database/migrations/NNN_name.sql` (применение), `NNN_name.down.sql` (откат), `database/checks/NNN_name_check.sql` (read-only проверка каталога), `database/tests/NNN_name_test.sql` (поведенческий тест, всегда `ROLLBACK`).
2. Применение только целиком в одной транзакции: `psql -1 -v ON_ERROR_STOP=1 -f NNN_name.sql`.
3. Уже применённый файл не редактируется; исправления — новым пакетом.
4. **Откат объектов с данными журнала:** `.down.sql` отказывается работать, если в объектах есть строки (A10 — история аудита сохраняется). Такой откат возможен только из резервной копии и только по отдельному решению пользователя.
5. Проверки из `database/checks/` — только `SELECT` по `pg_catalog` и счётчики строк; запуск в транзакции `read only`.

| Среда | Что это | Что разрешено |

| E2 | Рабочая `dwh` | Только после PASS в E1, резервной копии и **отдельного разрешения** на конкретный пакет |

### Процедура пакета

1. E0: применение → check → test → down → check absent → повторное применение; снимок каталога после down равен исходному.
2. E1: резервная копия `dwh` (`pg_dump -Fc` + `pg_dumpall --globals-only`, SHA256 в `runtime/backup`), восстановление в `dwh_i02_04_test`, затем те же шаги, что в E0.
3. E2 (по разрешению): новая резервная копия → применение → check `PASS` → фиксация в roadmap.
4. Сбой на любом шаге — STOP, откат транзакции, отчёт; повторять только после анализа.

## 5. Пакет M-SS02 — защита журнала и один ACTIVE секрет на профиль

**Решение пользователя 02.11.2026 (В1):** для источника-БД один секрет; у API-источника (например, «Микросервис») у каждого сервиса свои учётные данные. Это совпадает с утверждённой моделью I02-02: источник → N профилей (`integration_profile`, `UNIQUE(source_system_id, profile_code)`), у профиля свой `secret_ref`. Правило: **не более одной `ACTIVE` привязки на (`source_system_id`, `profile_code`)**. Контракт доступа `SOURCE_SYSTEM_<id>` не меняется.

Файлы:
- `database/migrations/002_secret_store_hardening.sql`:
  - G1: функция `reject_truncate()` и триггеры `BEFORE TRUNCATE` на обе таблицы;
  - G2: колонка `binding.profile_code` (формат `^[A-Z][A-Z0-9_]{0,63}$`, как у кодов модулей и ролей), ограничение «`ACTIVE` требует профиль», частичный уникальный индекс `binding_one_active_per_profile`, триггер неизменности профиля.
- `002_secret_store_hardening.down.sql` — возврат к состоянию M-SS01; отказывает, если хотя бы у одной привязки задан `profile_code`.
- `database/checks/002_secret_store_hardening_check.sql` и `..._check_readonly.ps1` — 14 проверок каталога; после применения 002 заменяют проверку 001 (её счётчики объектов больше не совпадут).
- `database/tests/002_secret_store_hardening_test.sql` — T01–T24 (базовые правила, теперь с профилем) и N01–N13 (TRUNCATE, профиль, REPLACE), всё с `ROLLBACK`.

Строки, созданные до 002, получают `profile_code = NULL` и не изменяются: `PENDING` нельзя перевести в `ACTIVE`, отозвать можно.

**Факт E1 от 02.11.2026 (копия `dwh`, вывод пользователя):** в `secret_store` 3 привязки источника `CRM_RETAIL` (id 1):
- `PENDING` от 28.10 16:04, `OUTCOME=FAILED`;
- `ACTIVE` от 28.10 17:26;
- `ACTIVE` от 29.10 14:55.

Журнал — 6 событий. Обе `ACTIVE` записи **не отражены в журнале roadmap**; это расхождение документации (G8). Первая версия 002 на этих данных остановилась бы: защитная проверка E1 сработала до применения.

**Решение (вариант B):** правило `binding_active_requires_profile` добавляется как `NOT VALID`. Оно проверяет все новые и изменяемые записи, а существующие `ACTIVE` без профиля сохраняет без изменений. Две такие записи на `CRM_RETAIL` по профилю использовать нельзя. Отзывать их — только аудируемой операцией после M-SS03, потому что журнал пока не умеет записывать REVOKE (G3). Отозвать их в самой миграции нельзя: изменение прошло бы без аудита (A05, A10).

**Результат в E0 (02.11.2026, PostgreSQL 16.15, с имитацией строк от 28.10: ATTEMPT, PENDING, OUTCOME=FAILED):**

**Порядок применения:**
1. E1 (разрешено пользователем 02.11.2026): `database/run_002_e1_test.ps1` на сервере 5433. Скрипт делает резервную копию `dwh` в `runtime/backup` (`pg_dump -Fc`, globals без паролей ролей, SHA256), создаёт новую БД `dwh_i02_04_test` и восстанавливает в неё копию.
