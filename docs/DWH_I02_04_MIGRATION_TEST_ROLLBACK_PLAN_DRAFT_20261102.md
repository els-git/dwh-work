## 2. Правила миграций

1. Каждый пакет: `database/migrations/NNN_name.sql` (применение), `NNN_name.down.sql` (откат), `database/checks/NNN_name_check.sql` (read-only проверка каталога), `database/tests/NNN_name_test.sql` (поведенческий тест, всегда `ROLLBACK`).
2. Применение только целиком в одной транзакции: `psql -1 -v ON_ERROR_STOP=1 -f NNN_name.sql`.
3. Уже применённый файл не редактируется; исправления — новым пакетом.
4. **Откат объектов с данными журнала:** `.down.sql` отказывается работать, если в объектах есть строки (A10 — история аудита сохраняется). Такой откат возможен только из резервной копии и только по отдельному решению пользователя.
5. Проверки из `database/checks/` — только `SELECT` по `pg_catalog` и счётчики строк; запуск в транзакции `read only`.

### Среды

| Среда | Что это | Что разрешено |
|---|---|---|
| E0 | Песочница Claude, PostgreSQL 16, заглушка `meta.source_system` | Любые испытания; не заменяет E1 |
| E1 | Изолированная БД `dwh_i02_04_test` на PostgreSQL 17.11, восстановленная из свежей резервной копии `dwh` | Применение, тест, откат, сравнение снимков |
| E2 | Рабочая `dwh` | Только после PASS в E1, резервной копии и **отдельного разрешения** на конкретный пакет |

### Процедура пакета

1. E0: применение → check → test → down → check absent → повторное применение; снимок каталога после down равен исходному.
2. E1: резервная копия `dwh` (`pg_dump -Fc` + `pg_dumpall --globals-only`, SHA256 в `runtime/backup`), восстановление в `dwh_i02_04_test`, затем те же шаги, что в E0.
3. E2 (по разрешению): новая резервная копия → применение → check `PASS` → фиксация в roadmap.
4. Сбой на любом шаге — STOP, откат транзакции, отчёт; повторять только после анализа.

**Результат в E0 (02.11.2026, PostgreSQL 16.15):** применение OK; check 11/11 PASS; test 24/24 PASS, `ALL_TESTS_PASS`, после теста 0 строк; down на пустой схеме OK, check absent PASS; down при 1 строке журнала — `ROLLBACK REFUSED`, схема и строка сохранены; повторное применение поверх существующей схемы отклонено; снимок каталога после down совпал с исходным (8 → 38 → 8 объектов, md5 равен).

## 4. Находки review существующей схемы

| ID | Находка | Подтверждение | Требование |
|---|---|---|---|
| G1 | `TRUNCATE` обходит построчные триггеры append-only: владелец может стереть журнал | Тест E0: после `TRUNCATE` 0 строк | A10, S04–S05 |
| G2 | Для одного источника допускается несколько `ACTIVE` привязок | Тест E0: 2 `ACTIVE` на один источник | S06; модель REPLACE не определена |
| G3 | Журнал описывает только CREATE: `operation_id = create_operation_id`, нет типа операции; REPLACE, REVOKE и служебный READ не журналируются, REVOKE не оставляет записи | Чтение DDL | A05, A10, E09 |
| G4 | Нет поля проверенного актора | Чтение DDL | A05 |
| G5 | Нет `key_id` версии мастер-ключа в `binding` | Чтение DDL | K07–K08 (ротация) |
| G6 | Ни одной роли не выданы права и нет функций записи: писать может только владелец `dwh_admin` | Чтение DDL, комментарий в файле | E01, E06, минимальные привилегии |
| G7 | SQL изменения `app.resource` от 26.10.2026 не версионирован | Нет файла в git | Воспроизводимость, откат |
