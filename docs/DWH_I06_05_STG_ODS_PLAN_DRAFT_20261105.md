## 1. Что получится в итоге (простыми словами)

**I13-07 — DWH ничего не меняет в источниках.**
1. Каждое подключение DWH к базе источника — из UI (проверка, объекты, снимок), из `run-object` и из CRM ETL — открывается через **один общий шлюз**.
2. Шлюз выполняет только чтение, иначе останавливает работу до первого запроса.
3. Для будущих источников API (I11) тот же шлюз разрешает только `GET`. Файлы (I12) открываются только на чтение.

**I06-05 — данные из STG переносятся в ODS.**
1. У объекта появляется вторая настройка: «ODS» — какие поля STG-таблицы, в какую таблицу `ods` и с каким преобразованием из белого списка.
2. Произвольный SQL пользователь не пишет.
3. После успешной загрузки в STG тот же запуск переносит строки в ODS по ключу.
4. Повторный запуск дублей не создаёт.
5. История «было/стало» ведётся, как в STG.

Под «исходящими запросами» здесь понимаются запросы DWH **к внешним источникам**. Свою базу `dwh` (STG, ODS, журналы) DWH по-прежнему пишет — это его работа.

## 3. Где ставить запрет записи (рекомендация по требованию пользователя)

Запрет записи держится на трёх уровнях: каждый следующий страхует предыдущий. Абсолютную гарантию даёт только уровень 3; уровни 1 и 2 — в коде DWH, и их делаю я.

| Уровень | Что делает | Что защищает | Ограничение |
|---|---|---|---|
| **1. Шлюз в коде DWH** (`source_gateway`, общий для backend и ETL) | Единственная функция открытия соединения с источником. Сервер получает при подключении `default_transaction_read_only=on`, драйвер — режим `read_only`. До первого запроса шлюз проверяет `SHOW transaction_read_only` = `on`, иначе отказ `SOURCE_NOT_READ_ONLY`. Курсор шлюза пропускает только чтение: `SELECT` / `WITH … SELECT`, `DECLARE … CURSOR FOR SELECT`, `FETCH`, `CLOSE`, `SHOW`, `COMMIT`, `ROLLBACK`. Отказывает при `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `TRUNCATE`, `COPY … FROM`, DDL, `GRANT`, `CALL`, `DO`, `SET … READ WRITE`, `LOCK`, `VACUUM`. | Ошибку в коде DWH | Это защита от ошибок нашего кода, не от злоумышленника с доступом к серверу DWH |
| **2. Сервер источника в режиме чтения** (часть уровня 1) | PostgreSQL сам запрещает запись в транзакции только для чтения: изменение таблиц, `nextval`, вызов изменяющих функций внутри `SELECT` | Запрос, который проскочил фильтр текста (например, `SELECT` функции, которая пишет) | Транзакцию может вернуть в режим записи только явная команда, а её отсекает фильтр уровня 1 |
| **3. Учётная запись источника только на чтение** (I13-06, делает владелец источника) | У учётной записи DWH в источнике есть только `SELECT` (и `USAGE` на схемы) | Всё, включая ошибку в самом DWH | Не в нашей власти; для CRM `vtb` сейчас есть права записи (находка I04) |

**Тест-«сторож»:** unit-тест в наборе проверяет, что прямые вызовы `psycopg.connect` к источникам и HTTP-клиенты есть только в шлюзе. Если позже кто-то добавит обход, тесты упадут.

**Почему не прокси или сеть:** фильтр протокола PostgreSQL на прокси (pgbouncer и подобные) не разбирает SQL. Он добавил бы ещё одну точку отказа, а на пути к источнику `OPERATION_COLLECTOR` уже стоит пул соединений. Шлюз в коде плюс права учётной записи проще и надёжнее.

**Сейчас (read-only просмотр кода 05.11.2026):** к источникам ведут три пути.
1. Backend `postgres_connector.py`: `default_transaction_read_only=on` и проверка `SHOW` — **уже есть**.
2. `run-object` (`etl/src/run_object.py`, `source_connect`): только режим драйвера, без проверки сервером.
3. CRM ETL (`etl/src/dwh/db.py`, `connect_readonly`): только режим драйвера; `check-crm` печатает `transaction readonly: on`.

Фильтра команд нет ни в одном пути. Шлюз сводит все три пути к одному.

## 6. Что не входит

- Кнопка запуска и «Продолжить» / «Выполнить заново» — I08; расписание — I09.
- Перенос в ODS по изменениям (инкремент из STG) — при необходимости новая задача.
- Объединение нескольких объектов в одну таблицу ODS, справочники, связи между таблицами — позже, отдельным решением.
- Права учётных записей источников (уровень 3) — I13-06, решение владельцев источников.
- HTTP-шлюз для API — код вместе с I11, правило (Г3) — сейчас.

## 7. Риски

- Фильтр команд разбирает текст запроса. Он строже, чем нужно, и может отказать новой законной форме чтения. Тогда — точечное расширение списка по решению пользователя, без отключения проверки.
- Пул соединений источника может не принять параметр подключения `options`. Сейчас проверка подключения в UI с ним работает (`OPERATION_COLLECTOR` и `CRM_RETAIL` — `READY`). Если путь CRM ETL откажет, шлюз включит режим чтения командой `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` и всё равно проверит `SHOW`.
- Ошибка преобразования одной строки останавливает шаг ODS целиком (без частичной записи). Код ошибки и колонка — в журнале.
