# I17-10 — Доработка ИИ-помощника: разбор ошибок загрузок, память диалога, сворачивание

<sub>Проект плана · 18.11.2026 · ждёт утверждения пользователя (решения Р1–Р7)</sub>

## 1. Требование пользователя (18.11.2026)

1. **Разбор ошибок загрузок** по журналам ошибок и запусков — коротко, по существу, быстрее.
2. **Память диалога** — последние 10 сообщений, включая контекст снимка экрана.
3. **Сворачивание чата вместо закрытия:** ответ готовится в фоне, о готовности — всплывающее уведомление; значок «×» заменён значком сворачивания.

## 2. Что есть сейчас (проверено по коду 18.11.2026)

- Помощник (`backend/src/dwh_api/ai_assistant.py`): `/api/ai/help` (справка, снимок экрана) и `/api/ai/report` (отчёт по `dm`). Каждый вопрос — **без истории**: модель получает только текущий вопрос.
- Модель одна (`dwh-llm`, контекст 16 384 токена) и отвечает на один вопрос за раз — длинная подсказка = медленный ответ.
- Ошибки загрузок `dwh_app` уже читает: `etl.v_integration_error` (экран «Загрузки → Ошибки и история», `/api/etl/errors`, право `ETL_VIEW`), состояние объектов `etl.v_object_load_status`, витрин `etl.v_dm_mart_status`. Ошибки содержат код, поле, число строк, до 5 значений (`bad_value`) и ключи (`diagnostic_context`, I13-08). **Пакет БД для чтения не нужен.**
- Окно чата (`frontend/src/AiAssistantPanel.tsx`) висит на всех экранах; «×» прячет окно, но запрос продолжает идти — ответ приходит незаметно для пользователя.
- Журнал помощника `app.ai_request_log`: виды `HELP`, `REPORT`, `SAVED_REPORT`, `MART_VIEW` (ограничение в БД — новый вид требует пакета).

## 3. Решения (на утверждение)

| № | Вопрос | Рекомендация | Другой вариант |
|---|---|---|---|
| Р1 | Как разбирать ошибку | **A** — не пересказ экрана, а **диагноз** (раздел 3.1): сервер собирает досье фактов об ошибке и даёт модели вместе с базой знаний причин по кодам; модель пишет, что случилось, где именно (источник → таблица → столбец → строки), почему (с доказательствами из досье), что сделать по шагам и как проверить результат. Пока модель пишет — сразу видна короткая карточка «что случилось» без модели | B — только краткое объяснение кода (быстрее, но без диагноза) |
| Р2 | Откуда начинается разбор | **A** — кнопка «Разобрать с помощником» у ошибки в «Загрузки → Ошибки и история» и у объекта / витрины с последним запуском `FAILED` («Объекты», «Витрины»); чат открывается с разбором | B — ещё и свободный вопрос в чате «почему упал applicant?» (нужно угадывать объект по тексту — менее надёжно) |
| Р3 | Права | Разбор доступен при `AI_ASSISTANT_USE` **и** `ETL_VIEW` (то же право, что экран ошибок). Клиент передаёт только номер ошибки / объекта; текст ошибки сервер читает сам под `dwh_app` | — |
| Р4 | Какие факты получает модель | **A** — досье (раздел 3.1), включая значения и ключи из ошибки: это доказательства для диагноза. Модель — только на сервере (`127.0.0.1`); в журнал помощника досье и значения не пишутся (только номер ошибки) | B — без значений (диагноз о формате данных станет догадкой) |
| Р5 | Память диалога | **A** — история хранится в браузере (на вкладке) и отправляется с вопросом: последние **10 сообщений** (вопросы и ответы, каждое до 2 000 символов); сервер обрезает и сам не хранит. Снимок экрана **не пересылается заново** — в памяти остаётся ответ модели о нём (повторная передача картинки замедляет каждый ответ). Справка ищет разделы по текущему и предыдущему вопросу; отчёт получает прежний вопрос и прежний SQL («а теперь по месяцам»). Кнопка «Новый диалог» очищает память | B — история на сервере (таблица, пакет БД, доступна с другого компьютера) |
| Р6 | Сворачивание и уведомление | **A** — «×» заменяется на «—» (свернуть); запрос продолжается; при готовности, если окно свёрнуто, — всплывающее уведомление на странице «Ответ готов — открыть» и точка на кнопке «Помощник»; «Стоп» работает и в свёрнутом виде через уведомление | B — ещё системное уведомление браузера (нужно разрешение браузера; на HTTPS с временным сертификатом может не работать) |
| Р7 | Журнал разборов | **A** — без пакета БД: разбор пишется видом `HELP`, в сообщении — «разбор ошибки №…» / «объект …» | B — новый вид `LOAD_ERROR` (пакет 024: замена ограничения вида, E0/E1/E2) |

### 3.1. Как помощник ставит диагноз (замечание пользователя 18.11.2026: «не повторять экран, а анализировать по существу»)

Так же, как разбор ошибок шёл в этом проекте вручную: сначала факты, потом вывод. Сервер сам (под `dwh_app`, только чтение, без запросов модели к базе) собирает **досье**:

| Факт | Откуда | Зачем |
|---|---|---|
| Ошибка: код, `SQLSTATE`, сообщение, шаг (STG / ODS / витрина), поле, правило, число строк, значения с количеством, ключи, номер порции | `etl.v_integration_error`, журнал витрин | что именно и на каких строках |
| История объекта: последний успешный запуск, сколько запусков подряд падают, с какой версии маппинга | `etl.v_object_load_status`, запуски | «работало вчера, сломалось после публикации версии 4» или «никогда не работало» |
| Поле целиком: тип в источнике (снимок), тип STG/ODS, преобразование и формат (`DD.MM.YYYY` …), ключ ли это | версии маппинга STG/ODS, снимок источника | «в поле `birth_date` формат `DD.MM.YYYY`, а в 4 строках текст `birthD`» |
| Структура: изменилась ли таблица источника после публикации | снимки структуры (drift) | «в источнике удалён столбец `x`» |
| Подключение: последняя проверка, её результат и время; источник и хост | `meta.source_connection` | «источник не отвечает с 13.11; DWH-сервер не допущен в `pg_hba.conf`» |
| Витрина: тип (конструктор / SQL), таблицы и ключ, текст запроса | версии витрин | «ключ `client_id` повторяется в `ods.x`: 1 ×2» |

**База знаний причин** — по каждому коду (`SOURCE_NO_RESPONSE`, `SOURCE_CONNECT_FAILED`, `TYPE_CONVERSION`, `KEY_NULL`, `KEY_DUPLICATE`, `SCHEMA_DRIFT`, `TARGET_DRIFT`, `DISK_SPACE`, `LOCK_TIMEOUT`, `TIMEOUT`, `DM_KEY_*`, `DM_SQL_*`, `DATABASE_ERROR` по `SQLSTATE` …): типичные причины, как их отличить по фактам досье, что делать и кто это делает (пользователь в интерфейсе / владелец источника / администратор сервера). Наполняется опытом этого проекта (например: ответ источника теряется в сети → `SOURCE_NO_RESPONSE`; маска `99.99.9999` — корректные даты, ломают только строки с текстом).

**Ответ помощника** — строго по фактам: «Что случилось», «Где» (источник → таблица → столбец → строки/ключи), «Почему» (причина и на каком факте основан вывод; если фактов не хватает — так и сказать, без выдумки), «Что сделать» по шагам с названиями экранов и кнопок, «Как проверить». Ответ строится по досье, поэтому модель не может «увидеть» данные сверх того, что записала ошибка; новых запросов к источнику помощник не делает (возможная проверка подключения — только кнопкой пользователя, через шлюз только на чтение).

**Насколько реализуемо:** для известных классов ошибок (подключение, формат и типы, пустой/повторяющийся ключ, изменение структуры, место, блокировки, ключи и запросы витрин) — да, диагноз будет конкретным, потому что факты собирает сервер, а не модель. Для редких ошибок базы (`DATABASE_ERROR` с неизвестным `SQLSTATE`) — объяснение по коду и сообщению с пометкой «требует проверки администратором». Время: досье — доли секунды, карточка — сразу, текст модели — около 1–2 мин (подсказка длиннее, чем у справки).

## 4. Шаги до `DONE` (при рекомендациях — без пакета БД)

| Шаг | Содержание | Режим |
|---|---|---|
| 1 | Утверждение плана (Р1–Р7) | решение пользователя |
| 2 | Песочница: сбор досье и база знаний причин (раздел 3.1), карточка (ru/az/en), API разбора `POST /api/ai/load-error` (по `error_id` / объекту / витрине), память диалога в `/api/ai/help` и `/api/ai/report`, кнопки «Разобрать с помощником», сворачивание и уведомление, «Новый диалог»; справка; тесты, сквозная проверка, браузер | песочница |
| 3 | Выпуск, приёмка на сервере: разбор нескольких настоящих ошибок из «Ошибок и истории» (подключение, формат, ключ — по тому, что есть в журнале): диагноз называет таблицу, столбец, строки, причину и шаги; уточняющий вопрос по справке и по отчёту с памятью; снимок экрана и вопрос о нём следующим сообщением; сворачивание во время ответа и уведомление; реестр | сервер |
| 4 | Подтверждение пользователя — I17-10 `DONE` | решение пользователя |

При Р7 = B добавляется пакет 024 (E0 → E1 → E2, каждый переход с разрешения) между шагами 2 и 3.

## 5. Не входит

Автоматическое исправление ошибок и перезапуск загрузок помощником; память между вкладками и компьютерами (при Р5 = A); голос; разбор ошибок источников, которых нет в журнале DWH.
