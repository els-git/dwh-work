# I12 — источник «файлы JSON/XML» (проект плана)

<sub>24.11.2026 · `IN_PROGRESS` (выбрана пользователем 24.11.2026) · решения Ф1–Ф10 ждут утверждения.</sub>

## 1. Задача (roadmap I12-01…I12-06)

Загружать данные из файлов JSON/XML, которые появляются в папке: снимок целиком (FULL — последний готовый файл) или все новые файлы по порядку (INCREMENTAL). Дата файла берётся из имени (`YYYY-MM-DD_HHMMSS`), а не из времени файла в ОС. Каждый файл учитывается в реестре (контрольная сумма, результат, попытки), повторно успешно обработанный файл не применяется. Чтение безопасное: только разрешённая папка, предел размера и вложенности, без внешних сущностей XML (XXE).

Утверждённые ранее правила, которые план не меняет:
- I02-02, «Защита истории», п. 6: для FILE актуальность — дата внутри имени файла; файл с той же или более ранней датой может только **добавлять отсутствующие ключи**, существующие записи не обновляет;
- I02-03, «Безопасность подключений», п. 7: отдельные минимальные права для FILE;
- I03: у источника вида `FILE` — одно подключение (`meta.source_connection.source_kind = 'FILE'` уже предусмотрен пакетом 005).

## 2. Что уже есть в коде

- Разбор ответа JSON/XML, путь к записям, раскладка вложенных полей `a.b`, подбор типов, проверка структуры и «Сохранить структуру» — `api_request.py` / вкладка «HTTP-запрос» (I11). Для файлов используется тот же разбор.
- Движок загрузки STG → ODS, история, инкремент, `SOURCE_DRIFT`, заявки, расписания, диспетчер (I06–I09, I11).
- Вид подключения `FILE` в `meta.source_connection` (005) без реализации.

## 3. Решения

| № | Вопрос | Рекомендация | Другой вариант |
|---|---|---|---|
| Ф1 | Откуда DWH берёт файлы | **A** — из папки на сервере DWH: корень `/srv/dwh/files`, у источника — своя подпапка (`/srv/dwh/files/<код источника>`). Сетевую папку администраторы подключают туда только на чтение (или файлы кладут `scp`); пароль от сетевой папки хранится у ОС, не в DWH | B — DWH сам забирает файлы по SFTP / SMB (нужны новые библиотеки и секреты) |
| Ф2 | Что задаёт пользователь | **A** — у источника: подпапка (только имя внутри корня, без `..` и абсолютных путей); у объекта: маска имени (`services_*.json`), шаблон даты в имени (по умолчанию `YYYY-MM-DD_HHMMSS`), формат, путь к записям | B — полный путь к файлу у объекта |
| Ф3 | Форматы | **A** — JSON (массив или путь к массиву), JSON Lines (строка — запись), XML (путь до элемента записи); кодировка UTF-8 (с BOM или без) | B — только JSON и XML |
| Ф4 | Когда файл «готов» | **A** — размер и время изменения не менялись 60 секунд (настройка объекта); если поставщик кладёт рядом файл-метку `<имя>.done` — можно требовать её (флажок) | B — только метка `.done` |
| Ф5 | FULL и INCREMENTAL | **A** — FULL: последний готовый файл по дате в имени; INCREMENTAL: все готовые необработанные файлы по возрастанию даты, каждый — отдельным шагом с записью в реестр; файл с датой не новее уже применённого — только добавление отсутствующих ключей (правило I02-02 п. 6) | B — опоздавшие файлы пропускать с предупреждением |
| Ф6 | Реестр файлов | **A** — новая таблица (пакет 034): объект, имя, размер, SHA-256, дата из имени, статус (`LOADED` / `FAILED` / `SKIPPED_DUPLICATE` / `SKIPPED_NO_DATE` / `LATE_INSERT_ONLY`), запуск, попытки, ошибка; файл с той же суммой второй раз не применяется; упавший файл повторяется следующим запуском | B — без реестра, только журнал запусков |
| Ф7 | Что делать с файлом после загрузки | **A** — ничего: DWH только читает (не удаляет и не переносит); хранение и очистка — у поставщика/администраторов | B — переносить в `processed/` (нужны права записи) |
| Ф8 | Защита чтения | **A** — путь проверяется после разворота ссылок (только внутри корня), предел размера файла (по умолчанию 200 МБ, `DWH_FILE_MAX_BYTES`) и вложенности (64), XML с `DOCTYPE`/`ENTITY` отклоняется (`FILE_XML_DTD_FORBIDDEN`), сторож-тест: к файлам обращается только новый модуль `file_gateway.py` | B — без предела размера |
| Ф9 | Структура и ручные поля (I12-06) | **A** — «Проверить файл» читает последний готовый файл и предлагает колонки и типы (как у API); можно добавить поле вручную по пути (`a.b.c`) с типом — для полей, которых нет в образце | B — только автоматическая структура |
| Ф10 | На чём проверяем | **A** — новая задача I12-07: инструмент `tools/server/dwh_test_files.py` кладёт в `/srv/dwh/files/PV_FILES/` снимки `public.services` (JSON, JSON Lines, XML) с датой в имени и отдельные «плохие» файлы (битый, без даты, с DTD, слишком большой) — как тестовый сервис I11-05 | B — ждать настоящий источник файлов |

Ф10 = A добавляет задачу **I12-07** (ID — с вашего согласия).

## 4. Шаги до `DONE`

1. **Утверждение** Ф1–Ф10 (и I12-07) и ответ: есть ли уже настоящий поставщик файлов (откуда, как часто, формат, примерный размер).
2. **Опись на сервере** (только чтение): свободное место, есть ли `/srv/dwh/files`, под кем работают диспетчер и API, точки монтирования.
3. **Песочница:** пакет 034 (вид объекта `FILE`, настройки файла в версии объекта, реестр файлов, функции для `dwh_app`/`dwh_etl`, откат), E0; `file_gateway.py`, разбор файлов (общий с API), ветка `FILE` в движке, API и вкладка «Файлы» в «Маппинге», `dwh_test_files.py`, справка, `DWH_ENGINES.md`; тесты, сборка, ESLint 0/0, браузер, сквозная проверка.
4. **Выпуск, E1 и E2 пакета 034** (каждый — с разрешения).
5. **Подготовка папки на сервере**: `/srv/dwh/files/PV_FILES` (владелец — администратор, `dwh` только читает), тестовые файлы.
6. **Приёмка:** FULL — последний файл; INCREMENTAL — три файла по порядку, повтор без изменений, файл-дубликат пропущен, опоздавший файл только добавляет ключи, файл без даты и битый — понятные ошибки, файл с DTD и слишком большой — отказ, путь вне корня — отказ, запуск по расписанию. Реестр; подтверждение — `DONE`.

## 5. Не входит

SFTP / SMB / FTP-клиенты в DWH (Ф1 = B), CSV и Excel, архивы (zip/gz), запись или перенос файлов, файлы с пользовательского ПК через браузер.
