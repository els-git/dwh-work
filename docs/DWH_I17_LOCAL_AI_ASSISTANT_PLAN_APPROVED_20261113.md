# DWH — локальный ИИ-помощник и отчёты по описанию (проект плана)

Статус: **УТВЕРЖДЁН** пользователем 13.11.2026 (проект — `..._DRAFT_20261113.md`). ID итерации — **I17**.
Решения Л1–Л9 — по рекомендациям; **модели выбирает пользователь** (Л1: ограничения ниже, сравнение — проба шага 2).

## 1. Что просил пользователь (13.11.2026)

Чат с LLM внутри приложения, **локальный, без выхода в сеть**. Две работы:

1. **Помощник по приложению.** Отвечает, как делать настройки, где находятся отчёты, какая структура таблиц, какие шаги запуска — всё, что умеет UI.
2. **Отчёт по описанию.** Пользователь пишет, например, «дай все кредиты по каналу ИБ». Помощник составляет SQL к таблицам DWH и показывает результат отчётом в UI.

## 2. Как это будет устроено

```
браузер ── HTTPS ── nginx ── dwh-api ──┬── dwh-llm (llama.cpp, 127.0.0.1:8081, без сети)
                                       ├── справка и описание таблиц (поиск по тексту)
                                       └── PostgreSQL: роль dwh_ai_ro — только SELECT по разрешённым витринам
```

- **Модель** работает на самом сервере, отдельной службой `dwh-llm`. Она слушает только `127.0.0.1`, в интернет не ходит.
- **Модель не видит данных.** Ей передаются только вопрос, найденные куски справки, описание разрешённых таблиц и словарь терминов. Сами строки идут из PostgreSQL сразу в UI, минуя модель.
- **SQL выполняет не модель, а `dwh-api`.** Порядок:
  1. проверка: один `SELECT`/`WITH`, только разрешённые таблицы, без опасных функций;
  2. выполнение отдельной ролью «только чтение»;
  3. предел времени и числа строк.
- **Действия в приложении** помощник не выполняет: не запускает загрузки, не меняет настройки. Он только объясняет, как это сделать.

### 2.1. Часть А — помощник по приложению

- **Знания.**
  - **Справка пользователя** — новый документ `docs/DWH_USER_GUIDE.md`: разделы UI, настройки, отчёты, запуски, ошибки. Пишется в этой итерации, иначе модели неоткуда знать ответы.
  - **Реестр функциональности.**
  - **Тексты интерфейса** — названия кнопок и экранов на трёх языках.
  - **Описание таблиц** `stg`/`ods`/`dm`: колонки, типы, комментарии из каталога PostgreSQL.
- **Поиск.** На каждый вопрос находятся 3–5 подходящих кусков знаний, и модель отвечает по ним со ссылкой на экран или раздел. Если в найденном ответа нет, модель так и говорит, а не выдумывает.
- **Язык ответа** — язык вопроса: русский, английский или азербайджанский.

### 2.2. Часть Б — отчёт по описанию

1. Пользователь пишет описание отчёта.
2. Модель получает описание разрешённых витрин, **словарь терминов** и **примеры проверенных запросов** и составляет SQL.
3. `dwh-api` проверяет SQL и выполняет его ролью `dwh_ai_ro`: только чтение, 30 с, до 10 000 строк.
4. UI показывает:
   - SQL (его можно скопировать);
   - таблицу результата;
   - выгрузку Excel / PDF тем же модулем, что и обычные отчёты;
   - кнопку «Неверно» — для пополнения примеров.
5. Если запрос отклонён проверкой или упал, модель получает текст ошибки и делает ещё одну попытку. Не больше двух.

**Словарь терминов — главное для точности.** Модель не знает, что «ИБ» — это значение `IB` в `sales_channel`, а «кредит» — определённый продукт. Администратор заводит такие соответствия в «Администрировании». Проверенные запросы становятся примерами для модели.

**Что есть в DWH сейчас:**
- витрина `dm.v_retail_application_current` (заявки);
- таблицы ODS по CRM и `asan_pension_requests`.

Отчёты можно строить только по тому, что загружено. Если в DWH нет поля для вопроса пользователя, модель должна ответить «таких данных в DWH нет».

## 4. Безопасность

- **Сеть.** Служба модели слушает только `127.0.0.1`. Модель и программа ставятся офлайн-пакетом со сверкой SHA256, как выпуски DWH. Исходящий интернет сервера для неё не нужен (I13-11).
- **Данные.** Модель не получает строк данных, паролей, настроек подключений, `secret_ref`, журналов.
- **SQL.** Проверка до выполнения:
  1. один оператор, только `SELECT`/`WITH`;
  2. только таблицы белого списка;
  3. запрещённые функции: `pg_read_file`, `dblink`, `lo_*`, `pg_sleep`, `set_config` и т. п.;
  4. `EXPLAIN` перед выполнением.
- **Вторая защита — сама роль `dwh_ai_ro`:**
  - права только `SELECT` на белый список;
  - `default_transaction_read_only = on`;
  - `statement_timeout`.
  Даже ошибка проверки не даст ничего изменить.
- **Права пользователя.** Отчёт по описанию видят только пользователи с правом `AI_REPORT_RUN`. Ограничение строк по ролям (если появится) применяется и здесь.
- **Подмена инструкций.** Справка и описания таблиц — наши файлы. Текст пользователя не может расширить права: проверка SQL и роль от модели не зависят.

## 5. Ресурсы сервера

- **Память.** Модель 7B Q4 занимает ~5–6 ГБ. Сейчас под PostgreSQL отведено ~8 ГБ, приложения и ОС — ~4 ГБ; из 31 ГБ остаётся с запасом.
- **Процессор.** Модели отдаётся 8 из 16 ядер (`--threads 8`), чтобы не мешать загрузкам. Одновременно — 1 запрос, остальные в очереди.
- **Диск.** Модели — `/var/lib/dwh-llm` (~5–10 ГБ на системном SSD; при нескольких моделях — отдельный диск, как в плане I16).

## 7. Риски и ограничения

- **Точность.** Модель 7B на процессоре ошибается на сложных отчётах: соединения многих таблиц, нестандартные периоды. Защита: показываемый SQL, словарь, примеры, кнопка «Неверно». Порог приёмки — в шаге 7.
- **Скорость.** Ответ 15–40 с, один запрос одновременно. Для нескольких пользователей нужна видеокарта (Л1, альтернатива).
- **Азербайджанский язык.** У небольших моделей он слабее русского и английского. Проверяется на шаге 2.
- **Модель можно скачать только на ПК** с доступом к Hugging Face (файл GGUF + SHA256) и перенести `scp`, как пакеты выпуска.
- **Отчёты ограничены загруженными данными.** Для вопроса «кредиты по каналу ИБ» нужны поля продукта и канала продаж в витрине. Если их нет, сначала нужна загрузка или витрина (I06/I09 и т. п.).
- **Сохранённые отчёты, расписание отчётов, графики** — не в этой итерации (Л9).

## 8. Шаг 2 — проба моделей на сервере (порядок)

**Модели выбирает пользователь.** Ограничения сервера (16 ядер, 31 ГБ, без видеокарты):
- формат GGUF (для llama.cpp), вариант instruct / chat;
- сжатие Q4_K_M или Q5_K_M; файл до ~10 ГБ — вместе с PostgreSQL (~8 ГБ) память должна остаться;
- лицензия, допускающая использование в компании;
- желательно — хороший русский и SQL.

Модели скачиваются на ПК и переносятся `scp` в `/var/lib/dwh-llm/models` со сверкой SHA256 (или скачиваются на сервере, пока его интернет открыт — I13-11 отложена).

**Программа:** `llama-server` из llama.cpp — пакетом Debian, если он есть в Debian 13, иначе готовой сборкой.

**Запуск на время пробы:** временная служба `systemd-run` под отдельным пользователем (`DynamicUser`), только `127.0.0.1:8081`, 8 потоков, предел памяти. После пробы останавливается. DWH не меняется.

**Инструмент:** `tools/server/dwh_llm_probe.py` + `llm_probe_questions.json` (10 вопросов по приложению, 10 описаний отчётов по витрине `dm`):
- ответы на вопросы — по кускам документации, найденным по словам;
- SQL проверяется только `EXPLAIN` ролью `dwh_app` в транзакции «только чтение» — запросы **не выполняются**, данных в отчёте нет;
- итог — Markdown-отчёт (ответы, SQL, время, токенов в секунду) и `PROBE_RESULT`.

Проверено в песочнице с имитацией `llama-server` (PostgreSQL 16, витрина-заглушка): `EXPLAIN` различает верный SQL, ошибку колонки и `NO_DATA`; отчёт пишется.

**Результат шага:** по каждой модели — скорость и качество ответов. Пользователь выбирает модель для I17.
