## 1. Что получится в итоге (простыми словами)

В Administration → Integrations у исходной системы появляется блок **«Подключение»**:
- **БД или файлы:** одни настройки подключения на весь источник (хост, порт, база или путь к папке) и **не более одной учётной записи**, если она нужна. Они общие для всех групп и объектов источника;
- **API:** у источника только название. URL, параметры и учётные данные настраиваются у каждого объекта, даже если значения повторяются. Это относится к объектам API (I11), не к I03;
- учётные данные можно **задать, заменить и отозвать**, но **нельзя прочитать** — ни в UI, ни через API, ни администратору;
- каждая операция с учётными данными идёт через `secret_store` (M-SS01–M-SS04) и пишется в журнал с актором;
- сохранение даёт статус `DRAFT` и **ничего не запускает**. `READY` возможен только после проверки подключения (`test_connection`), которая появляется в I04.

### Шаг 7 — чек-лист приёмки на ПК (синтетические данные)

1. Источник БД: «Подключение» → заполнить host/port/database/username → «Сохранить настройки» → статус `DRAFT`.
2. Ввести синтетическое значение (не настоящий пароль) → «Задать» → состояние `ACTIVE`, поле пустое.
3. «Заменить» другим синтетическим значением → `ACTIVE`, новая дата.
4. «Отозвать» → подтверждение → `NONE`.
5. Источник API: панель показывает только пояснение.
6. Read-only проверка журнала: в `secret_store` — операции CREATE, REPLACE, REVOKE по источнику; синтетические значения не встречаются ни в БД, ни в ответах, ни в логе backend.
