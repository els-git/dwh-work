# I13-05 — Просмотр журналов администратором

<sub>План утверждён пользователем 23.11.2026 (Ж1–Ж6 = A; Ж2 — только `ADMIN` и `SUPERADMIN`; Ж5 — выгрузка не нужна в принципе)</sub>

## 1. Задача

Задача заведена 04.11.2026 по итогам I03: администратор видит журнал аудита и журнал операций с паролями источников (`secret_store`) в интерфейсе, через функции базы, без прямых прав `dwh_app` на таблицы журналов. Значения паролей, `secret_ref` и содержимое файлов не показываются никогда.

**Критерий (из roadmap):** администратор видит операции CREATE/REPLACE/REVOKE (и READ) по источнику; значения и `secret_ref` не показываются.

## 2. Что есть сейчас (по коду)

- `audit.security_event` — общий журнал: время, пользователь, уровень, тип события, объект, действие, итог, источник, `request_id`, `details` (JSON). Пишут вход и пользователи, роли и доступ, интеграции (подключения, объекты, маппинг, публикации), загрузки и заявки, витрины, помощник, SecretStore. У `dwh_app` прав на таблицу нет.
- `secret_store.operation_event` (+ `operation`) — журнал операций с паролями: CREATE / REPLACE / REVOKE / READ, этапы ATTEMPT / OUTCOME, коды (`PERMITTED_ATTEMPT`, `DENIED_ATTEMPT`, `SUCCEEDED`, `FAILED`), актор (`DWH_USER` / `SERVICE`). У `dwh_app` прав на схему нет. Сейчас журнал читается только на сервере от `postgres` (`dwh_secret_check.py`, `dwh_secret_accept.py journal`).

## 3. Решения (утверждены 23.11.2026: Ж1–Ж6 = A)

| № | Вопрос | Рекомендация | Другой вариант |
|---|---|---|---|
| Ж1 | Какие журналы | **A** — оба: «Журнал аудита» (все события) и «Операции с паролями» (по источнику) | B — только операции с паролями |
| Ж2 | Кому видно | **A** — уровням `SUPERADMIN` и `ADMIN`, как остальное «Администрирование» | B — отдельное право `AUDIT_LOG_VIEW` (можно выдать роли аудитора) |
| Ж3 | Где | **A** — «Администрирование» → вкладка «Журналы»: фильтры (период, тип события, пользователь, объект, итог), постранично по 100; в карточке источника — ссылка на его операции с паролями | B — только в карточке источника |
| Ж4 | Подробности события (`details`) | **A** — показываются, но функция базы убирает поля с секретами (`secret_ref`, `password`, `token`, `dsn`, ключи, файлы, хэши файлов) | B — без подробностей |
| Ж5 | Выгрузка | **A** — без выгрузки в этой задаче | B — CSV по фильтру |
| Ж6 | Просмотр журнала | **A** — каждое открытие с фильтром записывается событием `AUDIT_LOG_VIEWED` | B — не записывать |

## 6. Шаг 2 — опись на сервере

Скрипт `database/diagnostics/i13_05_audit_inventory.sql` — только чтение, от `postgres` в транзакции только чтения. Выводит колонки, индексы, права, число строк и период, типы событий, **только имена** ключей `details` (значения не печатаются), ключи, похожие на секретные, коды журнала `secret_store`, существующие функции чтения. Проверен в песочнице (база `e0_027`). Итог описи — здесь, им задаётся список скрываемых ключей (Ж4) и индексы пакета 029.

### 6.1. Итог описи на сервере (23.11.2026)

- `audit.security_event`: 1 163 строки с 30.09.2026, 63 типа событий; индексы по времени, типу, пользователю и объекту уже есть — новые не нужны. `secret_store.operation_event`: 296 строк с 28.10.2026, индексы по источнику и времени есть.
- Права: у `dwh_app` нет чтения ни одного журнала (только `USAGE` на схему `audit`) — подтверждено.
- Ключи `details`, похожие на секретные: `secret_ref` (3 события `SECRET_STORE_LEGACY_REVOKE`) — **скрывается**; `key_id` (имя мастер-ключа, например `K2026_04`, не секрет) — **показывается**; `definition_hash`, `ddl_sha256`, `sql_sha256` — хэши настроек и DDL, не файлов паролей — показываются; `must_change_password`, `password_initialized` — флаги — показываются. Правило скрытия — по имени ключа на любом уровне (кроме флагов `true/false`) и пароль в строке подключения `…://user:***@…`.
- Функций чтения журналов для `dwh_app` нет — их добавляет пакет 029.
- **Сторонняя находка (не в этой задаче):** у роли `dwh_etl` есть права `INSERT, SELECT, UPDATE, DELETE, TRUNCATE` на `audit.security_event` — служба загрузок технически может изменить или удалить записи аудита. Для неизменяемости журнала достаточно `INSERT` (и записи через `audit.log_security_event`). Решение — за пользователем.
