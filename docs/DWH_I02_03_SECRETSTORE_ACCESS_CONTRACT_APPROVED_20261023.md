# DWH I02-03 — согласованный контракт прав SecretStore (проект, без применения)

**Решение пользователя:** 23.10.2026, согласованы коды `ADMIN_INTEGRATION_MANAGE`, `INTEGRATION_SOURCE_SYSTEM` и привязка к `meta.source_system.source_system_id`. **Статус документа:** утверждённый проект для дальнейшей реализации, не подтверждение наличия кодов и ресурсов в БД. **Scope:** I02-03; никаких новых полномочий или миграций этим документом не предоставлено.

## 1. Идентификаторы и право

| Поле | Утверждённое проектное значение | Ограничения |
|---|---|---|
| `permission_code` | `ADMIN_INTEGRATION_MANAGE` | Код применяется к новому типу операции только после проверки наличия и активности в `app.permission`; наличие в маршрутах backend **не доказывает** регистрацию/активность в справочнике БД. |
| `resource_type` | `INTEGRATION_SOURCE_SYSTEM` | Проектный код, наличие и активность в `app.resource` **не проверены** из-за ACL. Не создавать ресурс без отдельного разрешения. |
| `resource_code` | `"SOURCE_SYSTEM_" + str(source_system_id)` (положительный `bigint`, без ведущих нулей) | Только положительный ID, взятый с сервера из реальной строки `meta.source_system`. Клиент не выбирает resource_code/permission_code. |
| `actor_user_id` | Из действующей серверно проверенной сессии DWH | Не принимать actor ID, account level, роль, токен-хэш или контекст аудита из тела запроса. |
| проверка доступа | `app.has_scoped_permission(actor_user_id, 'ADMIN_INTEGRATION_MANAGE', 'INTEGRATION_SOURCE_SYSTEM', resource_code)` | Требуется строго `TRUE`; `FALSE`, `NULL`, ошибки, недоступность БД и неподтверждённое сопоставление → отказ **до обращения к секрету**. |

**Семантика:** администраторский общий маршрут `/api/admin/integrations` сам по себе не заменяет доступ к выбранному `source_system_id`. Источник должен существовать и быть активным (`meta.source_system.is_active`); ID и состояние проверяются в доверенном серверном/SQL-контракте. Справочные `app.permission`/`app.resource` должны существовать и быть активными, а фактические пары `resource_type/resource_code` должны соответствовать источнику. До отдельного безопасного подтверждения этих данных **все реальные операции SecretStore закрыты**.

### Запрет на расширение полномочий

Данный договор **не** разрешает `INSERT/UPDATE/DELETE`, `CREATE FUNCTION`, `GRANT`, новые коды ролей, изменять `auth.py`, раскрывать секрет, запускать ETL, или встраивать endpoint в действующий API. В частности, запрещено давать `dwh_app` прямое `EXECUTE` на `audit.log_security_event()`. Выполнение SQL, изменение реального API и регистрация справочных кодов требуют отдельных согласованных шагов.

## 2. Контракт будущего API (не реализован)

- Операция человека: только `CREATE`/`REPLACE` для конкретного существующего `source_system_id`; чтение plaintext человеком, включая администратора, запрещено.
- Тело запроса при будущем согласовании API-маршрута: server-approved ID источника + credential payload только на запись. Никаких клиентских `actor_user_id`, `permission_code`, `resource_type`, `resource_code`, `secret_ref`, аудиторских полей или ключа шифрования.
- Выполняющий backend должен заново подтвердить сессию, связь источника с ресурсом и scoped permission в момент операции; при ошибке запрещается обращаться к файловому секрет-хранилищу.
- Ответы, URL, frontend, сообщения ошибок и логи не должны содержать raw credential, токен, DSN, master key, ciphertext или plaintext. Разрешён только несекретный идентификатор результата после подтверждённого завершения.
- Действующие `secret_store.py`, `secret_file_store.py`, `secret_key_provider.py`, `secret_dwh_identity_adapter.py` и `secret_access_boundary.py` сейчас являются изолированными компонентами. Наличие unit-тестов **не** доказывает production/E2E готовность.

## 3. Проект защищённой SQL-границы (не исполняемый DDL)

Предлагаемая узкая `SECURITY DEFINER` функция `app.integration_secret_audit_append` (окончательные аргументы и RETURNS подлежат review вместе с I02-04) должна:

1. Принимать внутренний проверяемый контекст сервера/сессии, `source_system_id`, `request_id`, фазу и ограниченный набор метаданных; **не** доверять переданному извне `actor_user_id`/коду разрешения/ресурса.
2. Повторно подтвердить действующую сессию штатным механизмом `app.*`, серверное существование и активность источника, approved mapping и scoped permission; запросы для журнала отказов обрабатываются отдельно так, чтобы отсутствие права не исключало фиксацию отказа по достоверной сессии.
3. Допускать только белый список событий `ATTEMPT` (`DENIED`/`PERMITTED_ATTEMPT`) и `OUTCOME` (`SUCCEEDED`/`FAILED`), с чёткой семантикой отсутствия/повтора события и идентификатором запроса для корреляции.
4. Вызывать существующий `audit.log_security_event()` из защищённой схемы (с ограниченным `search_path`), не расширяя права прямого доступа `dwh_app` к audit.
5. Передавать в `details` только whitelisted несекретные значения, никогда пароли, ключи, токены, DSN и исходный `secret_ref`; fingerprint можно использовать только после отдельного анализа рисков корреляции.
6. Проводить запись попытки в **отдельной подтверждённой транзакции до filesystem-операции**. Итог фиксировать отдельно и проверять успешный COMMIT; rollback основной операции не должен удалять попытку.
7. Закрывать доступ при сбоях журнала и несоответствии actor/session/context; проект требует проверить безопасность выставления actor/security_source/request_id GUC штатными SQL-функциями.

**Важная граница:** транзакция PostgreSQL не может атомарно коммитить файловую запись. Поэтому одного `SUCCEEDED` audit event недостаточно для гарантированной публикации: до I02-04 нужен отдельный проект PENDING/ACTIVE, согласованная точка публикации, идемпотентность, reconcile при обрыве между файлом и SQL, восстановление и тесты отказов. В текущем SecretFileStore UUID-файл создаётся под конечным именем; серверный active binding и сервисная READ-защита пока отсутствуют.

### Предлагаемая сигнатура для review (не SQL-команда)

`app.integration_secret_audit_append(p_server_session_token_hash text, p_source_system_id bigint, p_request_id text, p_ref_fingerprint text, p_phase text, p_outcome text) RETURNS bigint` — **кандидат**, не утверждённая исполняемая сигнатура. Проверка сессии внутри SQL должна использовать доверенный `app.integration_admin_session_user` либо эквивалент, доступность и полная семантика которого подлежат подтверждению перед реализацией. Отказы в доступе нужно уметь аудировать без разрешения на изменение секрета: нельзя строить writer так, чтобы `has_scoped_permission = FALSE` обрывал регистрацию отказа.

### Точка будущего backend-вызова (не API-маршрут)

Согласованный поток: `verified AuthState / server session` → `source_system_id from server-validated meta.source_system` → `has_scoped_permission` → `durable ATTEMPT COMMIT` → `encrypted PENDING store` → `durable OUTCOME COMMIT` → `activation according to I02-04 protocol`; при любой неоднозначности секрет не используется. Конкретный HTTP URL, параметры `request_id`, план смены/отзыва секрета и сервисный ETL READ должны быть оформлены отдельно до применения.

## I02-03 — решение о привилегированном доступе от 26.10.2026

**Решение пользователя, 26.10.2026:** сохранить существующую модель административных полномочий DWH для управления секретами источников. Администраторы с соответствующим привилегированным `account_level` и активным `ADMIN_INTEGRATION_MANAGE` вправе создавать/заменять секреты для активных ресурсов `INTEGRATION_SOURCE_SYSTEM`; от них не требуется отдельное назначение каждого ресурса роли. Обычные пользователи проходят обычную проверку `app.has_scoped_permission()` со scoped-настройками назначения прав и ресурсов. Код/уровни привилегированных учётных записей не меняются, новых ролей и разрешений не создаём.

**Пример:** при наличии активного ресурса `INTEGRATION_SOURCE_SYSTEM/5` действующий привилегированный администратор может заменить секрет `OPERATION_COLLECTOR` (`source_system_id=5`) при выполнении штатных серверных проверок. Пользователь, не имеющий права на этот ресурс, получает отказ. Никто из пользователей, включая администратора, не получает API для чтения открытого секрета.

**Важное следствие:** появление нового активного ресурса может изменить результат уже действующей `app.has_scoped_permission()` для привилегированных учётных записей без назначения нового права роли. Этот эффект **согласован как проектное поведение**, но не является разрешением исполнять SQL, создавать ресурс или подключать SecretStore к API.

**Не подтверждено в действующей БД:** фактические строки `app.permission`, `app.resource` (`/1`, `/5`), их активность, полные последствия для реальных сессий и безопасный сценарий восстановления после `COMMIT`. Для них остаётся `STOP` перед изменением PostgreSQL. Аудит операций с секретами и эксплуатационный API ещё не подключены.

## Дополнение от 26.10.2026 — проверенная миграция и изолированный scoped-adapter

Согласованный формат ресурсов: `INTEGRATION_SOURCE_SYSTEM/SOURCE_SYSTEM_1` и `INTEGRATION_SOURCE_SYSTEM/SOURCE_SYSTEM_5`. PostgreSQL `dwh` на порту 5433: `ADMIN_INTEGRATION_MANAGE` активен; оба ресурса отсутствовали на момент read-only проверки. В тестовой БД `dwh_i02_03_test` подтверждены создание, аудит `RESOURCE_CREATED` (2 события), COMMIT и восстановление пустой схемы. **Рабочая БД не изменялась; тестовое восстановление не является процедурой восстановления рабочей БД.**

Изолированный модуль `backend/src/dwh_api/secret_source_scope.py` проверяет доверенный ID пользователя, активность `meta.source_system`, режим транзакции read-only и строго `TRUE` от `app.has_scoped_permission()` с новым форматом. Не использует `AuthState.permissions` как дополнительный запрет для привилегированных администраторов. Это **не** разрешение на эксплуатационный вызов: trusted mapping `secret_ref` к источнику, durable audit, PENDING/ACTIVE и API отсутствуют. Модуль не встраивается в действующие маршруты и не меняет прежний изолированный адаптер идентичности.
