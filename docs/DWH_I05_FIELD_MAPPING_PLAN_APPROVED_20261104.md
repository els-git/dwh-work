## 1. Что получится в итоге (простыми словами)

Для объекта нового источника (первый — `OPERATION_COLLECTOR` / `public.asan_pension_requests`) администратор в интерфейсе:

1. выбирает целевую таблицу DWH (существующую или заявляет новую — см. п. 4);
2. в двустороннем редакторе сопоставляет поля: слева — поля из снимка структуры источника (I04) и добавленные вручную, справа — поля целевой таблицы; справа предлагаются только совместимые по типу поля;
3. выбирает бизнес-ключ объекта (одно или несколько полей) — один раз для объекта;
4. для каждого поля задаёт правило записи (`AUTHORITATIVE` / `INSERT_ONLY` / `NO_WRITE`) и разрешение явного `NULL`;
5. нажимает «Проверить», затем «Опубликовать»: опубликованная версия неизменяема, объект получает статус `READY`;
6. если структура источника изменилась относительно опубликованной версии (новый снимок), система показывает расхождение (schema drift) и не даёт объекту оставаться `READY` без решения администратора.

Загрузка данных по этой конфигурации — **I06** (не входит в I05). Существующий контур `CRM_RETAIL` не меняется.

## 7. Шаг 2: результат (04.11.2026, `dwh_app`, только чтение)

- `meta.source_object`: стратегии `FULL`/`INCREMENTAL`/`INCREMENTAL_OVERLAP`/`SNAPSHOT`, типы `TABLE`/`VIEW`, уникальность `(source_system_id, source_schema, source_object)` — подходит как объект новой модели (М3).
- Legacy-каталоги `meta.column_contract`, `meta.mapping_rule`: источник по `source_system_code` (без FK), версии `version_no`/`valid_from`/`valid_to`; новая модель их не меняет.
- `stg`/`ods`: владелец `dwh_admin`; `dwh_etl` — USAGE и права по умолчанию на чтение/запись новых таблиц, без CREATE; у `dwh_app` USAGE нет → новые цели создаются только пакетом БД (М5).
- Таблицы: `stg` — 12 таблиц `crm_retail_*` (9 колонок, ключ `_dwh_landing_id`), `ods` — 12 таблиц `crm_retail_*` (ключ `source_id`, у событий — `source_event_hash`); других целей нет.
- Образец STG и счётчики legacy-каталогов не получены (ошибки запросов, исправлено правило: SQL перед передачей прогоняется в песочнице под `dwh_app`); для решений не нужны — legacy определяется в БД функцией.

## 8. Пакет 008 (шаг 3)

Файлы: `database/migrations/008_object_config.sql`, `.down.sql`, `database/checks/008_object_config_check.sql` (10 проверок), `database/tests/008_object_config_test.sql` (31 испытание, `ROLLBACK`), `database/run_008_e1_test.ps1`, `database/run_008_e2_apply_dwh.ps1`.

**Что создаётся (схема `meta`, только владелец; доступ через функции):**
- `object_config_version` — версии конфигурации объекта: `DRAFT` → `PUBLISHED` (неизменяема), один черновик на объект, `draft_revision`, `definition_hash` (SHA-256 канонического описания, считается в БД);
- `object_config_field` — целевая колонка ← колонка источника, нормализованные типы, конвертация `NONE`/`SAFE`/`CONFIRMED`, правило записи `AUTHORITATIVE`/`INSERT_ONLY`/`NO_WRITE`, явный `NULL`;
- `object_config_key_part` — бизнес-ключ (только поля маппинга);
- `object_config_validation` — результаты проверки (только добавление);
- `object_config_current` — версия в силе, `READY`/`DRIFT`;
- `target_change_proposal` — DDL-проекты новых таблиц/колонок, только хранение.

**Функции для `dwh_app`** (сессия, аудит): `integration_object_config_get`, `_save_draft`, `_record_validation`, `_publish`, `_set_drift`, `integration_target_proposal_create`, `_reject`. Публикация в БД заново проверяет: ревизию и хеш успешной проверки, существование целевой таблицы и всех колонок, непустой ключ без `NO_WRITE`/`NULL`, отсутствие другого `AUTHORITATIVE` объекта на тех же колонках (A08).

**М7:** `meta.source_is_legacy` — источник legacy, если у него есть строки в `column_contract` или `mapping_rule`; для таких источников запрещены черновики и снимок структуры из UI (функция снимка из 006 дополнена этой проверкой; откат восстанавливает версию 006).
