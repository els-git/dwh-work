# I19 — План: конструктор витрин DM (шаг «ODS → DM»)

> Статус: **УТВЕРЖДЁН** пользователем 16.11.2026 (решения Д1–Д11 по рекомендациям, ID итерации — I19). Проект: `docs/DWH_DM_BUILDER_PLAN_DRAFT_20261116.md`.
> Основание: подтверждение пользователем логики слоёв 16.11.2026 (вопрос о витрине по пенсиям из шага 9 I17).

## 1. Цель

Третий шаг общего механизма загрузки: после успешного ODS заполняются витрины `dm`, которые собираются из одной или нескольких таблиц ODS по общим ключам, с приоритетом источников и агрегатами. Витрины настраиваются в интерфейсе без ручного SQL и сразу доступны «Отчётности» и ИИ-помощнику (с правом доступа).

## 2. Логика пользователя (подтверждена 16.11.2026)

1. Интеграция загрузила STG.
2. STG успешен → заполняется ODS.
3. ODS успешен → заполняется DM.

DM может брать данные из нескольких таблиц ODS (например, клиенты, договоры, счета) по общему ключу, который в таблицах может называться по-разному (`client_id`, `cust_id`, …), с правилом приоритета. Пользователь выбирает поля из всех таблиц и агрегаты (сумма остатков по счетам, количество договоров и т. п.).

## 11. Шаг 5 — backend и движок (песочница, 16.11.2026)

**Генератор SQL** — `backend/src/dwh_api/dm_sql.py` (без обращений к БД; один код для движка и предпросмотра в API):
- каждая таблица сначала сводится к ключу зерна, потом соединяется (Д1): дочерние — подзапрос `GROUP BY` ключа с агрегатами; поэтому суммы по нескольким дочерним таблицам не умножаются;
- `SAME_KEY` и справочники — `LEFT JOIN` к отфильтрованной таблице; справочник соединяется с колонкой более ранней таблицы, одна таблица под несколькими псевдонимами — роли (Д12);
- поле из нескольких источников — `coalesce` в порядке приоритета (Д3); `COUNT`/`COUNT_DISTINCT` без дочерних строк — 0;
- поле `varchar(n)` строится как `text`: слишком длинное значение даёт ошибку при вставке, а не молча обрезается;
- значения фильтров — параметры с приведением к типу колонки (`IN` — массив).

**Движок** — `etl/src/dm_mart_worker.py`, роль `dwh_etl`, в процессе диспетчера (`run_request_dispatcher.main` берёт заявки витрин, когда пусты очереди CRM и объектов):
1. захват заявки, `etl.dm_mart_run_begin`;
2. проверка: таблицы и колонки версии есть в ODS (`DM_SOURCE_MISSING`); нет пустых ключей зерна (`DM_KEY_NULL`); ключи `GRAIN`/`SAME_KEY` и колонки справочников уникальны (`DM_KEY_NOT_UNIQUE` / `DM_LOOKUP_NOT_UNIQUE`: сколько значений повторяется и до 10 примеров с числом строк);
