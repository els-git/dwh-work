**Статус документа:** проект, ждёт решений пользователя С1–С8 и утверждения.
**Статус итерации:** I16 `PLANNED` (задачи I16-01…I16-06). Порядок: после I08 (`DONE` 12.11.2026), до I09.

**Требования пользователя:**
- 11.11.2026: у сервера нет доступа в интернет, GitHub в том числе. Обновление — офлайн-пакетом с ПК со сверкой SHA256. Диски считать по ожидаемым объёмам: 23 МБ в `dwh` сейчас — только тестовые запуски.
- 12.11.2026:
  - сервер локальный и закрыт для доступа извне — нужен способ доставлять обновления;
  - в будущем на сервере — небольшая LLM, которая генерирует SQL-запросы для построения отчётности. Параметры сервера должны это учитывать.

## 1. Что получится в итоге (простыми словами)

- DWH (веб-интерфейс, API, диспетчер, ETL, PostgreSQL `dwh`, ключи SecretStore) работает на сервере круглосуточно. Рабочий ПК для работы DWH больше не нужен.
- Пользователи открывают DWH в браузере по адресу внутренней сети через HTTPS, например `https://dwh.<домен>`.
- Сервер сам ходит только к источникам (CRM `10.30.58.64:5432`, `OPERATION_COLLECTOR` `10.1.42.6:54320`) и только на чтение — шлюз I13-07. В интернет он не ходит.
- Обновления: на ПК собирается **пакет выпуска** (один архив + файл SHA256). Его кладут на сервер, и одна команда:
  1. проверяет пакет;
  2. делает резервную копию;
  3. ставит обновление;
  4. проверяет, что всё работает;
  5. при ошибке — откатывает.
- Службы запускаются сами после перезагрузки. База копируется каждую ночь, копия проверяемо восстанавливается.
- Сервер сразу подбирается с запасом под будущую LLM. Сама LLM — отдельная будущая итерация (раздел 6), в I16 не ставится.

## 3. Решения для пользователя

### С1. Операционная система сервера
- **A (рекомендую): Windows Server 2022 или 2025.**
  - Всё, что уже принято, работает без переделки: ключи DPAPI (I02-05), скрипты PowerShell, команды из CLAUDE.md, `psql.exe`.
  - Небольшая LLM на Windows тоже работает: llama.cpp или Ollama с видеокартой NVIDIA (CUDA).
- **B: Linux (Ubuntu Server 24.04).**
  - Лучше для больших LLM-серверов (vLLM).
  - Но нужно: переписать хранение мастер-ключей (DPAPI на Linux нет), перевести все `.ps1` на bash, заново пройти приёмку SecretStore. Это несколько дополнительных шагов и риск для уже принятого.

### С2. Где будет LLM
- **A (рекомендую): на этом же сервере**, отдельной службой с ограничением ресурсов. Сервер заказывается сразу с видеокартой (раздел 4).
- **B: отдельная машина позже.** Сервер DWH дешевле, LLM-машина — в будущей итерации.

### С3. PostgreSQL на сервере
- **A (рекомендую): PostgreSQL 17 — служба Windows**, офлайн-установщик со сверкой SHA256.
- **B: Docker на Windows Server.** Сложнее без интернета, лишний слой.

### С4. Как доставлять обновления (сервер закрыт извне)
- **A (рекомендую): пакет выпуска через внутреннюю папку.**
  - На ПК команда `make_release.ps1` собирает `dwh_release_<версия>.zip`. Внутри:
    - `git bundle` с изменениями;
    - собранный frontend `dist`;
    - Python-пакеты `.whl` — только если изменились;
    - SQL-пакеты;
    - `manifest.json` с SHA256 каждого файла.
  - Рядом кладётся `dwh_release_<версия>.sha256`.
  - Пакет копируется в защищённую папку сервера по внутренней сети (SMB, доступ только у администратора DWH) или на USB-носитель, если сеть закрыта и для ПК.
  - На сервере `server_update.ps1 -Package <файл>` по шагам:
    1. сверяет SHA256;
    2. останавливает службы;
    3. делает копию базы;
    4. обновляет код и frontend;
    5. запускает службы;
    6. делает короткую проверку (`/api/health`, проверка подключения);
    7. при ошибке возвращает предыдущую версию и копию.
  - Пакеты базы (E2) ставятся тем же способом — отдельной командой с подтверждением `APPLY`, как сейчас на ПК.
- **B: внутреннее git-зеркало на сервере.** ПК отправляет изменения по внутренней сети в репозиторий на сервере. Удобнее для кода, но frontend и Python-пакеты всё равно нужно передавать отдельно, а на сервере открывается ещё один вход. Не рекомендую.

### С5. HTTPS
- **A (рекомендую): один веб-сервер (uvicorn) отдаёт API и frontend на порту 443** с сертификатом внутреннего удостоверяющего центра. Сертификат выпускают администраторы.
- **B: IIS как обратный прокси** перед uvicorn. Привычно для Windows-администраторов, но ещё один компонент.

### С6. Как запускать службы
- **A (рекомендую): WinSW** — один `.exe` с открытой лицензией, кладётся в проект со сверкой SHA256. Две службы: «DWH API» (API + frontend) и «DWH Dispatcher» (диспетчер; заявки — отдельными процессами, как сейчас). Автозапуск и перезапуск при сбое.
- **B: Планировщик задач Windows** «при запуске системы». Без сторонних файлов, но слабее контроль перезапуска.

Разделение API и диспетчера на две службы — изменение по сравнению с ПК, где это один процесс. Так API не зависит от загрузок.

### С7. Резервное копирование
- **A (рекомендую):**
  - каждую ночь `pg_dump -Fc` базы `dwh` на отдельный диск сервера; хранить 14 копий;
  - раз в неделю — копия во внешнее хранилище, которое назначат администраторы;
  - копии ключей `.dwhkey` хранятся **отдельно** от копий базы, как в runbook I02-05;
  - раз в месяц — проверочное восстановление на копию `dwh_restore_test`.
- **B:** только еженедельная копия. Не рекомендую.

### С8. Служебные учётные записи
- **A (рекомендую):**
  - отдельная учётная запись Windows `svc_dwh` без интерактивного входа: от неё работают службы, под ней ключи DPAPI;
  - вход администратора DWH — отдельной личной учётной записью;
  - в PostgreSQL — прежние роли `dwh_app` и `dwh_etl`.
- **B:** службы от учётной записи администратора. Не рекомендую: ключи привязываются к человеку.

## 4. Параметры сервера

Объём `dwh` для оценки дисков — ориентир по CRM. В `app_retail.application` сейчас 44 301 строка. Число будущих источников и объектов и срок хранения истории пользователь уточняет в шаге 1; таблица ниже — исходная оценка с запасом.

| Параметр | Только DWH | DWH + небольшая LLM для SQL (С2 = A) |
|---|---|---|
| Процессор | 8 ядер | 16 ядер |
| Память | 32 ГБ | 64 ГБ (лучше 128 ГБ, если модель частично на процессоре) |
| Видеокарта | не нужна | NVIDIA с **24 ГБ** памяти (RTX 4090 / L4 / A10). 48 ГБ (RTX 6000 Ada / L40S) — если захотите модель ~32B |
| Диск ОС и программ | SSD 200 ГБ | SSD 200 ГБ |
| Диск базы | NVMe SSD 500 ГБ (уточняется в шаге 1) | то же |
| Диск копий | отдельный физический диск 1–2 ТБ | то же |
| Диск моделей | — | SSD 200 ГБ (несколько моделей и версий) |
| Сеть | доступ к источникам (порты 5432, 54320); пользователи → сервер, порт 443 | то же |

**Почему 24 ГБ видеопамяти:**
- модели для генерации SQL среднего размера (7–14 млрд параметров, например Qwen2.5-Coder-14B) в сжатом виде занимают 5–10 ГБ;
- на 24 ГБ помещаются с запасом под длинное описание схемы в запросе и одновременную работу нескольких пользователей;
- без видеокарты такая модель на 16 ядрах пишет запрос десятки секунд — терпимо для пробы, неудобно для работы.

Драйвер NVIDIA и CUDA ставятся офлайн-установщиками.

## 6. Будущая LLM для отчётности — что закладываем сейчас (без установки)

Предложение для отдельной будущей итерации. Новый ID — только с вашего согласия.

- **Модель локальная**, данные никуда не уходят. Модели и программа доставляются тем же пакетом выпуска.
- **Модель видит только описание** витрин и представлений отчётности (`dm`, при необходимости `ods`): названия, колонки, комментарии. Сами данные она не видит.
- **Готовый SQL выполняется:**
  - только через отдельную роль «только чтение» на разрешённые представления;
  - с пределом времени и числа строк;
  - через фильтр «только SELECT», как шлюз источников I13-07.
- **Пользователь видит SQL до запуска.** Запросы и ответы пишутся в журнал.
- **Что нужно от I16:** место и ресурсы на сервере (раздел 4) и порт службы LLM, доступный только локально. Ничего больше.

## 7. Ограничения и риски

- **Доступ к источникам с сервера** зависит от сетевых правил. Если CRM или `OPERATION_COLLECTOR` закрыты для сервера, шаг 4 стоит до решения администраторов.
- **Сертификат и DNS-имя** выпускают администраторы.
- **Зависание драйвера на Windows** закрыто в I08 (шлюз, раздел 12.38 реестра). На сервере это проверяется в шаге 8.
- **Уровень С1 = B (Linux)** добавит шаги и повторную приёмку SecretStore. План пересчитывается.
