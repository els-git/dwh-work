## 1. Границы проекта

Проект определяет логическую структуру, необходимые ключи, проверки и контракты взаимодействия. **Не создаёт** таблицы, SQL-миграции, API, роли, расписания, ETL и пользовательские экраны. Утверждение этого проекта **не является** разрешением на запись в PostgreSQL. Физический DDL, secret storage и план отката согласуются в I02-03/I02-04. Реализация начинается по утверждённому roadmap с I03.

В архитектуре различаются:

- **Система** (`meta.source_system`, существующая) → **техническая группа** (`DATABASE` / `API` / `FILE`) → **объект** → **одна или несколько целевых таблиц**.
- **Профиль** — переиспользуемая логическая идентичность параметров подключения внутри системы; техническая группа в опубликованной версии выбирает профиль. Объект однозначно наследует выбранный профиль группы. Отдельное групповое **исполнение** отложено до I15: в v1 запускается отдельный объект.
- **Стабильные идентификаторы** и **настройки определённой версии** хранятся раздельно; нельзя исправлять опубликованную конфигурацию на месте.
- **Ручной запуск/расписание** находится вне Administration → Integrations. Сохранение, установка галочки и проверка не запускают ETL.

## 2. Перечень сущностей — 19 новых таблиц (проект, не фактическая БД)

### 2.1. Постоянные идентичности — `meta`

| Таблица | Первичный ключ | Ссылки / уникальность | Назначение |
|---|---|---|---|
| `integration_profile` | `profile_id` | `source_system_id → source_system`; `UNIQUE(source_system_id, profile_code)`; `source_kind` | Стабильная идентичность логического профиля; без пароля и изменяемых настроек соединения |
| `integration_group` | `group_id` | `source_system_id → source_system`; `UNIQUE(source_system_id, group_code)`; `group_type` | Техническая группа подключения типа DATABASE/API/FILE |
| `integration_object` | `object_id` | `(source_system_id,group_id) → integration_group`; `UNIQUE(group_id,object_code)`; опциональная ссылка на `meta.source_object` только для совместимого legacy DB | Логический объект внутри группы |
| `integration_target` | `target_id` | `object_id → integration_object`; `UNIQUE(object_id,target_code)` | Стабильная идентичность целевого набора объекта, включая вложенные массивы API |

Согласованная иерархия — строгая. Составные ссылки не позволяют объекту одновременно принадлежать другой системе. Существующий `meta.source_object` не расширяется значениями API/FILE: его ограничение TABLE/VIEW сохраняется.

### 2.2. Версионные настройки — `meta`

| Таблица | Первичный ключ | Ссылки / уникальность | Назначение |
|---|---|---|---|
| `integration_schema_version` | `version_id` | `(source_system_id,version_no)` уникально; `(version_id,source_system_id)` как составной кандидатный ключ; `based_on_version_id` ограничен той же системой | DRAFT → PUBLISHED, `draft_revision`, `definition_hash`, атрибуция публикации |
| `integration_schema_group` | `(version_id,group_id)` | обе сущности той же `source_system_id`; выбранный `profile_id` той же системы/типа, `UNIQUE(version_id,profile_id)` | Версионный профиль группы, общие настройки, ссылка на секрет; для API — необязательные общие значения |
| `integration_schema_object` | `schema_object_id` | `(version_id,object_id)` уникально; FK `(version_id,group_id)` на версионную группу, FK `(source_system_id,group_id,object_id)` на стабильный объект | `enabled`, типовая конфигурация объекта, API-метод/URL/headers/params/body/pagination, приоритет переопределений; ссылки на секреты |
| `integration_schema_target` | `schema_target_id` | FK на `schema_object_id` и `(object_id,target_id)`; `UNIQUE(schema_object_id,target_id)`; `UNIQUE(schema_object_id,target_schema,target_table)` | Целевая физическая таблица, стратегия FULL/INCREMENTAL, область снимка и включение контроля отсутствия |
| `integration_schema_key_part` | `(schema_target_id,key_position)` | `UNIQUE(schema_target_id,target_column)` | Упорядоченные части простого/составного ключа: `target_column`, `source_path`, тип; `key_position >= 1` |
| `integration_schema_field_map` | `(schema_target_id,target_column)` | FK на версионную цель; `write_policy` ∈ AUTHORITATIVE/INSERT_ONLY/NO_WRITE | `source_path`, явность присутствия поля, разрешённость `NULL`, совместимое преобразование |
| `integration_schema_target_relation` | `(schema_object_id,parent_target_id,child_target_id)` | оба FK `(schema_object_id,schema_target_id)` на цели **этого** объекта; запрет parent=child | Зависимость вложенных сущностей, связь ключей, порядок применения |

Контракт: поля бизнес-ключа сопоставляются через `key_part`; для того же поля нет независимого правила `field_map` с конфликтующей семантикой. Правило проверяется при публикации. Бизнес-ключи не NULL, не пустые и уникальны в пределах набора. Имена полей/таблиц валидируются по фактической схеме PostgreSQL; произвольный SQL из UI не исполняется.

`connection_config`/`object_config` содержат **только несекретные** настройки. Все токены/пароли представлены непрозрачным `secret_ref` и никогда не отдаются UI. Реализация секрет-хранилища и конкретных прав — I02-03.

### 2.3. Проверка и переключение конфигураций — `meta`

| Таблица | Первичный ключ | Ссылки / уникальность | Назначение |
|---|---|---|---|
| `integration_schema_validation` | `validation_id` | FK на `(version_id,source_system_id)`, `draft_revision`, `definition_hash`, тип/статус проверки | Неизменяемый результат проверки выбранных объектов и публикации; безопасные диагностические сообщения |
| `integration_system_current` | `source_system_id` | FK `(current_version_id,source_system_id)` на версию той же системы, `lock_revision` | **Единственный** указатель действующей версии каждой системы |
| `integration_publication_event` | `publication_event_id` | `source_system_id`, `from_version_id`, `to_version_id`, `validation_id`, `action`, `outcome`, время, актор | Неизменяемый аудит PUBLISH/ROLLBACK и неудачных попыток без секретов |

`integration_schema_version.status` означает **исторический факт** публикации, а не текущую активность. Действующую версию задаёт `integration_system_current`.

FK гарантирует ту же систему, но **не** статус PUBLISHED: в транзакционной операции переключения под блокировкой системы выполняется отдельная обязательная проверка статуса и соответствия верификации. Черновик нельзя активировать. После публикации весь состав версии неизменяем; новая правка порождает новый DRAFT/версию. Неуспешная публикация не изменяет действующую версию, но фиксирует событие ошибки отдельно. Указатель прежней версии может быть выбран вручную для rollback после полной проверки совместимости. Для работающей legacy CRM отсутствие указателя допустимо: её путь выполнения сохраняется.

### 2.4. Выполнение, история и наличие — `etl`

| Таблица | Первичный ключ | Ссылки / уникальность | Назначение |
|---|---|---|---|
| `integration_run_binding` | `run_binding_id` | `version_id` + `schema_object_id` одной версии, FK на `etl.batch_run`; при совместимости — на `etl.job_run`; уникальность `(batch_run_id,schema_object_id)` | Закрепляет опубликованную неизменяемую конфигурацию за запуском объекта, порядок/статус и provenance |
| `integration_record_change` | `change_id` | FK на run binding, target и версионную цель; индексы `(target_id,key_hash,changed_at)` | Append-only история фактических INSERT/UPDATE: полный канонический бизнес-ключ, изменённые разрешённые поля (before/after), время/источник/версия |
| `integration_record_presence` | `record_presence_id` | уникальная логическая комбинация «stable target + область снимка + канонический ключ»; индекс по хешу и проверка полного ключа | Последнее подтверждённое присутствие, первое отсутствие, счётчик, статус, последний применённый порядок запуска по записи |
| `integration_presence_event` | `presence_event_id` | FK на состояние присутствия и run binding | Append-only события MISSING / REAPPEARED без физических удалений |
| `integration_snapshot_state` | `snapshot_state_id` | уникальность «stable target + нормализованная область полного снимка», FK на последний успешно применённый run | Полнота, границы/охват набора, watermark, дата в файле, порядковый номер подтверждённого снимка |

**Физический ключ присутствия** не зависит от версии схемы: `target_id` стабилен; при смене бизнес-ключа/физической цели публикация требует отдельной процедуры совместимости, иначе блокируется. Хеш — индексный ускоритель, **не** единственное доказательство равенства: полный нормализованный типизированный бизнес-ключ сравнивается обязательно. Каноническое представление ключа ограничивается валидатором по размерам и типам.

`integration_record_presence` используется как техническая запись текущего состояния и при отключённом контроле отсутствия — для защиты от устаревшего применения. Фиксация MISSING и счётчиков производится только при явно включённом контроле и только по подтверждённому полному снимку той же области. Одинаковая бизнес-строка не создаёт историю изменений; обновление метаданных last_seen само по себе допустимо.

## 3. Физические инварианты и контроль при публикации

**Обязательно enforce в БД (PK/UNIQUE/FK/CHECK):**

1. `(source_system_id,group_id)` и `(source_system_id,group_id,object_id)` — кандидатные уникальные ключи стабильной иерархии; составные FK исключают кросс-системные связи.
2. `(version_id,source_system_id)` — кандидатный ключ версии; `(version_id,group_id)` — версионная группа; FK настройки объекта одновременно подтверждает ту же версию/группу/стабильный объект.
3. `(schema_object_id,version_id,object_id)` — кандидатный ключ версионного объекта; версионная цель привязана одновременно к нему и к собственному стабильному `target_id`.
4. `(schema_object_id,schema_target_id)` — кандидатный ключ цели для составных FK связей parent/child; запрет самоссылки. Уникальность порядка/состава бизнес-ключа и поля маппинга.
5. Уникальный `(source_system_id,version_no)`, единый `integration_system_current.source_system_id`; технические `CHECK` для перечислений и неотрицательных счётчиков.
6. Ссылки на существующие `meta.source_system`, `etl.batch_run`/`etl.job_run` без изменения их действующих структур в рамках I02-02.

**Обязательно enforce транзакционной логикой публикации / проверками целевого контракта:**

- `PUBLISHED` + соответствие `definition_hash` и `draft_revision` последней успешной проверки; опубликованные версии и события неизменяемы. Проверка статуса и переключение указателя в одной транзакции с сериализацией операций по системе.
- Реальный тип/совместимость колонки и её наличие; существование таблицы, ключа/уникального индекса; пригодность преобразований и канонизации ключа; отсутствие дубликатов в исходном наборе; ограничения на объём/типы ключа; отсутствие циклов зависимостей.
- Общая проверка владения полями по **всем действующим опубликованным системам**, не только текущей: не более одного AUTHORITATIVE для физической пары «schema.table.column». INSERT_ONLY не перезаписывает существующие поля; NO_WRITE никогда не пишет. При наличии legacy CRM те же поля считаются защищёнными до явной отдельной проверки совместимости. Конфликт блокирует **только публикацию изменяемой системы**, действующие не меняются.
- Если несколько новых источников первоначально создают одну запись, сериализация выполняется по фактическому физическому ключу; журнал фиксирует победившую запись. Без отдельной договорённости приоритетов нет скрытого «последний записал — победил» для UPDATE.
- Профиль соответствует типу группы; для DATABASE общий DBMS+соединение, для FILE общий каталог/доступ, для API общие значения необязательны и переопределяются по явно заданному precedence для каждого объекта. Движок исполняет объект, не группу.
- Действительная проверка доступности/структуры **только проверяет**, а не запускает ETL; проверка каждого enabled объекта обязательна перед публикацией целой системы. Один failed объект блокирует публикацию, даже если другие прошли.

## 4. Публикация, rollback и исполнение: протокол

### Публикация одной системы

1. Администратор изменяет DRAFT. `enabled` — флаг включения объекта в будущую версию, не команда запуска. Проверка доступности/контрактов сохраняет `validation_id` с ревизией и хешем черновика.
2. `PUBLISH` блокирует переключение версии **только этой системы**, заново сверяет ревизию/хеш и валидность всех enabled объектов; проверяет глобальные конфликты полей, целевые схемы/ключи, доступность секретов и результаты проверок.
3. Только при полном успехе создаётся неизменяемая опубликованная версия, атомарно переключается `integration_system_current`, фиксируется SUCCESS event. Внешние системы не переключаются.
4. При ошибке указатель остаётся прежним; ошибка фиксируется безопасным FAILED event после отката неудачной транзакции. Ни ETL, ни физические DDL не инициируются.

### Возврат прежней опубликованной версии

1. Оператор вручную выбирает прежнюю PUBLISHED версию **этой же системы**.
2. Предварительно проверяются подключения, секреты, цели, колонны, составные ключи, маппинги, совместимость схемы и глобальное владение полями.
3. Успех — атомарное переключение указателя и неизменяемый ROLLBACK event; ошибка — отсутствие переключения и FAILED event. Данные/история не откатываются, выполнение уже стартовавших запусков закреплено за прежними версиями.

### Исполнение объекта

1. При запуске объект получает `run_binding` с неизменяемой PUBLISHED версией; если версия исключает объект, новые запуски не разрешены. Приоритет параметров API: явно настроенные объектовые override над необязательными настройками группы, отсутствие override наследует группу. Валидация обязательных свойств проводится перед запросом.
2. Извлечение API/DB/FILE и материализация полного исходного набора могут осуществляться отдельно от транзакции записи. **Применение** всех связанных таблиц одного объекта — одна транзакция после предвалидации каждого ключа, поля, правил и структуры.
3. Перед записью для каждого нормализованного физического ключа/набора полей выполняются упорядоченная синхронизация и проверка свежести. Порядок DWH защищает от запоздало завершившихся API/DB запусков, но не заменяет отсутствующую версию источника. Для FILE первична дата в имени/содержимом по утверждённому шаблону; тот же/старый файл вправе только вставить ранее отсутствующий ключ.
4. Новая запись → INSERT; изменённые **разрешённые** поля → сохранение BEFORE/AFTER и UPDATE; равные поля → SKIP. Не пришедшее поле отличается от явного `null`; очистка `null` возможна только если `allow_explicit_null=true` у AUTHORITATIVE источника.
5. Ошибка любого вложенного target/ключа/преобразования → rollback **всех** применяемых целевых таблиц этого объекта без частичного результата; диагностика логируется безопасно отдельно. Журналы ETL/DQ можно использовать по существующим контрактам, без их изменения в I02-02.
6. Контроль исчезновения работает лишь для явно помеченной цели, при доказанном полном успешном снимке **той же области** (включая всю пагинацию, неустаревшем поколении, без частичных ошибок). Отсутствие → MISSING и WARNING («Предупреждение») без удаления, хранение `first_missing_at/last_seen_at/missing_count`; возвращение → REAPPEARED event. Частичный, incremental или старый снимок не меняет статус отсутствия.
7. Ретрай идентичного набора не создает дублей истории, событий или повторного применения. Решение о повторном запуске остаётся объектовым, групповой планировщик — I15.

## 5. Конфликты, безопасность и миграционная совместимость

- **CRM_RETAIL**: оставить неизменными `meta.source_system`, `meta.source_object`, `meta.mapping_rule`, `meta.column_contract`, `etl.batch_run`, `etl.job_run`, `etl.watermark`, `dm.refresh_retail_application()` и `dm.retail_application_history`, включая текущий FULL/CONTINUE. Новые указатели версий применяются только к явно переведённым в новый контур системам; отсутствие `integration_system_current` не меняет legacy поведение.
- **Профили/секреты**: ссылочный `secret_ref`, серверная проверка полномочий, redaction ошибок; историческая публикация закрепляет ссылку/несекретные настройки, а не пароль. При отзыве/смене секрета rollback требует повторной проверки доступности. Конкретная модель ролей и хранилища — I02-03.
- **Структура целевых таблиц**: никакого автоматического ALTER/DDL при сохранении маппинга или публикации. Добавление поля/изменение ключа/исторических данных требует отдельной согласованной операции; несовместимость → STOP до записи.
- **Источник истины для данных**: AUTHORITATIVE единственный на физическую колонку, вставка из иных источников только INSERT_ONLY; неявное обнуление запрещено. Смена владения между опубликованными системами требует проверки отсутствия пересекающихся активных запусков.
- **Audit**: ключи и изменения могут включать персональные данные; выдача, маскирование и хранение истории ограничиваются будущими правилами безопасности (I02-03). Не логировать raw токены, пароли, DSN или несанкционированные полные payload.
- **Rollback миграций**: отличается от rollback версии системы: переключение конфигурации не является откатом схемы PostgreSQL или данных. План DDL rollback и резервирования — I02-04 с отдельным разрешением на исполнение.

## 6. Критерии приёмки модели I02-02

| ID | Обязательная проверка проекта / будущий тест | Ожидаемый результат |
|---|---|---|
| A01 | Чужая группа/система в связи объекта или конфигурации | FK / проверка принадлежности запрещает |
| A02 | Чужая система или DRAFT как current version | Атомарное переключение отклонено; текущая версия сохранена |
| A03 | Публикация изменённого после проверки DRAFT | Хеш/ревизия не совпадают; отказ без побочных эффектов |
| A04 | Enabled объект не прошёл проверку, остальные прошли | Полная публикация одной системы заблокирована |
| A05 | Rollback старой версии при несовместимой новой структуре | Отказ, текущая конфигурация и данные не изменены |
| A06 | API отдаёт клиент+договор+3 залога, у залога ошибочный ключ | Все изменения этого объекта откатываются |
| A07 | Повторяются те же значения | 0 новых исторических изменений |
| A08 | Два API пытаются изменить одну физическую колонку | Публикация конфликтующего второго AUTHORITATIVE отклонена |
| A09 | Дополнительный API содержит старое ФИО клиента | INSERT_ONLY не изменяет существующее значение |
| A10 | Нет поля в payload / явный NULL без разрешения | Ранее сохранённое значение не стирается |
| A11 | Более старый DB/API запуск завершился после нового | Не перезаписывает успешно применённую новую запись |
| A12 | Старый/равнодатный FILE, есть ключ / ключ отсутствует | Существующая запись не обновлена / новая вставка разрешена |
| A13 | Частичная пагинация или ошибка FULL | Нет ложных MISSING и нет частично применённых данных |
| A14 | Полный валидный снимок не содержит прежний ключ | MISSING, WARNING, first_missing/last_seen/count; запись сохранена |
| A15 | Запись вернулась в последующем полном снимке | REAPPEARED event, история изменений не повреждена |
| A16 | Сохранили DRAFT, сняли галочку, не публиковали | Рабочая версия и будущие запуски не меняются |
| A17 | Новая публикация исключает объект во время его старого запуска | Старый запуск закреплён, новые запуски исключённого объекта запрещены |
| A18 | Существующие CRM_RETAIL загрузки, отчёты, история, DQ | Регрессионные проверки PASS без изменения legacy контрактов |
| A19 | Попытка получить секрет через UI/API/лог | Секрет не возвращён и не разглашён |
| A20 | Сохранение настроек системы | ETL и расписание не стартуют |

**Статус проверок:** A01–A20 — **критерии**, а не выполненные испытания. Фактическая работоспособность должна быть проверена на этапах I03–I14. Для закрытия именно I02-02 необходимо одобрение данного контракта и фиксация решения в *актуальном локальном* roadmap.
