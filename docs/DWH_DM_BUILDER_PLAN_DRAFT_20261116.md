# Проект плана: конструктор витрин DM (шаг «ODS → DM»)

> Статус: **ПРОЕКТ** (16.11.2026), на утверждение пользователя. ID итерации и задач — только с согласия пользователя (условно «Ixx» ниже).
> Основание: подтверждение пользователем логики слоёв 16.11.2026 (вопрос о витрине по пенсиям из шага 9 I17).

## 1. Цель

Третий шаг общего механизма загрузки: после успешного ODS заполняются витрины `dm`, которые собираются из одной или нескольких таблиц ODS по общим ключам, с приоритетом источников и агрегатами. Витрины настраиваются в интерфейсе без ручного SQL и сразу доступны «Отчётности» и ИИ-помощнику (с правом доступа).

## 2. Логика пользователя (подтверждена 16.11.2026)

1. Интеграция загрузила STG.
2. STG успешен → заполняется ODS.
3. ODS успешен → заполняется DM.

DM может брать данные из нескольких таблиц ODS (например, клиенты, договоры, счета) по общему ключу, который в таблицах может называться по-разному (`client_id`, `cust_id`, …), с правилом приоритета. Пользователь выбирает поля из всех таблиц и агрегаты (сумма остатков по счетам, количество договоров и т. п.).

## 3. Что есть сейчас (факты)

| Часть | Состояние |
|---|---|
| STG и ODS по объекту | Общий механизм (I05–I08, I06-05): «Маппинг», «STG → ODS», ручной запуск; ODS — только после успешного STG |
| DM | В общем механизме **нет**. Единственная витрина — CRM: отдельный конвейер `refresh_marts.py` → функция БД `dm.refresh_retail_application` (SQL не в git) → `dm.retail_application_history` → `dm.v_retail_application_current` |
| Связь объектов между собой | Нет (группы — I15 `DEFERRED`) |
| Расписание | Нет (I09 `PLANNED`) |
| Общие ключи между таблицами, приоритет, агрегаты | Нет |
| ИИ-помощник | Работает только с витринами `dm` из белого списка (016); пенсий в `dm` нет |

## 4. Решения на утверждение (рекомендации)

| № | Вопрос | Рекомендация |
|---|---|---|
| Д1 | Зерно витрины | Обязательно: «одна строка — один <сущность>» (клиент, договор, счёт). Каждая таблица сначала сворачивается до ключа зерна, потом таблицы соединяются — суммы не удваиваются |
| Д2 | Общие ключи | Каталог сущностей: «Клиент» → `clients.client_id`, `contracts.cust_id`, `accounts.customer_no`; при объявлении проверяется совместимость типов. В первой версии ключ — одно поле |
| Д3 | Приоритет | Для поля, которое есть в нескольких таблицах, — порядок таблиц; берётся первое непустое значение |
| Д4 | Агрегаты | Только из списка: сумма, количество, количество различных, минимум, максимум, среднее. Простые фильтры по таблице (поле, оператор из списка, значение) |
| Д5 | Хранение | Витрина — таблица `dm`, заполняемая шагом 3 (быстрые отчёты, журнал и ошибки как у ODS); не представление |
| Д6 | Обновление | Полная перезаливка в одной транзакции (читатели видят старые данные до конца); инкремент — позже |
| Д7 | История витрины | Только текущее состояние; история остаётся в ODS |
| Д8 | Запуск | Вручную и автоматически после успешного ODS любой входящей таблицы; по расписанию — вместе с I09 |
| Д9 | Структура таблицы | Проект DDL строится системой и применяется пакетом после сверки SHA-256, как проекты STG/ODS (009, 013); после публикации изменение структуры — новая версия и новый проект |
| Д10 | Права | Настраивает `ADMIN_INTEGRATION_MANAGE`; у витрины — право просмотра для «Отчётности» и флаг «доступно ИИ-помощнику» (строка белого списка 016 с тем же правом) |
| Д11 | CRM | После приёмки — I18 переводит CRM на конструктор; ручная функция уходит |

## 5. Шаги до DONE (конечный список)

1. Утверждение плана, ID итерации и задач.
2. Разбор на сервере только на чтение: схема `dm` (владелец, права по умолчанию), объекты и функция витрины CRM, связь с «Отчётностью».
3. Пакет БД: каталог сущностей и ключей, определения витрин с версиями, проекты DDL, журнал запусков шага DM, функции для `dwh_app` и `dwh_etl`; E0 в песочнице.
4. E1 и E2 пакета на сервере.
5. Backend: API конструктора, генерация SQL заполнения (зерно, приоритет, агрегаты, фильтры), движок шага 3 с журналом и ошибками; тесты и сквозная проверка в песочнице на синтетических «клиенты / договоры / счета» с разными названиями ключа.
6. Интерфейс: каталог ключей, конструктор витрины, вкладка витрин в «Загрузках» (состояние, запуск, ошибки); build, ESLint 0/0, проверка в браузере.
7. Выпуск; первая витрина — пенсии (одна таблица ODS): проект DDL → пакет применения → заполнение → отчёт и вопрос ИИ-помощнику.
8. Приёмка на сервере (администратор и «аудит»), регрессия CRM.
9. Реестр функциональности, `DONE` после подтверждения пользователя.
