# I09 — Расписание загрузки отдельного объекта

<sub>План утверждён пользователем 23.11.2026 (П1–П10 = A). Итерация начата решением пользователя 23.11.2026.</sub>

## 1. Задача

Сейчас объект загружается только вручную: «Загрузки» → «Объекты» → «Запустить» создаёт заявку `etl.object_run_request` (пакет 015), диспетчер на сервере (`dwh-dispatcher`, опрос раз в 5 с) выполняет STG → ODS, затем витрины (I19). I09 добавляет **расписание у отдельного объекта**: диспетчер сам создаёт заявку в назначенное время.

Задачи roadmap: I09-01 — каталог расписаний с часовым поясом и защитой от наложения запусков; I09-02 — экран создания, изменения, включения и отключения; I09-03 — в истории видно, ручной запуск, плановый или повторный, дублей нет.

Согласованные ранее правила (roadmap, раздел 1.2): расписание и ручные запуски — **вне «Администрирования»** (в «Загрузках»); сохранение настроек и публикация **не запускают** загрузку; ручной запуск не включает расписание. Групповые расписания — I15, не в v1.

## 2. Что известно по коду (до описи)

- Очередь: одна активная заявка на объект (уникальный индекс `object_run_request_active`) — повторная заявка, пока идёт загрузка, невозможна; это и есть защита от наложения.
- Виды заявки: `RUN` (по стратегии версии), `CONTINUE_ODS`, `FULL_RERUN`; заявку создаёт пользователь (`requested_by_user_id` обязателен).
- Диспетчер — `tools/server/dispatcher_service.py` → `etl/src/run_request_dispatcher.main()` под `dwh_etl`.
- Кода и таблиц расписаний в git нет; есть ли остатки старого механизма CRM в базе — покажет опись.

## 6. Шаг 3 — песочница (23.11.2026)

**Пакет 032** (`database/migrations/032_object_schedule.sql`, владелец `dwh_admin`):
- `etl.object_schedule` — одно расписание на объект (П1): периодичность `EVERY_MINUTES` (15–720), `EVERY_HOURS` (1–24), `DAILY`, `WEEKLY` (дни 1–7), время ЧЧ:ММ, вид загрузки `RUN` / `FULL_RERUN` (П8), повторы 0–3 через 5–60 мин (П7), пояс `Asia/Baku` (П3), автор включения (П10), `next_run_at`; ограничения формы проверяет база;
- `etl.object_schedule_event` — что сделал планировщик: `QUEUED`, `RETRY_QUEUED`, `SKIPPED_BUSY` (П5), `SKIPPED_NOT_READY`;
- `etl.object_run_request` + `trigger_kind` (`MANUAL` / `SCHEDULED` / `RETRY`), `schedule_id`, `attempt`, `retry_of_request_id`; у старых заявок — `MANUAL`; повтор одной заявки — не больше одного (уникальный индекс);
- `etl.object_schedule_next()` — следующий запуск строго после момента; минуты и часы — по сетке от 2026-01-01 00:00, поэтому время сохранения не сдвигает запуски;
- `etl.object_schedule_ready()` — объект можно грузить (активны объект и источник, маппинг `READY`), те же условия, что у ручного запуска;
- `app.object_schedule_save` / `app.object_schedule_list` (`dwh_app`; сессия и право — `app.integration_run_admin_session_user`, П9) — сохранение не создаёт заявку, событие `OBJECT_SCHEDULE_SAVED` в журнале аудита;
- `etl.object_schedule_fire(worker)` (`dwh_etl`) — наступившие расписания → заявки `SCHEDULED` от автора включения (П4, П10), занятый объект — пропуск с записью (П5), после простоя — один запуск, следующий считается от текущего времени (П6), неудачная плановая заявка — повтор `RETRY` (П7), если после неё не было новой заявки; событие `OBJECT_RUN_REQUEST_CREATED` с видом запуска;
- откат `032_object_schedule.down.sql` отказывает, если есть расписания или плановые заявки (тогда — копия `pre-032`).
