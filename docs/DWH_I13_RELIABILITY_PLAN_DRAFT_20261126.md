# I13 — контракты, ошибки, права и надёжность загрузок (I13-01…I13-04): проект плана

Статус: **проект 26.11.2026**, ждёт утверждения пользователя (решения Р1–Р5). Остальные задачи I13 уже закрыты (`DONE`/`CANCELLED`), I13-09 — `DEFERRED` (доступ к `OPERATION_COLLECTOR`, ждёт владельцев источника, в этот план не входит).

## 1. Задачи (roadmap, без изменений формулировок)

| ID | Задача | Критерий завершения |
|---|---|---|
| I13-01 | Любой schema drift относительно утверждённой схемы → STOP | Подробный лог, никакой частичной загрузки |
| I13-02 | Разделить ошибки соединения, поля, ключа, преобразования, DQ и расписания | Диагностика по объекту, доступна повторная попытка |
| I13-03 | Согласовать разрешения и аудит изменений профилей/маппинга/расписания | Доступ только по разрешениям, не раскрываются секреты |
| I13-04 | Проверить конкурентность, crash-recovery, состояние транзакций и идемпотентность | Нет двойных запусков и частичных ODS-коммитов |

## 2. Что уже есть (по коду `main`, 26.11.2026)

**I13-01 — schema drift.**
- Источник БД: до чтения строк движок сверяет каждое поле маппинга с источником (`check_structure`: нет колонки или другой тип → `SCHEMA_DRIFT`) и каждое поле цели с таблицей (`check_target` → `TARGET_DRIFT`); ничего не читается и не пишется. Снимок структуры ставит версии статус `DRIFT` и пишет событие `INTEGRATION_OBJECT_CONFIG_DRIFT`.
- ODS: `check_target` для таблицы ODS до записи.
- API: поле маппинга, которого нет ни в одной записи **первой** непустой страницы → `SOURCE_DRIFT`; следующие страницы не проверяются (отсутствующее поле там станет `NULL`).
- Файлы: проверка в каждом файле → `SOURCE_DRIFT` с именем файла; ранее загруженные файлы этого запуска остаются (порядок «файл за файлом», план I12).
- Новые колонки источника, которых нет в маппинге, загрузку не останавливают (их нет в утверждённой схеме объекта).

**I13-02 — виды ошибок.**
- У каждой ошибки есть код и этап (`etl.error_log.error_stage`, `error_code`), причина по полю, числу строк и значениям (I13-08), карточки помощника по 30+ кодам (I17-10, I17-12), предупреждения файлов (пакет 035). Повторная попытка — «Запустить» / «Заново полностью» / «Продолжить (ODS)» на «Загрузки» → «Объекты».
- **Нет:** единой группы ошибки (соединение / структура / поле / ключ / преобразование / DQ / расписание / файл / система) на экране и в фильтре; кнопки повторной попытки прямо у ошибки.
- **DQ:** старые правила DQ удалены вместе со старым контуром CRM (I18, пакет 020); схема `dq` осталась пустой. Проверок качества данных у объектов сейчас **нет**.

**I13-03 — права и аудит изменений.**
- Изменения маппинга STG/ODS, публикация таблиц, подключение и пароль, объекты API и файлов, расписания, заявки, витрины идут через функции базы с проверкой сессии и права и пишут `audit.security_event` (пакеты 005, 008, 012, 018/019, 021, 028, 032–034). Пароли и `secret_ref` не показываются (I02-03, I13-05).
- Полной описи «какая функция меняет данные без записи в журнал» ещё не было — её даёт шаг 2 (часть A/B).

**I13-04 — конкурентность и восстановление.**
- Одна активная заявка на объект (пакет 015), блокировка объекта на время запуска (`etl.object_run_begin`), захват заявок под сессионной блокировкой, потерянная заявка закрывается `DISPATCHER_LOST`, сторожа источника (`LOCK_TIMEOUT`, `SOURCE_NO_RESPONSE`), время заявки (`TIMEOUT`).
- Объект до 100 000 строк пишется одной транзакцией. **Больше 100 000 строк** — порциями с фиксацией каждой (I21, решение Б5, 18.11.2026): при ошибке в середине записанные порции STG **и ODS** остаются, повтор их не дублирует (запись по ключу). Это расходится с критерием I13-04 «нет частичных ODS-коммитов» и с I13-01 «никакой частичной загрузки» — нужно решение Р2.
- Сценарии «процесс убит посреди запуска», «две заявки одновременно», «расписание и ручной запуск в одну минуту» в одном наборе тестов не проверялись. В песочнице опись уже нашла заявки `RUNNING` с завершённым `FAILED` запуском (остатки прерванных сквозных проверок) — такой сценарий войдёт в проверки.

## 3. Решения

| № | Вопрос | Варианты | Рекомендация |
|---|---|---|---|
| Р1 | Проверка полей API на каждой странице | **A** — проверять каждую страницу, поле маппинга отсутствует во всех записях страницы → `SOURCE_DRIFT`, запуск останавливается до записи (порция не пишется); **B** — оставить только первую страницу | **A** |
| Р2 | Большие объекты (> 100 000 строк) и критерий «без частичной загрузки» | **A** — оставить Б5 (порции остаются, повтор идемпотентен), в ошибке и в «Загрузках» явно писать «записано порций N из M, повторите загрузку», критерии I13-01/I13-04 уточнить: «объект до одной порции — без частичной записи, больше — частичная запись видна и восстанавливается повтором»; **B** — STG порциями, а ODS одной транзакцией (долгая транзакция и блокировка таблицы ODS на время записи); **C** — всё одной транзакцией (возврат к пределу I06, отказ от I21) | **A** |
| Р3 | DQ в I13-02 | **A** — проверки качества данных у объектов в I13 не делаем: группа «DQ» в справочнике ошибок резервируется, сами проверки — отдельной задачей с новым ID по вашему решению; **B** — простые правила в I13 (обязательное поле, диапазон, шаблон, уникальность) — новый пакет БД, экран правил, шаг проверки в движке | **A** |
| Р4 | Повторная попытка у ошибки | **A** — в «Ошибки и история» → «Ошибки ETL» у ошибки последнего запуска объекта кнопка «Повторить» (та же заявка, что «Запустить»; для ошибки ODS — «Продолжить (ODS)»), права и проверки прежние; **B** — только «Загрузки» → «Объекты», как сейчас | **A** |
| Р5 | Как проверять I13-04 | **A** — набор автоматических проверок в песочнице (убитый процесс в STG и в ODS, две заявки сразу, расписание + ручной запуск, повтор после частичной записи, падение базы посреди записи) + на сервере только опись (шаг 2) и одна контролируемая проверка на тестовом объекте `PV_FILES` (остановка диспетчера во время загрузки); **B** — только песочница | **A** |

Группа ошибки (I13-02) — свойство кода, задаётся в одном справочнике кода (рядом с базой знаний помощника); новые коды без группы не проходят тест. Коды API и базы не меняются (правило 10).
