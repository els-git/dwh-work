# I20 — Вход через LDAP / Active Directory

<sub>Утверждён пользователем 19.11.2026 (Д1–Д9 по рекомендациям, состав пакета 024 — раздел 6.3) · I20 `IN_PROGRESS`</sub>

## 1. Требование пользователя (17.11.2026)

Входить в DWH не только по локальному паролю, но и учётной записью домена. При создании пользователя администратор выбирает: локальный разовый пароль или LDAP / AD.

## 2. Что есть сейчас (проверено по коду 19.11.2026)

- Каталог пользователей (`backend/src/dwh_api/user_catalog.py`, «Администрирование → Пользователи»):
  - уже хранит способ входа `auth_provider` — `LOCAL`, `LDAP`, `AD`, `OIDC` — и внешний идентификатор `external_subject`;
  - пользователя `LDAP` можно создать без пароля; пароль обязателен только для `LOCAL`.
- Вход (`backend/src/dwh_api/auth.py`, `POST /api/auth/login`):
  - берёт пользователя функцией базы `app.auth_get_local_user` и сверяет только локальный хеш пароля;
  - пользователь `LDAP` войти не может: у него нет хеша.
  - Неудача пишется `app.auth_log_login_failure` (`INVALID_CREDENTIALS`), успех создаёт сессию `app.auth_create_session`.
- Смена пароля (`/api/auth/change-password`) уже разрешена только `LOCAL`.
- Функции входа базы (`app.auth_*`) созданы до git: их текст и права нужно прочитать на сервере (шаг 2).
- Связи сервера `app-dwh-srv` с контроллером домена ещё нет. Сервер без интернета; новые пакеты Python приходят в выпуске (`deploy/requirements-server.txt`).

## 3. Что ждём от инфраструктуры

| № | Сведения | Зачем |
|---|---|---|
| И1 | Имя (FQDN) контроллера домена — лучше два, основной и резервный; порт LDAPS (636) | подключение |
| И2 | Открыт ли доступ `10.1.20.20` → контроллер, TCP 636 | без этого вход невозможен |
| И3 | Сертификат корневого (и промежуточного) УЦ домена в формате PEM | проверка, что DWH говорит именно с контроллером (без него LDAPS не проверить) |
| И4 | Учётная запись для интеграции — **уже выдана** (логин и пароль у пользователя) | поиск пользователей в каталоге |
| И5 | Где искать пользователей: base DN (например `OU=Users,DC=bank,DC=local`); по какому атрибуту входят (`sAMAccountName` или `userPrincipalName`) | сопоставление имени |
| И6 | Нужна ли группа домена «Пользователи DWH» (вход только её членам) | ограничение круга |

**Логин и пароль интеграционной учётной записи в чат и в файлы не передаются.** Проверить их можно уже сейчас инструментом `tools/server/dwh_ldap_check.py --bind`: он спрашивает их на сервере, пароль не показывает и нигде не сохраняет. При внедрении пароль будет храниться зашифрованным (Д7).

### 3.1. Ответы инфраструктуры (19.11.2026)

| № | Ответ | Что из этого следует |
|---|---|---|
| И1 | Два контроллера (имена получены), порт — не 636 | имена и порт хранятся в настройках сервера (`/etc/dwh/dwh.env`), в документы не пишутся |
| И2 | Даны IP-адреса для проверки доступа с сервера | проверить TCP с `10.1.20.20` (команда в ответе) |
| И3 | «С этим портом сертификат не нужен» | если это обычный LDAP (389 / 3268), пароли сотрудников при входе пойдут по сети открытым текстом — **так нельзя**. Шифрование на этом порту даёт StartTLS; доверие к контроллеру — по отпечатку его сертификата (Д1), файл УЦ тогда не нужен |
| И4 | Учётная запись интеграции выдана | проверка `--bind` — только по зашифрованному и проверенному соединению |
| И5 | Вход как `vtbaze\user` или `user@vtbaze.local`; пользователей искать в двух папках (OU) | Д2: принимаются оба вида и просто `user`; поиск по `sAMAccountName` в обеих OU |
| И6 | Группа не нужна | проверки группы нет |

## 4. Решения (утверждены 19.11.2026)

| № | Вопрос | Рекомендация | Другой вариант |
|---|---|---|---|
| Д1 | Протокол и доверие к контроллеру | **Шифрование обязательно:** на выданном порту — StartTLS (если это LDAP 389 / 3268) или LDAPS. Доверие — по **отпечатку SHA-256 сертификата каждого из двух контроллеров**: `dwh_ldap_check.py` показывает отпечаток, пользователь сверяет его с инфраструктурой, и отпечатки записываются в настройки сервера. При смене сертификата контроллера вход через домен останавливается до записи нового отпечатка. Файл УЦ — если инфраструктура его даст, тогда отпечатки не нужны | Без шифрования — **не допускается** (пароли открытым текстом); без проверки сертификата — тоже нет (подмена контроллера) |
| Д2 | Как проверяется пароль | Пользователь вводит `user`, `vtbaze\user` или `user@vtbaze.local` — DWH приводит к `user`. Интеграционной учётной записью ищет `sAMAccountName=user` в двух OU, проверяет, что учётная запись включена, берёт её DN и `objectGUID`; затем проверяет пароль входом от имени пользователя. Пароль пользователя DWH не хранит и не пишет в журнал. Основной контроллер, при недоступности — резервный | B — сразу вход `user@vtbaze.local` без поиска (нельзя заранее проверить, что учётная запись включена) |
| Д3 | Кто может войти через домен | **Только заведённые в DWH:** администратор создаёт пользователя с входом `LDAP` и даёт ему роли в DWH. Неизвестное DWH имя — отказ | B — создавать пользователя автоматически при первом входе членов группы И6 (без ролей до назначения администратором) |
| Д4 | Сопоставление | Имя пользователя DWH = `sAMAccountName` (без учёта регистра); при первом входе в `external_subject` записывается `objectGUID`. Дальше сверяется GUID: переименование в домене не теряет связь, чужой однофамилец с тем же именем не войдёт | B — только по имени |
| Д5 | Отключён или заблокирован в домене | Отказ входа с понятной причиной в журнале («учётная запись домена отключена / заблокирована / пароль истёк»); пользователю — общий текст «Неверное имя или пароль» (не раскрываем состояние учётной записи) | — |
| Д6 | Контроллер недоступен | Вход через домен невозможен (fail-closed), сообщение «Служба входа домена недоступна»; **локальные администраторы (`LOCAL`) входят всегда** — резервный вход для восстановления | — |
| Д7 | Хранение пароля интеграционной учётной записи | **`systemd-creds`** на сервере (как мастер-ключи SecretStore, I16): шифруется ключом сервера, доступен только службе `dwh-api`; задаётся инструментом с вводом без показа | B — SecretStore (там учётные записи источников; для входа в DWH нужна отдельная сущность) |
| Д8 | Журнал | Каждый вход: способ (`LOCAL` / `LDAP`), успех или причина отказа (`INVALID_CREDENTIALS`, `LDAP_ACCOUNT_DISABLED`, `LDAP_UNAVAILABLE`, `LDAP_GUID_MISMATCH`); без паролей. Если функции входа базы не принимают причину — пакет 024 (решение на шаге 2) | — |
| Д9 | Группы домена → роли DWH | **Не в I20:** роли назначаются в DWH, как сейчас. Связь групп с ролями — отдельной задачей, если понадобится | B — включить в I20 |

  - Расшифровка отказов AD: неверный пароль, учётная запись отключена, заблокирована, пароль истёк и др.

## 7. Не входит

Единый вход Kerberos / SSO в браузере, OIDC, группы домена → роли DWH (Д9), смена пароля домена из DWH.

### 6.1. Доработка проверки под ответы инфраструктуры (19.11.2026)

`dwh_ldap_check.py`:
- `--port` любой: LDAPS на 636 / 3269, StartTLS на остальных (`--tls` — вручную).
- Порт без шифрования (контроллер отказал в StartTLS) — `FAIL` с причиной: пароли пошли бы открытым текстом.
- Сертификат контроллера всегда показывается: субъект, издатель, срок, имена, **SHA-256**. Доверие — `--pin <SHA-256>` (отпечаток, сверенный с инфраструктурой) или `--ca-file`.
- `--bind` — только по проверенному соединению, иначе `SKIP`.

Проверки: тесты StartTLS и сверки отпечатка; имитация контроллера в песочнице (LDAPS, StartTLS, отказ в StartTLS):
- без доверия — отпечаток показан, `FAIL`;
- верный отпечаток и пароль — `PASS`;
- чужой отпечаток — `FAIL`, пароль не отправлен;
- отказ в StartTLS — `FAIL` с причиной;
- LDAPS с УЦ и неверный пароль — «AD: wrong password».

### 6.2. Проверка связи на сервере (19.11.2026)

- Контроллер 1, выданный порт: без `--pin` — `FAIL` «сертификат не доверен» (ожидаемо, отпечаток показан); с `--pin <SHA-256>` (сверен пользователем) и `--bind` — `4 BIND PASS 0 success`, `LDAP_CHECK_RESULT: PASS`. Шифрованное соединение и вход интеграционной учётной записью работают.
- Контроллер 2: с `--pin` и `--bind` — `BIND PASS`, `LDAP_CHECK_RESULT: PASS`.
- Первые проверки `--bind` выполнены личной учётной записью пользователя. Затем **служебная учётная запись, выданная администраторами**, проверена на обоих контроллерах: `4 BIND PASS 0 success`, `LDAP_CHECK_RESULT: PASS`. Её DWH и будет использовать (Д2, Д7); логин в документы не пишется.
